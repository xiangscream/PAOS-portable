# skill-engineering-change

**只回答"怎么做"**：如何把一个工程变更安全地实现、验证并形成可复核的落地证据。
它不承担任何任务的责任、权限、生命周期或收口；不复制工作流程的语义；不自动授予写入、push 或 merge 权限。是否执行、改动范围与落地权限由当前任务与批准范围决定。

这不是一套必须全跑的固定仪式：**验证深度由风险与改动面决定**，逐步选择，而不是无条件跑满所有层。

## 1. 先读合同与当前事实

- 读取**预期契约**：需求/Issue/验收口径/相关不变量，以及该变更被要求满足的行为。
- 读取**当前事实**：实际代码/配置/依赖/环境的现状，而不是凭记忆或历史报告推断。
- 明确**边界**：这次改动应触碰什么、明确不应触碰什么（数据、兼容性、他人负责面）。
- 固定要执行与要验证的**候选/基线**（用稳定引用），以便他人可复现；这条纪律属本技能，不进入工作流程。

## 2. 有界实现

- 变更范围与已确认的契约一致；不顺手扩大改动面。
- 遵循目标代码库/项目已有的约定、结构与工具链，而不是引入新的未授权依赖或风格。
- 小步、可回退；把行为变化与纯重构区分开。

## 3. 按风险选择证据层

以下各层是**选项**，按适用风险与改动面选取，不是固定门禁：

- **focused 回归**：针对改动涉及的行为做最小但决定性的验证。
- **full verifier / 边界卫生**：当改动影响面广或涉及共享契约时，跑项目现有的完整校验与静态检查。
- **真实机器 / 跨运行时 smoke**：当"原生行为"本身是契约的一部分时（真实进程、真实文件系统、真实路径/编码、跨平台语义），用真机实验证，而不是仅靠 mock。
- 只对**风险足够**的变更请求独立复核；低风险小改动不必套用重仪式。

记录每层证据的**结论与命令**，而不仅是"跑过了"。

## 4. 区分历史问题与本次回归

- 验证失败时先定位：是**既有问题**（存在于基线）还是**本次引入的回归**。
- 用基线对照说明差异，不要把历史问题记成本次责任，也不要用"本来就有"掩盖真实回归。

## 5. 形成可复核报告与 merge-gate evidence

- 报告包含：改动意图、契约、候选/基线引用、证据与命令、结果、已知限制、未做项。
- **merge-gate evidence**：能让他人独立判断"是否满足契约"的最小决定性证据集合，而非面面俱到。
- **自报"完成"不构成验收**：本技能不授予 merge/acceptance 权限；落地与验收遵循相应发布、复核与接受流程。
- 若需要独立复核，把候选/基线固定成稳定、可定位的引用交给复核者。

## 检查问题（自用）

- 我是否先读了契约和当前事实，而不是先写代码？
- 这次改动是否仍在授权范围内？
- 我的证据深度是否与风险和改动面相称（既不过度也不不足）？
- 失败是历史问题还是我的回归？我怎么证明？
- 报告是否足以让他人独立作出决定？
