# 产品功能挖掘

## 核心目标

从已有材料中找到真正能改变用户行为的功能，并回答四个问题：

1. 用户为什么第一次想买；
2. 用户今天为什么会开机；
3. 一次使用结束后留下什么；
4. 哪些软硬件能力可以让体验越用越完整；
5. 最终由哪条产品力主线把这些功能连在一起。

不要把“发现了更多功能”当成完成。最终应形成一条能说清楚、能演示、能讨论实现方式的产品体验，并明确回答哪些功能应成为核心、哪些只是辅助、哪些暂时不应加入。

## 基本原则

- 先调研，后综合。不得只读一份主稿或几条评论就开始重写产品结论。
- 先理解当前产品，再发散功能。不得因为相邻市场很热就改变产品对象。
- 从用户行为写功能：谁在什么时刻做什么，系统怎样回应，最后得到什么。
- 优先寻找功能之间的复用与协同，避免每个想法都新增一套硬件、链路和入口。
- 同时看购买吸引力、使用频率、结果价值、信任与维护，不只看首发传播性。
- 将技术能力翻译成用户可感知的结果，不把芯片、模型、自由度或接口本身写成价值。
- 研究严谨放在上游，产品综合保持单向推理。不要在成稿中一边下结论、一边逐句审判自己的结论。
- 保留当前阶段的判断强度，但用自然产品语言表达。不要默认套 Gate、证据等级、审计台账或“结论边界”。
- 信息足够时必须敢于给方向性结论。条件式结论也要说明当前更倾向哪一条路线。
- 未经用户要求，不替公司做最终立项、资源和商业决策；给出产品判断、方案关系和需要讨论的问题即可。

## 工作流

### 1. 明确研究对象并完整收集材料

先明确这次要回答的产品问题，例如：

- 哪项功能能提高日常使用频率；
- 哪种功能组合能形成新品类体验；
- 现有技术能力能否转成用户价值；
- 两种结构或系统方案会怎样改变产品力；
- 当前文档为什么仍像功能清单。

随后读取并搜索：

- 当前产品思考、PRD 或报告主稿；
- 最新会议纪要和人工修改意见；
- 竞品与相邻品类资料；
- 购买前评论、已购体验、长期使用和放弃使用原因；
- 同类产品的成功案例与失败案例；
- 技术方案、结构讨论和内部可复用能力；
- 成本、可靠性、维护与配件信息（功能涉及硬件时）；
- 已有版本之间的差异。

本地材料先用 `rg --files` 和关键词系统搜索，不凭文件名猜内容。涉及当前产品、价格、销量、规格或社区反响时，补充网络调研，并优先使用官方材料、论文、直接用户反馈和可复现实测。

调研至少覆盖以下视角，确实没有资料时再记录缺口：

| 视角 | 需要回答 |
| --- | --- |
| 直接竞品 | 用户为什么买、实际怎样用、哪里失望 |
| 相邻品类 | 哪种行为和闭环已经被用户理解 |
| 成功案例 | 什么组合带来了持续使用或内容结果 |
| 失败案例 | 为什么功能很多仍没有形成高频使用 |
| 用户信号 | 第一次购买、日常开机和长期保留分别由什么驱动 |
| 内部能力 | 哪些模块、数据和经验已经存在 |
| 技术条件 | 能力上限、不可补偿项和系统耦合 |

不要在材料尚未展开时就急着写产品稿。先做一张内部推理草图，确认每条主结论都至少连接了用户行为、相邻案例或技术条件中的两类输入。

先记录不可随意修改的内容：

- 产品对象与名称；
- 固定一级、二级标题；
- 已确认的核心判断；
- 用户明确不希望出现的写法；
- 文件是否允许覆盖。

用户要求基于旧版生成新版本时，创建新文件并保留旧版。若要求严格框架，先比较新旧标题，完成后再做标题 diff。

### 2. 建立完整推理框架

完成材料收集后，先建立一条从信息到结论的单向推理链：

```text
市场与用户发生了什么
  → 现有产品为什么没有完全解决
  → 用户缺少哪段行为或结果
  → 哪组功能能补上这段闭环
  → 需要哪些软硬件共同实现
  → 相比替代方案形成什么产品力
  → 当前应得出什么结论
```

每个主要章节只负责其中一段，不要在市场、竞品、技术和机会章节重复同一句结论。

遇到相互冲突的信息时，先在内部分析中解决：

- 区分不同用户、场景、版本和使用阶段；
- 找到冲突来自参数、体验还是产品目标；
- 无法完全解决时，把它收成一个具体条件；
- 不要把双方观点交替塞进正文，让读者代替作者做取舍。

### 3. 写出当前产品的一句话与产品力主线

用普通用户能理解的语言写一句话，至少包含：

- 这是什么；
- 用户拿它做什么；
- 最终得到什么。

避免用“智能平台”“全场景”“生态”“具身智能”等抽象词替代具体体验。

若一句话仍像多个名词拼接，说明功能主线尚未形成。

再写一条产品力主线：

```text
目标用户
+ 高频触发场景
+ 核心行为
+ 独特结果
+ 关键技术支撑
+ 相对替代方案的差异
```

产品力主线不是广告口号。它应能解释为什么选这些功能、为什么删掉其他功能，以及一段产品演示应该怎样展开。

### 4. 建立四条输入线

分别提取，不要混成一张竞品清单：

| 输入线 | 重点寻找 |
| --- | --- |
| 用户与场景 | 什么时候想用、为什么嫌麻烦、什么结果值得保留 |
| 竞品与相邻品类 | 已被理解的玩法、成熟交互、失败的历史组合 |
| 公司与产品能力 | 已有硬件、算法、数据、供应链和内容链路 |
| 技术与结构 | 能力上限、不可补偿项、耦合关系、成本与维护变化 |

相邻品类用于借玩法、交互和任务闭环，不直接把其市场规模或用户全部算成本产品市场。

### 5. 从五类功能角色中挖掘机会

对每个候选功能判断它主要承担什么：

| 功能角色 | 要回答的问题 |
| --- | --- |
| 购买功能 | 用户为什么第一眼想拥有或愿意了解 |
| 频率功能 | 没有重大事件时，为什么今天仍想拿出来 |
| 结果功能 | 一次使用后得到什么可保存、可分享或可复用的结果 |
| 信任功能 | 为什么用户敢用、敢带出门、坏了还愿意继续拥有 |
| 扩展功能 | 用户和社区怎样增加新玩法，而不破坏基础体验 |

一个功能可以承担多个角色。优先保留能同时服务两类以上角色、并复用现有系统的功能。

### 6. 把功能写成完整循环

用下面的行为链检查每个重要功能：

```text
触发时刻
  → 用户动作
  → 系统响应
  → 当下反馈
  → 使用结果
  → 下次再用的理由
```

若功能只停在“系统可以做某事”，继续追问：

- 用户什么时候会主动使用；
- 它与主体验怎样切换；
- 结果在哪里出现；
- 用户为什么会再来一次。

将多个功能连成一条体验。例如：

```text
想玩路线
  → 第一视角驾驶
  → 活动和发现自然发生
  → 自动跟拍让用户进入画面
  → 系统挑出短片
  → 分享或换一条路线再玩
```

### 7. 检查系统协同，而不是只列功能

为每个核心功能写清：

- 与哪些硬件、算法、数据和交互入口共用；
- 是否会与其他模式争用相机、算力、带宽、功耗、空间或控制权；
- 能否拆分为基础体验与增强配置；
- 它改变的是产品主线，还是只增加一个附件。

优先寻找这种组合：

- 同一相机同时服务感知、预览与内容；
- 同一图传链路同时服务接管、探索和监看；
- 同一动作同时表达状态、改变机位和增加角色感；
- 同一保护结构同时解决耐久、维修和个性化。

### 8. 处理技术与结构方案

技术讨论必须回答“它能补偿什么、不能补偿什么”。

比较架构方案时：

1. 使用公平基线，让共同需要的模块同时出现在两种方案中；
2. 分开比较性能上限、成本路线和开发工作量；
3. 不把一个子系统的改善写成另一个子系统能力的替代；
4. 区分角度、平移、冲击、热、噪声、控制和内容结果；
5. 理论难以收敛时，给出能区分方案的样机和观测项。

不要只写“方案 A 更强、方案 B 更便宜”。写清楚：

- 少了什么自由度、行程或信息；
- 新增模块补回了哪一部分；
- 哪些损失仍然存在；
- 目标场景是否真正会用到这些能力；
- 怎样用同条件对比得到答案。

复杂系统优先按层分工。例如移动影像可以拆为输入抑制、被动隔振、主动姿态、算法收尾和内容处理，避免让单个模块承担所有问题。

### 9. 将相邻能力翻译为本产品能力

复用其他项目或品类经验时，按以下顺序写：

1. 原能力解决什么问题；
2. 本产品中对应的用户动作是什么；
3. 哪些模块可以直接复用；
4. 哪些环境变化会引入新问题；
5. 最终应收成什么产品模式或交互。

不要因为公司做过相似技术，就写成“可以直接搬过来”。说明新的结构、散热、链路、交互和安全条件。

### 10. 收敛产品力主线并敢于给结论

综合阶段停止继续发散，按下面四类做取舍：

| 结论类型 | 含义 |
| --- | --- |
| 核心功能 | 没有它，产品主线不成立 |
| 关键支撑 | 用户不一定为它购买，但它决定核心体验是否可用 |
| 增强功能 | 能增加覆盖或乐趣，可以分级配置或后续加入 |
| 暂不加入 | 与主线关系弱、负担过大或会把产品带向另一品类 |

结论必须使用方向明确的表达，例如：

> 我目前的判断是：A 应成为首版主体验，B 作为关键支撑，C 适合选配，D 暂时不进入产品定义。

可以给条件式结论，但不能没有方向：

> 在目标场景集中于铺装和轻度起伏路面时，当前更倾向方案 B；如果首版必须承担跳跃落地和复杂恢复，再转向方案 A。

不要用“各有优劣、后续验证”结束。说明当前为什么倾向某项，并把真正可能改变结论的条件集中列在文末，通常保留 3 至 5 个即可。

### 11. 重写产品文档

先确定最适合的输出：

- 功能机会清单；
- 单项功能讨论；
- 产品体验闭环；
- 技术选型讨论；
- 基于现有文档的 vNext；
- 面向会议的产品思考稿。

编辑长文档时：

- 保留用户指定的标题层级和顺序；
- 把新增内容放回对应章节，不在文末堆“补充模块”；
- 每章只承担一个主要问题；
- 删除前后重复的结论，但保留必要的上下承接；
- 让市场、竞品和技术最终回到产品体验；
- 开头给出产品力主线，正文沿推理框架展开；
- 最终章节明确给出当前功能取舍，不把判断留给读者；
- 结尾收敛到一段可演示的完整过程和少量具体讨论问题。

## 产品功能卡

需要逐项比较功能时，使用：

```markdown
### 功能名称

用户时刻：
用户动作：
系统链路：
当下反馈：
使用结果：
为什么适合这个产品：
复用的现有能力：
新增的工程负担：
与其他功能的关系：
最小完整形态：
```

不要强制打综合分。产品判断更适合说明功能在整体循环中的位置，以及它会带来哪些新负担。

## 写作要求

- 使用具体场景、动作和结果，少用抽象价值词。
- 明确给出“当前判断是什么”，不要每段都追加“仍需验证”“不能证明”“存在风险”。
- 对未知内容自然写成“目前更像”“先按这个量级讨论”“具体取决于……”，无需反复做证据声明。
- 少用连续的“不是……而是……”“形态是入口、功能是频率”式口号；保留一两句真正有记忆点的表达即可。
- 不把功能名写成标题后再重复解释标题。
- 不用长篇审计式免责声明冲淡产品观点。
- 不在一句产品判断后立刻补一段反方审查。必要限制集中放到对应方案条件或文末讨论题。
- 研究笔记可以保留来源、矛盾和未知；面向产品讨论的正文只呈现已经完成取舍的推理。
- 不为了显得完整而增加市场规模、合规、商业模式、组织能力等无关章节。
- 保留用户原有语气。用户要求“去 AI 味”时，优先用自然短句、真实取舍和具体工作语言。

## 停止无效发散

出现以下情况时，降级为配件、后续方向或删除：

- 找不到明确用户时刻；
- 与主产品体验没有切换关系；
- 只因竞品有或技术上能做；
- 引入一整套新硬件，却没有明显增加使用频率或结果价值；
- 需要用户自行开发才能成立；
- 功能之间互相抢相机、算力、结构空间或操作入口，却没有解决方案；
- 只能在宣传片中成立，普通使用过程没有闭环。

## 完成检查

- 产品的一句话是否比修改前更清楚；
- 是否先覆盖了竞品、相邻品类、成功与失败案例、用户、内部能力和技术条件；
- 是否存在一条从信息输入到产品结论的完整推理链；
- 是否找到购买、频率、结果、信任和扩展功能；
- 核心功能是否形成“触发到结果”的完整循环；
- 相邻品类是否只借了可转译部分；
- 技术方案是否写清可补偿项和不可补偿项；
- 是否明确区分核心、支撑、增强和暂不加入的功能；
- 是否敢于给出当前倾向，而不是用“各有优劣”结束；
- 是否避免功能堆叠和审计式行文；
- 是否保留指定框架和旧版本；
- 是否给出一段可以实际演示的产品体验；
- 是否把未解决的问题收成少量、具体的会议讨论题。

## 参考模式

遇到以下复杂任务时，读取 [references/feature-patterns.md](references/feature-patterns.md)：

- 从拍摄功能中挖掘日常使用频率；
- 将单点技术组合成分层系统；
- 将其他项目的技术积累转译到新产品；
- 比较执行器、云台或结构路线；
- 将保护、个性化和社区合并设计；
- 去除产品文档中的审计味和重复表达。
