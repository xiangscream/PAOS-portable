# 产品功能挖掘参考模式

## 0. 研究与综合分开

研究阶段可以保留：

- 完整来源；
- 相互冲突的用户反馈；
- 成功与失败案例；
- 不同技术方案的条件；
- 尚未解决的参数与成本。

综合阶段不要把这些原样倾倒进正文。沿一条推理链完成取舍：

```text
用户行为与市场变化
  → 当前体验缺口
  → 功能组合
  → 系统实现
  → 产品力差异
  → 当前结论
```

读者需要看到作者怎样得出结论，不需要看到作者在每句话后重新怀疑一次。

## 1. 从低频任务中找到高频玩法

低频任务本身可能有价值，但不足以支撑日常使用。不要直接增加无关功能，先寻找与核心硬件共用的高频行为。

```text
低频任务：重要活动时自动拍摄
高频行为：平时通过第一视角驾驶和探索
共同能力：相机、云台、底盘、图传、录像
内容闭环：探索中产生事件，系统自动留下片段
```

挖掘问题：

- 用户没有原始任务时，核心硬件还能创造什么活动；
- 活动结束后是否自然产生核心任务需要的结果；
- 两种状态能否在一次使用中切换，而不是两个独立 App。

## 2. 将单点功能变成分层系统

当一个问题由不同频率、方向或物理机理组成时，不要押在单一模块上。

移动影像示例：

| 问题 | 适合的层 |
| --- | --- |
| 路面输入和大冲击 | 轮胎、结构行程、路径与速度 |
| 高频细振 | 柔性悬置与结构阻尼 |
| 低频大幅姿态 | 主动云台与底盘前馈 |
| 剩余角抖动 | 相机侧 IMU、EIS、rolling shutter 修正 |
| 大量无效素材 | 事件标记、自动选片与短片生成 |

先说明每层负责什么，再说明层与层之间的接口和互相影响。

## 3. 公平比较结构方案

不要用“强底盘但无云台”对比“弱底盘但有云台”。将共同需要的相机、云台或传感器同时加入两种方案。

```text
方案 A + 共同模块：观察能力上限
方案 B + 共同模块：观察成本和简化空间
```

重点问：

- 新模块补的是角度、位置、冲击还是信息；
- 被删减的自由度、行程和恢复能力能否补回；
- 增大剩余执行器只能补功率，还是也能补工作空间；
- 同一路面、速度、负载和算法下，结果差异是什么。

理论难以收敛时，定义最小样机：

- 先用现成部件看低成本方案下限；
- 再用完整方案看性能上限；
- 同时记录机身、任务载荷和最终输出，不只看动作视频。

## 4. 将已有技术积累转成新产品能力

复用链路：

```text
原项目能力
  → 本产品中的相同底层模块
  → 新环境带来的差异
  → 用户可理解的模式
```

例如，无人机图传经验可以复用相机、编码、无线、眼镜、头追、OSD 和录像；地面产品仍需重新处理近地遮挡、静止散热、低速控制、碰撞停止和驾驶视野。

最后应收成“探索模式”“拍摄模式”“一键回正”等产品体验，不停留在“公司有图传技术”。

## 5. 将定制外壳拆成三个真实需求

不要直接讨论高价整套换壳。按层处理：

1. 承力与安全骨架：不可随意修改；
2. 可替换保护件：解决磨损、跌倒与维修；
3. 轻量风格件：解决角色表达、礼物和社区创作。

这样，同一结构同时服务信任功能、购买功能和扩展功能。

## 6. 从相邻市场借什么

| 相邻品类 | 可借内容 | 不应直接搬用 |
| --- | --- | --- |
| RC / FPV | 手柄、走线、维护、第一视角和路线玩法 | 整套 DIY 门槛、竞速标准和全部玩家规模 |
| 跟拍无人机 | 一键模式、自动录制、快速出片 | 空中路径、飞行散热和用户规模 |
| 角色机器人 | 动作语言、外观和拥有感 | 对话助手预期和纯新奇留存 |
| 自动内容设备 | 自动筛选、惊喜内容和分享单位 | 固定设备的低运动难度 |
| 研究平台 | 结构、控制、仿真和开源工具 | 将开发者体验直接交给普通用户 |

相邻市场的作用是帮助产品找到已被理解的行为，不是替新产品证明销量。

## 7. 识别功能堆叠

以下句子通常意味着功能仍未形成产品：

- “同时支持 A、B、C、D……”
- “未来可扩展到家庭、户外、教育、巡检……”
- “通过开放 SDK 让用户自行开发场景。”
- “既是相机，也是机器人、玩具、平台和助手。”

改写时选择一个完整过程：

```text
用户为什么启动
  → 怎样操作
  → 产品如何回应
  → 最后看到什么
```

其他功能只保留与该过程有明确关系的部分。

## 8. 去掉审计味

审计式写法：

> 现有证据不能证明该功能形成独立市场，仍需通过 Gate 验证用户付费意愿。

产品式写法：

> 这项功能目前更适合作为增强玩法。先用成熟套件做出完整体验，再看有多少用户愿意为专用硬件付费。

审计式写法：

> 结论边界：该方案无法证明所有目标路面均可通过。

产品式写法：

> 它更适合铺砖、短草和缓坡；连续碎石与大台阶会很快暴露结构行程不足。

保留事实强度，但把限制写成产品条件、方案取舍或具体场景。

把反方意见放在研究笔记里完成处理。正式产品稿中只保留会改变方案的条件，例如：

> 当前优先做手机与手柄入口，眼镜作为增强套装。只有当沉浸体验成为主要购买理由时，才值得把专用图传成本放进基础主机。

这句话同时包含方向和改变方向的条件，不需要再追加一段“证据不足、仍需验证”。

## 9. 产品文档的收敛结构

当用户已有固定框架时，不另起一套目录。将内容分别放回：

1. 市场：只保留会改变产品定义的判断；
2. 竞品：写清可借鉴点和未解决体验；
3. 技术：解释功能如何实现及方案关系；
4. 机会点：把用户、玩法、结果和系统连起来；
5. 结尾：给出一段完整演示与具体讨论题。

检查同一结论是否在市场、竞品和机会点重复三次。市场章节说明“为什么有机会”，机会点章节说明“产品具体怎样做”。

最后明确写出：

```text
核心功能：
关键支撑：
增强功能：
暂不加入：
当前产品力主线：
当前结论：
```
