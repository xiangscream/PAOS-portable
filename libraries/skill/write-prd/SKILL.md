# PRD 与产品定义

## 核心原则

先定义正确的产品，再把它写正确。

保持一条可追溯链：

```text
证据与已确认决策
→ 用户任务与问题
→ 产品目标和成功指标
→ 产品能力
→ 原子需求
→ 验收标准
→ 发布后指标
```

不要用功能数量代替产品定义，不要用宣传词代替规格，不要用原型图代替交互规则，不要用“研发自行处理”代替异常与恢复策略。

## 1. 判断任务阶段

先判断用户要的是哪一种产出：

- **产品定义**：方向尚未冻结，重点回答为谁、何时、解决什么、为什么成立、首版不做什么。
- **完整产品 PRD**：覆盖产品形态、系统、软硬件、关键工作流和版本范围。
- **功能 PRD**：产品方向已定，只定义某一功能或版本增量。
- **PRD 评审/重构**：保留已确认决策，寻找歧义、缺口、冲突和不可验收项。

信息不足但不影响主结构时，继续写并显式标记假设与待确认项。只有会改变目标用户、产品形态、首版边界或关键技术路线的问题，才先向用户确认。

若项目仍处于品类探索、需要大规模竞品和用户证据研究，且 `$product-definition-research` 可用，先用它完成探索，再回到本技能生成 PRD。

## 2. 建立事实底稿

读取用户指定的全部材料，优先采用最新版本和明确决策。把输入分成四类：

- **已确认事实**：规格、现状、研究数据、法规、系统能力。
- **已确认决策**：负责人已经选择的定位、范围、优先级、路线。
- **工作假设**：为继续撰写暂时采用、仍需验证的判断。
- **开放问题**：必须由具体角色在具体时间前关闭的问题。

冲突时不要静默选边。记录冲突来源，优先级按“最新负责人决策 → 最新正式文档 → 可核验事实 → 旧稿/口头线索”处理。

产品、价格、竞品、标准、法规或平台能力可能变化时，核验当前来源。不要把无来源数字写成确定规格。

需要了解本技能从哪些软硬件 PRD 样本中提炼、或复盘常见优缺点时，读取 [references/sample-synthesis.md](references/sample-synthesis.md)；正常撰写无需加载。

## 3. 冻结产品定义

在写功能前，形成一页定义。详细方法见 [references/product-definition.md](references/product-definition.md)。

至少写清：

1. 一句话产品定义：这是什么，给谁，在什么时刻完成什么结果。
2. 第一目标用户与第一任务。
3. 触发场景、现有替代方案和具体缺口。
4. 核心价值与差异化机制。
5. 首版目标与可度量成功标准。
6. 做什么、不做什么、后续再做什么。
7. 产品形态、系统边界、关键约束和依赖。
8. 价值、易用性、可行性、商业可持续性四类风险及验证方式。

如果一句话定义需要用“全场景、生态、平台、智能化”等抽象词才能成立，继续收敛。

## 4. 选择正确的 PRD 结构

按产品类型选择结构，不要机械添加无关章节。读取 [references/prd-architecture.md](references/prd-architecture.md)：

- 硬件/消费电子：重视产品形态、接口、物理交互、状态机、参数表、功耗、可靠性、安全、生产和兼容性。
- App/PC/网页：重视入口、前置条件、页面状态、主流程、异常流程、权限、保存策略、跨平台差异和文案。
- AI 功能：重视输入输出、触发条件、控制权、置信度、失败回退、性能目标、数据与隐私、评测集和人工接管。
- 软硬一体：先画系统边界与数据/控制流，再分别写设备、端侧软件、App/PC 和云服务要求。
- 预研/Demo：把“验证假设、实验条件、观测指标、通过阈值、停止条件”放在功能清单之前。

完整 PRD 默认包含：

```text
文档控制
→ 执行摘要与产品定义
→ 背景、问题、用户和场景
→ 目标、指标、范围与非目标
→ 系统边界、角色和关键工作流
→ 需求总表
→ 详细功能/硬件/AI 规格
→ 状态、异常、兼容与非功能要求
→ 数据埋点与评测
→ 依赖、风险、开放问题
→ 验收与发布计划
→ 相关资料
```

## 5. 先画全局，再写细节

在详细需求前先产出：

- 系统组成与各端职责；
- 主要角色与权限；
- 3–7 条关键用户工作流；
- 核心状态及转换；
- 控制权分配和互斥关系；
- 版本范围表；
- 需求总表与唯一 ID。

软硬件或多端系统必须写清信号、数据、命令和结果分别从哪里来、到哪里去。多个控制入口必须定义冲突优先级。

## 6. 将功能写成可测试的原子需求

详细规则和示例见 [references/requirement-writing.md](references/requirement-writing.md)。

每条需求使用唯一 ID，并至少覆盖：

```text
ID / 名称 / 用户价值 / 优先级 / 版本
前置条件 / 触发
主行为与可见反馈
状态变化与业务规则
参数、单位、范围、步进、默认值、记忆位置
异常、超时、重试、降级、恢复
依赖、兼容、权限、数据来源
埋点或日志
验收标准
```

写需求时：

- 用“在什么条件下，系统应产生什么可观察结果”。
- 一个句子只承载一个可独立测试的行为。
- 区分用户结果与技术实现；只有实现方式属于产品约束时才固定技术方案。
- 为开关和设置写默认值、作用域、持久化位置、升级迁移和恢复默认行为。
- 为参数写单位、合法范围、步进、边界行为和不同模式下的映射。
- 为异步任务写开始、进行中、成功、失败、取消、超时和重试。
- 为状态写进入条件、退出条件、可用操作、显示反馈和异常恢复。
- 为互斥能力写优先级、阻止行为、提示文案和解除条件。
- 把“不支持”和“非目标”写清，不让研发通过猜测补产品决策。

验收标准优先写成结果清单；复杂交互可用 Given / When / Then。不要只写“功能正常”“体验流畅”“符合设计稿”。

## 7. 管理优先级和版本边界

先定义本项目的优先级语义，再使用 P0/P1/P2 或 Must/Should/Could。推荐：

- **P0**：第一任务成立、法规/安全、系统闭环或首发承诺所必需。
- **P1**：显著提升覆盖、效率或体验，缺失不破坏首版闭环。
- **P2**：增强、探索或后续扩展。

每条 P0 必须有明确验收标准、负责人或归属模块、依赖和版本。避免把“重要”全部标成 P0。

把候选功能分成“首版核心、关键支撑、增强、后续、明确不做”。版本边界改变时同步更新目标、指标、需求总表和相关章节。

## 8. 处理未知和决策

所有待确认项写入同一张表：

| ID | 问题 | 当前假设 | 决策人 | 截止日期 | 影响需求 | 状态 |
|---|---|---|---|---|---|---|

禁止裸写 `TBD`。无法确定时写成“当前按 X 撰写；若 Y，则影响 REQ-…；由 Z 在日期前确认”。

重要取舍同时记录：

| 日期 | 决策 | 备选项 | 选择理由 | 影响范围 |
|---|---|---|---|---|

## 9. 完成质量复核

按 [references/quality-checklist.md](references/quality-checklist.md) 做五轮检查：

1. 产品正确性：目标用户、第一任务、价值、范围是否一致。
2. 结构完整性：系统、流程、状态、需求、非功能、验收是否齐全。
3. 规格可执行性：默认值、范围、异常、恢复、依赖是否可实现。
4. 可测试性：每个 P0/P1 是否有可观察验收结果。
5. 一致性：术语、编号、版本、原型、参数表和相关文档是否冲突。

对 Markdown PRD 运行：

```bash
python scripts/prd_lint.py <prd.md>
```

脚本用于发现结构缺口、重复需求 ID、无责任人的 TBD、模糊规格和缺少验收章节；人工复核仍是最终标准。

## 10. 交付

按用户要求交付以下一个或多个产物：

- 产品定义一页纸；
- 完整 PRD；
- 功能需求规格；
- 需求总表；
- 产品定义/PRD 评审报告；
- 开放问题和决策清单。

从 [assets/product-definition-template.md](assets/product-definition-template.md) 或 [assets/prd-template.md](assets/prd-template.md) 复制起稿。批量管理需求时使用 [assets/requirement-matrix.csv](assets/requirement-matrix.csv)。

成稿中明确标注：版本、日期、状态、已确认范围、仍待确认事项。不要虚构负责人、发布日期、指标基线、技术参数或用户证据。
