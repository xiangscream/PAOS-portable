## 样本范围

本技能综合了以下类型的材料：

- 三份本地产品文档：机械臂影像产品、无人机图传系统、Camera Dolly 产品线；
- 三份飞书硬件 PRD：AI 摄像机/会议摄像头等；
- 一份大型 App 软件 PRD；
- 一份虚拟追踪与虚拟内容工作流资料；
- 一份产品概述与硬件/软件/App 需求表格。

归纳的是可迁移的文档模式，不把任何单一模板视为完整标准。

## 共同有效模式

### 产品定义层

- 从场景、用户类型和现有方案缺口推出产品形态；
- 用一句话定位、产品目的、模块分工和版本路线形成主线；
- 对多个候选形态做同维度比较，说明当前优先级；
- 预研用 Demo 验证技术与结构假设；
- 把复杂能力拆成“用户控制、预设轨迹、AI 控制”等控制权组合。

### 硬件 PRD 层

- 用固定目录组织：更新记录、概述、产品信息、接口、硬件交互、产品需求、适配、参数、埋点、相关文档；
- 用状态表定义按键、指示灯、电量灯、蜂鸣器；
- 用模块—说明—优先级表管理大量需求；
- 给参数范围、默认值、记忆位置和互斥逻辑；
- 将设备、App/PC、遥控器和协议文档相互链接。

### 软件 PRD 层

- 从背景、目标、资料和系统要求进入详细功能；
- 按页面/模块写入口、控件、默认状态、操作与结果；
- 使用 case 覆盖权限拒绝、搜索超时、设备断连、素材超限、崩溃恢复等异常；
- 写保存/不保存、撤回/重做、禁用条件、Toast 文案、平台差异；
- 原型与正文并列，正文承担行为规则。

### 工作流层

- 架构图展示信号、数据、控制和输出；
- 比较官方流程与自有插件流程的适用版本、复杂度和依赖；
- 把协议、端口、数据流和控制入口连接到用户工作流。

### 表格层

- 产品概述与版本记录独立；
- 需求按一级/二级分类；
- 描述、备注、优先级、提出人和研发意见分列；
- 参数和待确认项不应混在功能名称中。

## 样本中的常见缺口

- 产品背景只有宣传式简介，缺目标用户、问题证据和成功指标；
- 产品定义、项目计划、技术可行性和详细需求混在同一层；
- 大量 P0 缺统一优先级语义；
- 使用 TBD，但没有决策人、截止日期和影响范围；
- 需求表有“模块/说明/优先级”，但缺唯一 ID、版本和验收；
- 以“同现有逻辑”“见原型”代替关键规则；
- 标题中塞入整段需求，目录失去导航价值；
- 参数写范围但缺步进、默认值、持久化和边界行为；
- 异常覆盖较多，但没有统一状态机和跨端真相源；
- 预研 Demo 有任务和 DDL，但缺通过阈值与停止条件；
- 数据埋点章节存在，但未始终与产品目标和成功指标闭环。

## 综合方法

因此本技能采用三层结构：

1. **产品定义层**：用户、任务、价值、形态、差异、范围、指标、风险；
2. **系统设计层**：角色、端侧职责、工作流、状态、控制权、数据流；
3. **需求规格层**：唯一 ID、原子行为、参数、异常、依赖、埋点和验收。

这三层通过可追溯链连接，既保留样本在软硬件交互和详细状态上的优势，也补齐目标、非目标、验收、开放问题治理和产品风险验证。

## 公开参考

- SVPG, *How To Write a Good PRD*: 区分市场机会、产品策略/路线图与特定版本 PRD；强调先研究用户、竞品和团队能力，再定义明确目的、可度量目标、用户及任务。  
  https://svpg.com/assets/Files/goodprd.pdf
- SVPG, *The Four Big Risks*: 在产品发现中尽早处理价值、易用性、可行性和商业可持续性风险。  
  https://www.svpg.com/four-big-risks/
- GOV.UK Service Manual, *Writing user stories*: 用户故事应包含角色、需求和目标；验收标准应描述满足用户需要的可观察结果。  
  https://www.gov.uk/service-manual/agile-delivery/writing-user-stories
- Atlassian, *How to create a product requirements document*: PRD 应包含目标、假设、用户故事、设计、开放问题和明确的非目标，并由产品、设计和研发协作维护。  
  https://www.atlassian.com/agile/product-management/requirements
