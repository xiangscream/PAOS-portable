## 原子需求模板

```markdown
### REQ-MODULE-001 功能名称

- 用户价值：
- 优先级 / 版本：
- 前置条件：
- 触发：
- 需求行为：
- 可见反馈：
- 状态与业务规则：
- 参数与默认值：
- 异常与恢复：
- 依赖 / 兼容 / 权限：
- 数据与埋点：
- 验收标准：
  - AC1 ...
  - AC2 ...
```

一条需求只描述一个可独立实现、测试和取舍的行为。多个条件分支可以属于同一条需求，但不要把整个模块塞进一个 ID。

## 参数与默认值

参数至少写：

| 字段 | 说明 |
|---|---|
| 名称 | 用户界面与协议术语保持一致 |
| 类型 | 开关、枚举、整数、浮点、文本、文件等 |
| 单位 | ms、fps、Mbps、°、m/s、dB 等 |
| 合法范围 | 最小、最大、枚举集合 |
| 步进/精度 | 每次调整量或允许小数位 |
| 默认值 | 首次使用值 |
| 作用域 | 全局、设备、账户、项目、模式 |
| 持久化 | 保存在哪里、何时写入 |
| 迁移 | 升级后如何处理旧值 |
| 恢复 | 恢复默认、断电、卸载、重置后的行为 |
| 边界行为 | 超限、非法值、能力不支持时怎么处理 |

不要只写“支持调节 0–100”。还需写步进、默认值、实时生效还是确认后生效、是否记忆。

## 状态机

为每个状态写：

- 进入事件；
- 前置守卫；
- 状态期间允许/禁止操作；
- UI/灯光/声音/日志反馈；
- 退出事件；
- 超时和自动转换；
- 异常转换与恢复；
- 与其他状态的优先级。

状态表：

| 当前状态 | 事件 | 条件 | 系统动作 | 用户反馈 | 下一状态 |
|---|---|---|---|---|---|

常见必查状态：初始化、空闲、工作中、暂停、成功、失败、休眠、关机、配对、升级、离线、目标丢失、存储满、电量不足、过温。

## 异常与恢复

至少检查：

- 必需设备/网络/权限/存储不存在；
- 用户输入为空、非法、超限或冲突；
- 过程中断电、断网、断连、App 崩溃；
- 异步任务超时、失败、重复提交；
- 数据部分成功或状态不同步；
- 能力不兼容、版本过低；
- 资源不足：电量、存储、算力、带宽、温度；
- 用户取消、返回、切后台、重启；
- 恢复后是否续传、回滚、重试或从头开始。

异常规格使用结构：

```text
触发条件 → 阻止/继续什么 → 用户看到什么
→ 是否保留已有结果 → 如何恢复 → 是否记录日志/埋点
```

## 互斥与优先级

多个模式、输入或控制端冲突时写：

1. 哪些能力互斥；
2. 当前链路是否优先于新请求；
3. 系统拒绝、自动切换还是询问用户；
4. 提示文案；
5. 解除互斥的条件；
6. 多端状态如何同步；
7. 紧急停止和安全策略是否拥有最高优先级。

使用矩阵：

| 当前状态/模式 | 新请求 | 处理 | 提示 | 恢复条件 |
|---|---|---|---|---|

## 验收标准

好的验收标准：

- 可观察；
- 有明确条件；
- 覆盖主流程、边界和关键失败；
- 不依赖“看起来差不多”；
- 与用户结果或系统契约相连。

简单结果清单：

```text
- 完成条件：...
- 边界条件：...
- 失败条件：...
- 恢复条件：...
```

复杂交互：

```gherkin
Given 用户已连接支持该能力的设备
And 当前未处于升级状态
When 用户开启该功能
Then 设备在 2 秒内进入工作状态
And App 显示“已开启”
And 断开后重连仍显示设备真实状态
```

性能指标注明测试条件、样本、统计口径和分位数；例如不要只写“延迟低于 200ms”，还要说明端到端范围、网络条件和 P95/P99。

## 软硬件与 AI 特殊规则

### 硬件

- 参数写公差、环境条件和测量方法；
- 机械运动写范围、速度、精度、负载、噪声、寿命、安全限位；
- 接口写协议、方向、带宽、电气和兼容；
- 灯/声音写优先级，避免同时触发冲突；
- 断电、低电、过温、堵转、碰撞必须有安全行为。

### 软件

- 页面不等于需求；补入口、状态、操作、反馈和保存；
- 原型是视觉证据，不是完整规格；
- 按钮写可用/禁用条件、点击结果、防重复和加载态；
- 表单写校验时机、错误文案、焦点和数据保留；
- 删除、覆盖、恢复默认等危险动作写确认与撤销/恢复。

### AI

- 把“识别/理解/自动”拆成输入、输出、阈值和回退；
- 区分用户可控参数、系统策略和模型能力；
- 写目标丢失、多人/多物、遮挡、低光、快速运动等场景；
- 写人工接管后哪些自由度仍由 AI 控制；
- 指标按场景分层，避免只给整体平均值；
- 明确误判成本高的禁止行为和安全兜底。

## 常见坏写法

| 坏写法 | 问题 | 改写方向 |
|---|---|---|
| “界面简洁友好” | 不可验收 | 写目标任务、步骤上限、可用性测试标准 |
| “快速连接设备” | 无条件和阈值 | 写支持设备、网络条件、P95 时间、失败提示与重试 |
| “支持智能跟踪” | 能力边界不明 | 写目标类型、触发、丢失、重获、控制权、指标 |
| “范围 0–100” | 缺默认和步进 | 补单位、步进、默认、保存、边界行为 |
| “异常时提示用户” | 提示与恢复未知 | 写异常类型、文案、数据保留和恢复入口 |
| “同现有逻辑” | 引用不稳定 | 链接并摘出关键规则，写差异与版本 |
| “TBD” | 无关闭机制 | 补当前假设、决策人、日期、影响需求 |
| “见原型” | 原型不含全部规则 | 正文写行为契约，原型只做视觉参考 |
