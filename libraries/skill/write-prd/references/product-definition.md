## 定义的完成标准

产品定义不是“产品功能简介”。定义完成意味着团队可以一致回答：

- 谁会首先购买或使用；
- 哪个具体时刻触发需求；
- 用户现在如何完成任务，哪里付出高成本或得不到结果；
- 产品最先必须完成哪一个任务；
- 用户得到的结果是什么；
- 为什么这个形态和能力组合比替代方案更适合；
- 首版为了聚焦明确放弃什么；
- 如何知道方向成立或不成立。

## 八格定义画布

| 模块 | 必须回答 | 常见错误 |
|---|---|---|
| 目标用户 | 第一用户是谁；谁购买、谁使用、谁影响决策 | “大众用户”“内容创作者”等范围过大 |
| 触发场景 | 何时、何地、频率、上下文、约束 | 只列行业，不写具体任务 |
| 用户任务 | 用户真正想完成的进步或结果 | 把功能名当任务 |
| 现有替代 | 当前做法、成本、失败点、为何仍被使用 | 只说竞品“不智能” |
| 产品结果 | 用户一次使用后获得什么 | 只说设备能做什么 |
| 独特机制 | 哪组软硬件能力创造差异 | 把参数领先当完整价值 |
| 首版边界 | 核心、支撑、增强、后续、不做 | 把愿望清单全塞首版 |
| 成立证据 | 目标指标、验证方法、停止条件 | 只写“提升体验” |

## 第一句话与第一任务

使用结构：

```text
为【第一目标用户】在【高价值触发场景】提供一款【产品形态】，
通过【独特机制】让其完成【第一任务】，获得【可感知结果】。
```

测试一句话：

1. 是否不用项目代号也能理解；
2. 是否能明确排除至少一类用户或场景；
3. 是否能推出首版必须有的三项能力；
4. 是否能推出一段 30–90 秒的核心演示；
5. 是否包含结果，而非只包含功能。

第一任务是“没有它产品就没有购买理由”的任务。对复杂产品只选一个第一任务，其他任务标为支撑或扩展。

## 价值主线

建立单向链：

```text
用户时刻
→ 用户动作
→ 系统响应
→ 可见反馈
→ 最终结果
→ 下次继续使用的理由
```

再检查五类产品力：

- **购买力**：第一眼为什么愿意了解或购买；
- **频率力**：为什么平常也会使用；
- **结果力**：使用后留下什么可保存、复用或分享的结果；
- **信任力**：为什么敢用、敢依赖、出错后仍可恢复；
- **扩展力**：如何增加新玩法而不破坏基础体验。

首版核心功能应至少同时服务“第一任务”和上述两类产品力。

## 范围与版本

按五层收敛：

| 层级 | 判定 |
|---|---|
| 首版核心 | 缺失会使第一任务不成立 |
| 关键支撑 | 用户不一定为它购买，但决定核心是否可用 |
| 增强 | 提升覆盖或体验，缺失不破坏闭环 |
| 后续 | 有价值，但证据、技术或资源尚不足 |
| 不做 | 与定位冲突、负担过大或会把产品带向另一品类 |

“不做”要具体到用户、场景、模式、平台或性能承诺。不要写“暂不考虑其他需求”。

## 四类风险

每个产品方向都检查：

| 风险 | 核心问题 | 典型证据/验证 |
|---|---|---|
| 价值 | 用户会选择、使用或购买吗 | 用户任务、付费信号、替代行为、原型选择 |
| 易用性 | 目标用户能独立完成任务吗 | 可用性测试、任务成功率、学习时间、错误率 |
| 可行性 | 在时间、成本、技术与可靠性约束下能实现吗 | 样机、技术实验、供应链与成本核算 |
| 商业可持续性 | 渠道、品牌、法务、隐私、售后、盈利是否支持 | 商业评审、合规评审、服务成本和渠道验证 |

优先验证最可能推翻方向的风险。不要平均分配研究量。

## 产品定义评审

评审时依次问：

1. 问题是否真实且足够频繁/重要；
2. 第一目标用户是否具体；
3. 第一任务是否唯一；
4. 形态是否由场景和任务推出；
5. 核心功能是否组成闭环；
6. 与替代方案的差异是否可感知；
7. 首版边界是否能保护进度和质量；
8. 成功指标是否反映用户结果；
9. 最大风险是否有最低成本验证；
10. 哪个新证据会改变当前结论。

若答案主要依赖“未来 AI 会更强”“后续做生态”“用户应该会喜欢”，定义尚未冻结。
