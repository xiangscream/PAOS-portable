# 项目管理与进度同步

把零散的进度汇报变成**一份能及时反映进度的项目管理文档**，并产出对上级的同步内容。

## 核心判断：文档是仪表盘，不是日记

读者（上级/协作者）只关心四件事，60 秒内必须能看到：**到哪了、变了什么、有什么风险、需要谁做什么**。
因此文档分两处落点，**分工不能混**：

| 落点 | 性质 | 更新方式 |
|-|-|-|
| **项目快照**（文档顶部） | 当前态 | **改写**，每次覆盖成最新 |
| **进度记录**（按日期） | 历史轨迹 | **追加**，只加不改，形成趋势 |

## 输入通道

| 通道 | 形态 | 处理 |
|-|-|-|
| **语音 / 原始记录**（首选） | 技术人员顺口说、随手记，**无模板、无必填项、无格式要求**；也可由项目负责人把当天录音直接交来 | 本地转写（见 `references/local-asr.md`，**不用云转写**）→ 归属 → 抽取 → **主动补全** → 改写 |
| **单次汇报** | 技术人员按四段模板单独发来（他们自愿用模板时才用） | 走下面的整理流程 |

**采集端零负担（硬要求）**：
- **不给技术人员加任何业务流转**——不发模板、不列必填项、不要求格式。他们只负责"说清楚"。
- 解析、归属、补全、成文**全部由整理者承担**。
- **缺项回问项目负责人（PM/Human），不问技术人员**。
- 能推出来的自己补（分工表、上一版快照、历史记录），只把实在推不出的列成待确认清单。

**两条通则**：
- **原始记录与正式文档分离**——口语记录**不原文搬进正式文档**，只把事实、数字与结论整理进去；过程损耗（"白搞一上午"）转成可行动结论（版本不一致 → 需要统一基线）。
- 涉及个人评价、抱怨的内容不进正式文档。

## 三条铁律

1. **原文先留档**。收到汇报先原样落盘（`<项目>/进度收集/报进度-<姓名>-<日期>.md`），一字不改。文档里只放整理后的内容；有分歧以原文为准。
2. **缺项回问，不自己编**。**只有真卡点**才回问负责人与目标日期；问题项不追问。缺项问**项目负责人**，不问技术人员。宁可写「待定」，不替对方猜。
3. **整理完回告**。说明改了哪节、当前状态色、还缺哪些字段。

## 整理流程

1. **收**：读取汇报原文。若走原始记录池，按「日期 → 姓名」定位当天新增，**只读不改**；单次汇报则读取文件。用 `scripts/check_report.py <文件>` 做完整性预检（四段是否齐、必填项是否在），缺项先回问，不猜测补全。
2. **抽出结构化字段**：报的人 / 日期 / 对应节点表行 / 问题 / 解决方法 / 结果 / 下一步 / 负责人 / 目标日期 / 是否外部依赖。
3. **过基线对齐检查**（见下），这一步不可跳过。
4. **改写项目快照**：状态（绿/黄/红 + 一句话原因）→ 本旬进展（结果）→ 里程碑（计划 vs 实际）→ **卡点 / 问题项** → 需要支持 → 下一步。
5. **追加进度记录**：困难 / 解决过程与结果 / 阶段性成果 / 下一步（或卡点），注明日期。**不修改已有历史条目**。
6. **产出对上级的同步**（需要时）：日更短讯或周报。

## 写作规则（套用 `references/writing-rules.md`）

要点摘要，细则见该文件：

- **写结果不写活动**：「静态平衡维持 30 s，Pitch 波动 ±1.5°」而不是「做了静态平衡测试」。
- **正面描述**：删掉「不/不会/不改」式反面句，除非它本身构成独立产品/技术决策。
- **不写过程流水**：不记「先试了 A 失败，又试了 B」。
- **禁止自我削弱**：不用「遗憾的是 / 仅 / 效果有限」；**不替读者总结弱点**。
- **主动说清优势与收口**：能收口的写收口（「若确认源于胎皮不对称，量产可消除」），别让读者自己从表里推。
- **多级嵌套**：并列能力/机制按层级归拢（如 目标 / 构图 / 任务 / 模式），不要平铺成长句。
- **状态诚实标色**：有外部等待项就标黄，不标假绿；假绿在周五变红是最差实践。

## 跨人基线对齐检查（重点，必做）

技术问题里相当一部分不是能力问题，而是**两个人用了不同的基线**（编译版本不统一、零点标准不统一、接口字段不统一、参数口径不统一、术语不统一），结果还要额外花时间互相适配。

每收到一份汇报，逐条过 `references/alignment-checklist.md`：

- 编译 / 固件 / 工具链**版本是否同一基线**；
- 零点、标定、坐标系、单位**标准是否同一口径**；
- 接口字段、状态定义、错误码是否对齐；
- 参数默认值、量纲、有效范围是否一致；
- 术语与命名是否统一。

发现不一致：**单列成「基线对齐」条目**（谁与谁、差在哪、以哪个为准、谁负责统一），写进快照的卡点或需要支持一栏——**不要埋在正文里**。

## 进度把控

- 文档里的**节点表是计划视图**，快照是状态视图，进度记录是轨迹。三者对同一件事的表述不能互相矛盾。
- 每次整理时核对**计划 vs 实际**，偏差显性化（哪个节点延迟、延几天、影响什么）。
- 偏差触发：关键节点延迟 → 状态标黄；影响交付日期或需要上级决策 → 标红并写明要谁决定什么。
- **区分「卡点」与「问题项」——不要把每个问题都写成卡点**：
  - **卡点**（真挡路）：有明确 owner、有解决路径与时间 → 写 内容 + 影响 + 负责人 + 目标日期。
  - **问题项**（已知原因、短期不解决、属未来改进）：只写 现象 + 原因 + 为什么不在本版处理。**不指派负责人、不编目标日期**。
- **不要拿管理模板硬盖现实**：小团队（几个人）、早期阶段，职责本就交叉、日期本就没定。"卡点 + owner + 目标日期" 在这种团队里是负担不是帮助——大部分技术问题只是**正常推进中的问题项**，写清现象、原因与下一步就够。**只有真正挡路、且有明确承接人的才升级为卡点。**
- 外部依赖单列（等厂家 / 等采购 / 等他组），写清「等谁的什么、要谁去推动」。

## 对上级的输出（模板见 `assets/`）

- **群内日更**（`assets/日更同步模板.md`，内含 2026-10-20 已采用样例）：每天日会后在项目群发**一条**，8–12 行——**一句背景 / 今日 / 明日（按域）**。
  - **背景一句**：说明这件事在整体里的位置（本月目标、当前阶段），让不在细节里的人读得懂。
  - **技术实现由执行者确定，日更不写**：**规格参数可列**（峰值扭矩、最大电流、角度区间），**推导与实现不列**（系数换算、相/线电流、寄存器量程、代码接线）。
  - 文档留全技术细节给执行者；群消息只留背景与影响给其他人。
- **日会更新的顺序**：日会 → 汇总进文档对应日期章（追加，不改历史）→ 按模板出群消息 → 由项目负责人发送。**先文档、后群消息**，避免群里先承诺、文档没落地。
- **周报**（`assets/周状态报告模板.md`）：状态色 + 一句话 + 本旬结果 + 节点对照 + 卡点 / 问题项（只有卡点带 owner 与日期）+ 需要的决定 + 下周计划。

上级若问到「能不能在某日期前完成」这类**承诺性问题**：**不代答**。把问题与判断所需信息整理出来交负责人回答；文档只记录已确认的结论。

## 文档落点

飞书文档结构见 `references/pm-doc-structure.md`（快照放标题下、节点表其次、进度记录按日期追加）。用飞书 CLI 做**块级增量**操作，禁止整篇覆盖；改前回读 revision，改后回读校验。

## 边界

- 不代替技术人员下技术结论；不把汇报里的推测写成已确认事实。
- 不修改已发布的历史记录条目。
- 不虚构负责人、日期、数据；缺就写「待定」并回问。
