# 写作规则细则（进度/项目文档通用）

## 一、总原则：文档是发布会，不是工作汇报

1. **只围绕最强优势组织叙事**——能收口的先收口，把"已经做到什么"放在最前。
2. **不按"做了什么、试过什么、哪些失败了"的过程写**。
3. **禁止自我削弱**：不写「遗憾的是」「仅」「仍明显落后」「效果有限」；**不替读者总结弱点**。
4. **优势必须主动说清楚**，别指望读者自己从表格里发现。
5. **结论只强化记忆点**，不突然自我否定。
6. **杜绝一切防御性写作**。

## 二、逐条禁例与改法

| 禁例 | 为什么 | 改法 |
|-|-|-|
| 「不改变底盘横移」 | 是对正面句的反面重复，读者已知道改的是什么 | 直接删；正面句「左右手势调整画面构图」已足够 |
| 「不提高速度设定、不切换 N/M」 | 同上，把边界靠枚举反面表达 | 边界由正面定义给出：「只修改景别字段」 |
| 「不把陌生人的手势当作换人授权」 | 反面叙述 | 正面：「手势确认只对操作者生效」 |
| 「上一版方案因并发状态闭合不足，本轮不推荐；但不推出……不可行」 | 过程叙述 + 连续自我削弱 | 讲优势：「为什么用双信息位：录音事实与运行状态会同时存在，单光点同一时刻只能表达一件事，会互相覆盖」 |
| 「……均为待评审、待测试的候选，不是已实现能力，也不是实测阈值」（重复多次） | 同一句免责声明说三遍，三连否定 | 只保留一次、一句：「本节数值为设计目标，待样机验证。」 |
| 「该反馈不表示素材保存完成」 | "不表示"是防御腔 | 「标记确认表示已写入当前录像；保存进度在结果入口单独显示」 |
| 「做了静态平衡测试」 | 写活动不写结果 | 「静态平衡维持 30 s，Pitch 波动 ±1.5°」 |

## 三、判断标准

**一句话判据：删掉之后，读者的判断或下一步行动是否会改变？** 不会 → 删。

**负面句唯一可保留的条件**：它本身构成一个**独立决策**（例如「FPV 松手驻停、恢复跟随需显式执行『继续 Follow』」——这是在定义行为，不是在辩解）。

## 四、结构：多级嵌套

并列的能力/机制要按层级归拢，不要平铺成长句。
例：交互能力按 **目标 → 构图 → 任务 → 模式** 四层组织，每层说明各入口（手机/遥控器/手势/语音）分别承担什么；而不是把六个入口各写一段长句。

## 五、状态标色

| 色 | 含义 | 何时用 |
|-|-|-|
| 绿 | 按计划推进 | 无未决阻塞 |
| 黄 | 有风险，处理中 | 有关键节点延迟风险、有外部等待项 |
| 红 | 影响交付，需决策 | 时间/范围/质量受损，需上级介入 |

**诚实标黄，不标假绿**：一路绿到周五突然红，是最差实践——标黄是为了让别人有时间帮你。

## 六、自检清单（每次交付前过一遍）

- [ ] 开头一段是否直接给出最重要的结论/状态？
- [ ] 每条是否写的是**结果**而不是活动？
- [ ] 有没有「不/不会/不改」开头的子句？它是否构成独立决策？
- [ ] 有没有重复的免责声明？
- [ ] 每个问题是否被正确分类？卡点才要负责人与日期，问题项不硬派？
- [ ] 外部依赖是否单列？
- [ ] 有没有替读者总结弱点、或主动列举失败尝试？
- [ ] 状态色是否诚实？
