# 每日原始记录通道（语音日报池）

## 第一原则：采集端零负担

**技术人员只负责"说清楚"，不负责任何格式。**

- **不要模板**、**不要必填项**、**不要格式要求**。任何"请填写…""请带上…"的要求都不合格。
- 想到什么说什么：口头化、跳跃、夹杂跑题都可以。
- 说多少算多少；没说的，由整理者去补。

**解析、归属、补全、成文，全部由整理者承担。** 让业务流转占用技术人员精力，就是这套流程失败。

**缺项回问的对象是项目负责人（PM/Human），不是技术人员。**

## 输入形态（哪种都行）

| 形态 | 说明 |
|-|-|
| **语音录音**（最省事） | 整段发来即可；可含多人对话、可长可短 |
| 语音转文字 | 飞书语音输入等 |
| 文字随手记 | 打字也行，但不强求 |

## 处理流程（整理者做）

1. **转写**：用本地管线（`references/local-asr.md`，faster-whisper + OpenCC 繁转简 + 分块断点续跑）。**不用云转写、不上传音频**。
2. **切分与归属**：按说话人 + 内容线索归属到人。归属不确定的标「（待确认是谁）」，不要硬派。
3. **抽取**：问题 / 解决方法 / 结果 / 下一步 / 阻碍项与依赖（**区分卡点与问题项**：挡路且有承接人的才是卡点）。
4. **主动补全**（关键一步）：用已有材料推断，不要什么都问——
   - 节点表的分工与负责人；
   - 上一版项目快照、已追加的进度记录；
   - 已知角色表（控制侧 / 驱动侧 / 结构 / 电热 / 感知 / 外部厂家）。
   能推出来的，**自己补上并注明推断依据**，不进待确认清单。
5. **待确认清单**：只列"实在推不出来"的（通常是**目标日期**和**跨人基线以谁为准**），交项目负责人，不交技术人员。
6. **改写进正式文档**：改写项目快照（当前态）+ 追加阶段性进度记录（历史）。
7. **回告**：改了哪几节、当前状态色、待确认清单。

## 口语 → 正式文档的改写示例

| 口语原始记录 | 整理后 |
|-|-|
| 「今天调了半天那个零点，后来发现是对面版本不对，白搞一上午」 | **基线对齐**：与对方固件版本不一致，导致零位复验失败；以 XX 版本为准；责任人 / 日期待定 |
| 「换了新轮胎以后振动小多了，低速还是有点抖，但站得住」 | **轮胎振动问题已解决**：更换优化件后整车振动大幅减轻；残余高频振动低速可见，低速稳定性不受影响 |
| 「翻车那个找到了，是没对齐，一直往后退」 | 昨日失稳根因定位为**驱动与控制未对齐**：设备误判腿部未完全抬起、持续后退维持平衡导致失稳；修复路径明确 |

**改写原则**：保留事实与数字，去掉语气、过程与抱怨；把「白搞一上午」这类**过程损耗**转成**可行动结论**（版本不一致 → 需要统一基线）。

## 分不清归属时的处理

- 转写里某人说的内容与他职责明显不符 → 标「（待确认）」，在回告里点出来。
- 同一件事多人提到且说法不一致 → **两种说法都保留**，标「口径不一致，需确认以哪份为准」——这往往正是基线问题的来源。
- 听不出数字或型号 → 不要猜，标「（转写不确定，待核对）」。

## 边界

- 口语不原文进正式文档。
- 推测一律标注「待确认」。
- 个人评价、抱怨不进正式文档；只留事实、结论、行动项。
- 转写可能出错：**关键数字、型号、版本号要回读核对**，必要时回听原音。
- 原音与转写稿留档，不改原文，便于追溯。
