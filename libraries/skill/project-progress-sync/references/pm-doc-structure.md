# 项目管理文档的结构与落点

## 一、整篇结构（自上而下）

```
标题
└─ 项目快照（高亮框 📌）        ← 当前态，每次改写
   ├─ 状态：绿/黄/红 + 一句话原因
   ├─ 本旬进展（3–5 条，全部是结果）
   ├─ 里程碑（计划 vs 实际）
   ├─ 卡点 / 问题项（卡点才带负责人与目标日期）
   ├─ 需要支持（要谁、做什么、什么时候）
   └─ 下一步（3–4 条）
一、节点表（计划视图，表格）      ← 任务清单，含勾选项与截止日期
二、配置（样机/环境）
三、实验内容（每节：目的 + 方法 + 验收 + 负责人）
四、阶段性进度（按日期追加）      ← 历史轨迹，只加不改
   └─ 每章：目的（上）+ 进度（下：遇到的困难 / 解决过程与结果 / 阶段性成果 / 下一步）
五、改进方向 / 后续方向 / 配套 …
相关文件
```

**关键分工**：快照＝当前态；节点表＝计划；进度记录＝历史。三者对同一件事的表述必须一致，不能互相矛盾。

## 二、项目快照的写法

- 用**高亮框（callout）**放在标题之下——不占章节编号，避免每次插入都重排章节号。
- 状态色判断：有关键节点延迟风险或有外部等待项 → 黄；影响交付且需上级决策 → 红；否则绿。
- 「本旬进展」只写**结果**，每条一行，不超过 5 条。
- 「卡点」每条带 内容 + 影响 + 负责人 + 目标日期；**「问题项」只写现象 + 原因 + 为何不在本版处理**。小团队、早期阶段大多数是问题项，不要硬升级为卡点。外部依赖单独标注。
- 「需要支持」不能长期写"无"——若连续几期都无，说明报告只是形式，或团队不敢提问题。

## 三、阶段性进度（历史）的写法

- **按日期独立成章**（如「四、阶段性进度：动力与结构（10-16）」），不塞进已有小节当"补充"。
- 章内固定结构：**目的（上）→ 遇到的困难 → 解决过程与结果 → 阶段性成果 → 下一步 / 卡点（下）**。
- **只追加，不修改历史条目**——这样才看得出趋势（哪些问题反复出现、哪些是新增的）。
- 阶段名加日期范围（如 "10-16 前"），便于对照。

## 四、飞书落点与操作

- 用飞书 CLI 的**块级增量**命令（`block_insert_after` / `block_replace` / `block_delete` / `block_move_after`），**禁止整篇 overwrite**。
- **改前回读 revision**（云端可能正被别人编辑），**改后回读校验**（比对关键字段）。
- **文档内导航**：交给**侧边目录**（H1–H3 自动生成，原地跳转）或**目录导航小组件**。
  **不要**在文档内用 `文档URL#block_id` 做目录式跳转——那会打开新页；该形式只适合跨文档引用或发到聊天。
- 表格改写（`block_replace` 整表）时注意保留：列宽、rowspan 合并、`<checkbox done>` 勾选状态。
- 代码块、画板等复杂块的插入方式见对应文档技能的规范文件。

## 五、留档

原始汇报存 `<项目>/进度收集/报进度-<姓名>-<日期>.md`，一字不改。文档里只放整理后的内容。
