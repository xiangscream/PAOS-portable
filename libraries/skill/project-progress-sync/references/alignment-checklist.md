# 跨人基线对齐检查清单

## 为什么必须做

技术问题里相当一部分不是能力问题，而是**两个人用了不同的基线**：编译版本不统一、零点标准不统一、接口字段不统一、参数口径不统一、术语不统一——结果双方都无法直接使用对方的产物，只能额外花时间互相适配。**这类问题重复出现率高、且完全可以在整理汇报时就发现。**

## 每次整理汇报时逐条核对

### 1. 构建与运行基线（编译类问题高发区）

- [ ] **固件/程序版本号**是否一致？各自基于哪个 commit / 哪个编译产物？
- [ ] **编译器与工具链**是否同一版本？（ARMCC / GCC / Keil / IAR；SDK 版本）
- [ ] **编译配置**是否一致？（优化等级、宏开关、目标板配置）
- [ ] 交付给对方的**是源码还是二进制**？二进制则必须带版本标识。

### 2. 标定与零点基线（控制类问题高发区）

- [ ] **零点定义**是否一致？（机械零位 / 电零位 / 上电自动标定）
- [ ] **上电后的初始化流程**是否一致？（是否需要手动设零、是否保存到 flash）
- [ ] **标定参数来源**是否一致？（各自标 vs 共用一份标定文件）
- [ ] **坐标系与正方向约定**是否一致？（右手系/左手系、正俯仰方向）

### 3. 接口与协议

- [ ] 字段名、数据类型、字节序、单位是否一致？
- [ ] 状态机与错误码定义是否共用同一份表？
- [ ] 谁负责维护接口定义，改动怎么同步？

### 4. 参数与量纲

- [ ] 默认值、量纲（rad/deg、m/mm、Nm/mNm）、有效范围是否一致？
- [ ] 限幅、死区、滤波参数是否共用同一份配置？

### 5. 术语与命名

- [ ] 同一件事是否被两个人叫了不同名字（模式名、状态名、部件名）？
- [ ] 文档里的术语是否与代码/硬件命名对应？

## 发现不一致时的写法

单列成 **「基线对齐」** 条目，写清四件事：

| 项 | 例 |
|-|-|
| **谁与谁** | 浩翔（控制侧）↔ 梁进（驱动侧） |
| **差在哪** | 编译版本不统一 / 零点标准不统一 |
| **以哪个为准** | 以 XX 为准（未定则写"待定"） |
| **谁负责统一** | 负责人 + 目标日期 |

放进**项目快照的「问题项 / 卡点」或「需要支持」**一栏——**不要埋在正文里**。这类条目往往是"进度低效"的真正来源，显性化之后才可能被消除。
