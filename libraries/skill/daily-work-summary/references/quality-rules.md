# Quality and evidence rules

## 1. Evidence levels

Use the user's existing evidence taxonomy when available. Otherwise use:

- **strong**: primary source, official specification, direct observation, reproducible test, or reviewed internal fact;
- **medium**: multiple credible secondary sources or consistent user evidence;
- **weak**: small samples, promotional material, desk inference, unverified agent synthesis, or a single anecdote;
- **unknown**: claim exists but evidence is missing or conflicting.

Framework completion is not product validation.

## 2. Completion status

Use precise status language:

- **not started**: no meaningful work performed;
- **in progress**: material exists but completion criteria are not met;
- **working draft complete**: the planned draft exists but is not reviewed or accepted;
- **reviewed**: an independent review occurred and required changes are known;
- **accepted baseline**: the team can use it as the current working truth;
- **formal deliverable complete**: completion criteria, review, and intended use are all satisfied.

Do not use “100% complete” when a second review or formal admission is still required. Say “learning draft closed; formal admission pending.”

## 3. Activity versus result

Activity examples:
- watched videos;
- created files;
- ran agents;
- collected links.

Result examples:
- narrowed the product hypothesis;
- rejected an invalid exclusion rule;
- corrected a technical misconception;
- established a reusable evidence structure;
- identified the next decision-critical unknown.

Lead with results. Keep activity as supporting detail.

## 4. Contradictions

When inputs conflict:
1. identify whether they describe different layers;
2. preserve both when compatible;
3. state the unresolved conflict when incompatible;
4. avoid inventing a reconciliation.

Examples:
- “five-stage workflow” and “six decision questions” can both be true;
- “knowledge line closed” and “fourteen cards need second revision” require a scoped status: learning baseline closed, formal library pending.

## 5. Next-task quality

A good next task includes:
- one decision question;
- one named output;
- measurable completion criteria;
- a time boundary;
- explicit non-goals.

Reject vague next steps such as “continue research,” “improve framework,” or “learn more.”
