# 软件业务流程梳理

把软件从页面、字段和接口的集合，还原成一份可执行的业务合同：用户从哪里开始，系统依据什么规则改变什么，失败后如何恢复，最终怎样证明成功。

默认先分析，不进入实现。未经授权，不修改代码、真实数据、进程或外部系统。

## 核心原则

1. 从用户目标开始，不从按钮或路由开始。
2. 先找唯一第一主路径，再展开必要的次要路径。
3. 状态是一份合同，不只是枚举值；来源、mode、权限和显示标签不得冒充状态。
4. 先还原现状，再设计目标；事实、推断、建议和待决策分开。
5. 异常只深入三类：真实发生、阻断第一主路径、可能静默损坏状态。
6. 每个可见选项都必须改变可观察行为；否则给出保留、隐藏、删除、补齐或暂缓的处置。
7. 保持个人项目尺度，不擅自加入组织、审批、多租户或安全仪式。
8. 输出以帮助决策为准，不为填满模板而补表、补状态或补接口。

## 选择分析深度

### 快速梳理

用于单一按钮、单一流程或明确的“为什么走不通”。优先使用 `templates/focused-analysis.md`，通常只保留：结论、当前流程、关键规则、恢复、验收、边界。

若一个实现缺陷在单一文件内即可直接确认，不启用本 Skill，按普通诊断处理。

### 专题梳理

用于一个生命周期、一个状态机、一组相关接口或一个功能域。按证据增加状态×事件、UI—业务—API—数据追踪和选项处置。

### 全面梳理

用于“整体业务逻辑、完整用户流程、全面收敛”。使用 `templates/full-analysis.md`，但核心正文只保留会改变产品决策的内容；完整路由、证据矩阵、错误清单放按需附录。

默认只交付一份核心文档。只有业务域确实独立或用户明确要求时才拆成多篇。

## 按需读取资料

- 建模前读取 `references/modeling-guide.md`。
- 涉及 UI、接口、路由、数据写入或外部手工交接时读取 `references/interface-and-traceability.md`。
- 交付前读取 `references/quality-gates.md`，只执行适用门槛。

不要把参考资料原样搬进输出。

## 工作流

### 1. 锁定目的、范围和第一主路径

写清：

- 用户最常见、最有价值的目标是什么；
- 流程从哪里开始、以什么结果结束；
- 本轮包含与不包含什么；
- 输出用于理解、诊断、决策还是实现前验收。

若有多个目标，先指定一条第一主路径。其他路径只有在影响它、真实高频或用户明确要求时展开。

### 2. 建立可复现基线

已有系统至少核对：

- 源码版本、分支和未提交改动；
- 正在运行的服务是否加载同一版本；无法确认时明确写出；
- 持久化数据的时间与 schema；
- 现有文档和测试对应哪个版本；
- 用户真实使用记录或摩擦是否与代码结论一致。

不要把“仓库代码”“正在运行的服务”和“真实数据状态”混成一个现状。

### 3. 建立证据与冲突清单

按结论选择最接近行为的证据：

- 运行状态/真实数据：实际发生过什么；
- 业务守卫与写入代码：允许、拒绝和改变什么；
- 测试：哪些合同被明确保护；
- schema/API：合法形状；
- 渲染后的 UI：用户实际看见和能触发什么；
- 配置、文档、注释：声明和意图。

标记为：**事实、推断、待决策**。来源冲突时并列报告，不挑选最顺眼的一方。

#### 负面结论规则

声称“没有调用方、未实现、纯声明、从未使用”前，至少检查：

1. 字段名和直接引用；
2. 业务同义词及别名；
3. 硬编码集合、条件守卫和重复策略；
4. 相关测试与真实数据。

仍未找到时，写“在已检查范围内未发现”，并说明范围。不得把一次文本搜索当成不存在的证明。

### 4. 建立业务词典与对象关系

给核心概念写互不重叠的一句话定义，并说明：唯一身份、生命周期或分类、与谁关联、当前事实还是历史证据。

特别区分：对象与视图、status 与来源、mode 与 status、Identity 与 capability、UI action 与业务动作、API route 与用户旅程、当前事实与历史证据。

### 5. 还原第一主路径

按 Job-to-be-done 描述：

1. 触发和前置条件；
2. 用户或真实外部参与者动作；
3. 系统判断；
4. 对象和状态变化；
5. 用户可见反馈；
6. 下一动作；
7. 失败恢复。

手动复制 Prompt、切换到外部 Agent、回贴结果等系统边界动作必须进入流程，不能因不在本系统内就省略。

### 6. 建立必要的状态与追踪模型

只有真实生命周期对象才画状态机。对每个状态核对来源、事件、守卫、写入、后态、反馈和恢复。

涉及实现时追踪：

```text
用户目标 → UI/调用方 → 业务动作 → API/命令
→ 守卫 → 数据变化 → 成功反馈 → 错误恢复
```

先追踪第一主路径。完整 API/路由表只有在定位跨层断点或准备实现时才生成。

### 7. 验真选项并给出处置

对每个用户可见选项回答：改变什么数据和流程、允许或禁止什么、用户能观察到什么差异、选错后如何恢复、真实使用证据是什么。

最后必须给出处置之一：**保留并解释、保留但隐藏、删除、补齐合同、暂缓等待真实使用**。

### 8. 分离现状、目标和方案

至少分清当前事实、用户影响与根因、未来必须满足的目标合同、可选方案及取舍、会改变方向的待决策问题。

优先设计语义动作，不让用户直接修改内部状态来绕过不变量。

### 9. 写最小验收合同

证明用户能走完，而不只是接口返回成功。优先覆盖第一主路径、真实发生的断路、状态损坏或静默覆盖、核心公共合同易复发的部分。

文案、布局和理论边界默认人工验收，不自动扩成大量阻塞测试。

### 10. 收口并停止

满足以下条件即停止继续扩展：

- 能一句话说明第一主路径的起点、规则、结果和恢复；
- 关键对象与状态没有未解释的概念冲突；
- 关键结论有证据或明确标为待决策；
- 选项有明确处置，而不只是问题清单；
- 验收足以判断下一版是否闭环。

不要因为还能找到更多接口、字段或理论异常而继续分析。

## 输出规则

默认顺序：

1. 一句话结论；
2. 基线与关键证据冲突；
3. 第一主路径；
4. 对象与状态；
5. 断路、恢复和选项处置；
6. 目标合同与待决策；
7. 最小验收；
8. 本轮边界。

写作要求：

- 先用用户语言，再保留必要技术标识；
- 表格用于比较，流程图用于顺序，状态图用于生命周期；
- 核心正文不重复同一合同，详细证据和接口移至附录；
- 大型项目先给一个可独立阅读的核心结论，不默认拆成多篇；
- 用户未要求落盘时直接在对话中交付，要求落盘时优先 Markdown；
- 不把候选方案写成已实现能力。

## 不适用场景

- 单一函数、单一报错或单文件缺陷可直接定位；
- 已确认设计后的纯编码；
- 单纯 API/SDK 语法；
- 项目排期、审批链、会议与组织职责；
- 纯视觉设计；
- 与软件无关的生活流程。

若任务同时要求梳理和实现，先交付业务合同并获得确认，再进入实现。
