# 软件业务流程梳理质量门槛

交付前先过必检项。专项项只在对应问题存在时使用；不为了“完整”机械填表。

## A. 必检项

- [ ] 明确源码、运行实例、数据三个基线；没有把文档或旧进程当现状。
- [ ] 用一句话说清用户目标、第一主路径起点和成功终点。
- [ ] 第一主路径包含必要的人机交接，不把复制、外部 Agent 或回写藏起来。
- [ ] 关键对象有不重叠定义，当前事实、历史证据与派生投影已区分。
- [ ] 每个非终态都有合法下一步；成功后能看见结果和下一动作。
- [ ] 只分析真实发生、阻断主路径或会损坏状态的异常，并给出恢复动作。
- [ ] UI、业务规则、接口与数据结果在关键路径上能互相对上。
- [ ] 用户可见选项已有处置：保留并解释、隐藏、删除、实现或延后验证。
- [ ] “未使用/未实现/无守卫”等负面结论完成了语义别名、硬编码守卫、测试和数据检查。
- [ ] 事实、推断、建议、待确认分开；关键事实有最小必要证据。
- [ ] 目标方案优先修通主路径，没有顺手引入企业权限、组织流程或未来抽象。
- [ ] 验收证明用户能完成目标，不只证明页面存在或接口返回 200。

## B. 按需专项

### 生命周期

- [ ] 只有真实生命周期对象才画状态机。
- [ ] 状态来源、事件、守卫、写入、副作用和恢复足够明确。
- [ ] 迁移态、历史态或异常态没有被误当日常入口。

### 接口与写入

- [ ] 运行版本与被审查代码一致。
- [ ] 写接口说明幂等、冲突、失败不变量和历史证据处理。
- [ ] 人工/外部 Agent 交接说明输入、回写和过期处理。

### 选项与模式

- [ ] 每个选项能指出可观察的行为差异。
- [ ] 真实数据中为零使用的选项被标为待验证假设，而不是自动当资产或死代码。
- [ ] 多入口没有把同一能力包装成多套业务语义。

### 迁移与恢复

- [ ] 当前事实可恢复，历史证据不会因兼容清理被静默丢弃。
- [ ] 失败不会留下半写状态；必要时说明备份与回退。

## C. 收口问题

交付前必须能自然回答：

> 用户从哪里开始，沿哪一条主路径完成目标；系统依据什么规则改变哪些事实；出错后从哪里恢复；成功后如何看见结果并继续？

如果答不出来，继续补主路径；如果已经答得出来，就停止扩表和扩异常。
