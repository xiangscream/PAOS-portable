## 1. 基线与证据

### 1.1 三个“现状”必须分开

| 层次 | 要确认什么 | 常见误判 |
|---|---|---|
| 源码现状 | commit、分支、工作区、配置 | 把未运行的新代码当成产品现状 |
| 运行现状 | 进程启动时间、加载版本、实际页面/API | 服务仍运行旧代码却按新代码下结论 |
| 数据现状 | schema、时间、真实对象与使用次数 | 把测试数据或迁移数据当成真实使用 |

无法核对运行版本时，明确写“运行版本未确认”，不要默认为源码版本。

### 1.2 证据能证明什么

| 来源 | 能证明 | 不能单独证明 |
|---|---|---|
| 真实数据/运行结果 | 实际出现过什么 | 是否符合设计意图 |
| 业务守卫与写入代码 | 允许、拒绝和改变什么 | 用户能否发现入口 |
| 测试 | 哪些合同被保护 | 未覆盖路径正确 |
| schema/API | 合法输入输出 | 调用后一定成功 |
| 渲染后的 UI | 用户实际看到和能触发什么 | 后端兑现承诺 |
| 配置 | 声明了哪些选项 | 选项真正生效 |
| 文档/注释 | 设计意图 | 当前仍一致 |

使用三类标记：**事实、推断、待决策**。来源冲突时，先写冲突，再决定哪一来源回答哪类问题。

### 1.3 负面结论证明协议

“没有、未实现、无调用方、从未使用”比“存在”更难证明。下结论前执行四向检查：

1. 搜索字段名、函数名和直接引用；
2. 搜索业务同义词、别名和旧名称；
3. 检查硬编码 allowlist/denylist、条件守卫和重复策略；
4. 检查测试、真实数据、日志或使用记录。

示例：配置字段 `can_create_x` 没有调用方，不代表能力未执行；业务层可能使用 `CREATION_IDENTITIES` 硬编码同一规则。正确结论可能是“配置与执行规则重复且入口不一致”，而不是“没有权限控制”。

若仍找不到，使用限定句：

> 在已检查的 UI、Service、Store、测试和真实数据范围内未发现……

### 1.4 文档新旧对照

已有分析文档不能自动成为证据。至少列：

- 仍成立；
- 已被后续实现修复；
- 与当前代码冲突；
- 超出本次范围；
- 仍待真实使用验证。

## 2. 第一主路径

### 2.1 先选一条主路径

第一主路径应同时满足：高频、价值最高、代表系统核心承诺。不要把所有旅程并列成同等重要。

Job-to-be-done 可写成：

```text
当 [情境] 时，我想 [完成目标]，从而 [得到价值]。
```

避免用按钮、HTTP 方法或内部字段表达目标。

### 2.2 旅程字段

| 字段 | 问题 |
|---|---|
| 起点/触发 | 用户为什么现在开始？ |
| 前置条件 | 开始前必须成立什么？ |
| 用户/外部参与者动作 | 谁做什么？ |
| 系统判断 | 检查哪些业务规则？ |
| 数据/状态变化 | 什么被创建、更新或追加？ |
| 可见反馈 | 用户怎样知道结果？ |
| 下一动作 | 成功后去哪里？ |
| 恢复 | 失败、取消或改变主意怎么办？ |

手动复制 Prompt、切换应用、把 Agent 输出回贴等边界动作也是流程步骤。它们不在系统进程内，但决定用户能否闭环。

### 2.3 次要路径进入条件

只有满足之一才展开：

- 阻断或改变第一主路径；
- 真实数据中高频出现；
- 会损坏状态或历史证据；
- 用户明确要求；
- 是可见选项承诺的必要差异。

## 3. 业务词典与对象关系

每个核心对象写：

```text
名称 / 唯一身份 / 一句话职责 / 生命周期或分类 / 关系 / 数据语义
```

重点区分：

- 对象 vs 页面卡片/投影；
- status vs 来源、归档或可见性；
- mode vs status；
- Identity/工作模板 vs capability；
- 当前事实 vs 历史证据；
- 本系统对象 vs 外部系统原生对象。

如果两个概念不能写出互不重叠的一句话定义，把它列为模型缺口。

## 4. 状态合同

一个字段只有同时具备状态集合、产生事件、前态守卫、后态、非法转换、终态和关联字段约束时，才算状态机。仅校验枚举可能只是标签。

### 状态×事件矩阵

| 当前状态 | 事件 | 触发者 | 守卫 | 写入 | 后态 | 用户反馈 | 恢复 |
|---|---|---|---|---|---|---|---|

优先寻找：

- 无入边状态；
- 非终态无出边；
- 任意跳转；
- 状态与关联字段矛盾；
- 同一概念在不同入口使用不同守卫；
- 来源/迁移被塞进生命周期；
- 终态被直接改活却无语义动作。

从历史或终态继续工作，通常优先创建新对象并保存 `continued_from` 等关系，而不是静默改写旧证据。

## 5. 异常与恢复

只深入：

1. 已真实发生；
2. 阻断第一主路径；
3. 可能静默覆盖、损坏或丢失状态。

其他理论异常记录为边界，不自动扩成设计任务。

恢复至少回答：用户还能做什么、输入是否保留、数据是否变化、能否安全重试、旧记录是否保留、替代入口在哪里。

错误文案优先表达：

```text
发生了什么 + 为什么 + 哪些内容没改变 + 下一步
```

## 6. 业务规则与不变量

业务规则写成可验证句子：

```text
当 [前置] 执行 [事件]，系统必须/不得 [行为]；
成功后 [状态/数据] 为 [结果]；失败时 [恢复]。
```

常见不变量：引用存在、终态字段成组存在、重试不重复、旧版本不覆盖、历史证据不静默改写、窄写不越界、一次动作全部成功或全部不提交。

不变量应放在所有入口都绕不过的业务/存储边界，不只写在页面逻辑里。

## 7. 选项验真与处置

| 选项 | 声称含义 | 真实改变 | 可观察差异 | 使用证据 | 冲突/恢复 | 处置 |
|---|---|---|---|---|---|---|

判断可以是：真实生效、部分生效、合同冲突、纯声明、错误建模。

处置必须是：

- 保留并解释；
- 保留但隐藏；
- 删除；
- 补齐合同；
- 暂缓等待真实使用。

真实使用为零不自动等于删除，但必须说明保留该选项对第一主路径的必要性；否则优先隐藏而非继续增加认知成本。

## 8. 现状、目标与方案

| 层次 | 内容 |
|---|---|
| 当前事实 | 今天实际如何运行 |
| 问题 | 用户影响与业务根因 |
| 目标合同 | 未来必须满足什么 |
| 候选方案 | 可以怎样实现及取舍 |
| 待决策 | 哪个选择会改变合同 |

目标合同不提前锁死字段名、框架或数据库。业务语义尚未稳定时，不用技术迁移代替产品决策。

## 9. 图表选择

- 线性步骤少：普通步骤表；
- 用户旅程和恢复分支：Mermaid `flowchart`；
- 单对象生命周期：`stateDiagram-v2`；
- 多系统调用时序：sequence diagram，仅在同步/异步差异重要时使用。

图只用于让关系更清楚。图中的状态、动作和分支必须能在正文或矩阵中找到；不要用一张大图同时表达旅程、状态、接口和数据。
