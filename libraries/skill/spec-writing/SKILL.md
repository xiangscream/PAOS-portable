# 规格写作（spec writing）

面向研发的文本分两种：**规格**（规定系统行为）和**说明**（关于系统的陈述）。
规格缺失会导致研发做错；说明缺失什么都不影响。混在一起读起来就像「防御性/审计性」。

## 一、核心判据

> **一句话如果删掉后，研发的行为不变、用户看到的东西也不变，它就是说明，不是规格。**

自检动作：逐句问「删了会怎样」。
- 研发会做错、测试会漏测 → 规格，保留。
- 什么都不变 → 说明，删。

这条判据比「禁止不是/而是」更深一层。只清对偶否定会漏掉大量同类问题——因为很多说明句根本不含否定词。

## 二、六种典型病灶

### 1. 实现手段（最隐蔽）
规定了研发本来就有自由怎么做的事。

- 病灶：「景别由主体距离、机身高度、云台朝向共同实现。」
- 判定：这是研发的设计自由，PRD 不该规定；对营销/设计是噪音。
- 改法：**删**。除非它同时是一个对外承诺（如「不裁切实现」）。
- 同类词：由…实现 / 内部由… / 通过…完成

### 2. 替用户辩解
解释用户「不需要懂」什么，实际什么都没规定。

- 病灶：「用户以实际预览选择画面，不必先理解米数和角度。」
- 改法：删后半句，留「用户看预览选景别」。
- 同类词：不必先 / 不需要先 / 无需了解 / 用户不用知道

### 3. 防误读声明
给一个本来不存在的误解打补丁。

- 病灶：「两者分开，避免把「抬高视角」混成单纯仰起镜头。」
- 改法：直接写正向分工：「拍摄高度调整相机位置，主体画面位置调整构图。」删掉「两者分开」「避免…」。
- 同类词：避免 / 两者分开 / 不要混淆 / 以免 / 防止误解

### 4. 能力免责式
把限制当成需要声明的免责，而不是当成事实说清楚。

- 病灶：「Close 受到近场运动距离和清晰范围约束。」
- 改法：写成事实：「Close 的最近可用距离取决于机器人能安全接近到多近。」
- 同类词：受到…约束 / 受限于 / 存在…限制

### 5. 条件-兜底句式
「需要 X 时…；不足时…」读起来像在打补丁。**注意误报**：若它规定的是「触发→系统动作」，那是规格。

- 病灶：「需要比机器人可安全接近的位置更大的主体画面时，系统优先利用可用构图余量；不足时告诉用户，保留可执行距离。」
- 判定：一句里塞了两个兜底分支，且与异常处理章节重复。
- 改法：把限制并入讲该能力的那句，删掉分支。
- 误报样例（保留）：「身份冲突时，提示用户确认目标或结束」——这是真实的行为规定。

### 6. 设计意图声明
讲「我们希望它表现得像什么」，属论证不属合同。

- 病灶：「异常应表现为能理解、能处理的任务状态，机器人不应无提示地停在远处。」
- 改法：删。前面的具体行为（提示什么、何时停）已经说清了。

## 三、必须保留的「否定句」

否定句不能一刀切。以下是规格，必须留：

| 类型 | 例子 |
|---|---|
| 禁止条款 | 「不能自动选择一个看起来差不多的人继续跟」「不能在松手后出现突然加速」 |
| 状态不变式 | 「Mark 不改变 Follow 状态，也不改变 Recording 状态」 |
| 边界定义 | 「不出现跳变」「不返回原来的地面坐标」 |
| 参数范围 | 「距离不超过 6 m」 |

判定：这句否定是否规定了系统**必须不做**某件事？是 → 留。

## 四、修订工作流

1. **先跑扫描脚本**找候选，别凭感觉（实测脚本比肉眼多找 8 处）。
2. **逐条判定**：真病灶改，误报（本身是规格）保留，并记下误报原因。
3. **改法是重写不是打补丁**：受影响的整句/整段重写，不追加「（修正）」。
4. **复扫**：候选应从 N 降到只有误报。
5. **量化净效果**：报字数变化，证明信息没丢。
6. **★ 检查载体**：清完再问一遍「每段该用什么形式」（见第五节）。清说明性文字**不等于**全改成表——这是两个独立动作，混起来会做出配置清单。

扫描脚本见 `scripts/spec_scan.py`。

## 五、载体选择：散文、列表还是表格

**★ 这是最容易做错的一步。** 把「无歧义」直接推成「全部转表」，会得到一份读起来像配置清单的文档——精确，但没人愿意读。读者读不下去的规格等于不存在。

**判据：看信息是否需要「多维度对照」，不看你多想把它说准。**

| 信息类型 | 载体 | 例子 |
|---|---|---|
| 多维对照（同一对象要并排比几个属性） | **表** | 状态一览（状态 / 含义 / 控制权 / 进入条件）；关系表（关系 / 画面 / 设备做什么） |
| 流水线步骤、一条条并列的规则 | **编号列表** | 功能需求清单 |
| 因果、时序、权衡、为什么这样设计 | **散文** | 为什么「正在建立」和「已经跟上」要区分开；松手后从当前位置恢复意味着什么 |

**反例（我犯过的）**：把「进入与建立 / 恢复与结束 / 用户心智」都做成表。这些本是**时序与因果**，硬塞进表里就变成一行行孤立的条件，读者看不到它们之间的关系。正确做法是用散文按因果串起来讲，只在真需要对照的地方落表。

**检验**：如果这张表只有两列、或者每行之间没有对照关系、或者必须连着读才有意义——那它应该是散文或列表。

**状态机的正确写法**：状态**一览**用表（状态 / 含义 / 控制权归属），但**状态之间的转移和恢复路径用散文讲**，因为转移是有方向、有条件的因果链。纯表会把「为什么松手后是回到当前位置而不是原地」这类关键语义压掉。

| 句式 | 用法 | 例子 |
|---|---|---|
| 触发式 | 事件发生 → 系统做什么 | 按下 Follow 键时，用上次的关系与景别开始 |
| 状态式 | 处于某状态时，系统做什么 | Follow 运行中，Mark 不改变 Follow 状态 |
| 禁止式 | 系统不得做什么 | 无法确认原目标时，不得自动选择新目标 |
| 数值式 | 带数字或可判定的阈值 | 最近可用距离取决于能安全接近到多近 |

## 五之二、让文档「漂亮」的其他要件

调研业界好 PRD（Linear / Webflow 公开样本、Lenny Rachitsky 模板、ISO 29148 要求）后归纳：

1. **读者 30 秒能抓到重点**——开头就是结论，不是铺垫。
2. **形式由读者决定，不由产品大小决定**——给研发看的要完整可验证，给营销看的要能读懂。
3. **一条需求一行，可验证，不含「和」**（ISO 29148：可验证、无歧义、单一）。
4. **表格是对照工具，不是正文骨架**。表格前要有引入句说明它在回答什么，表格后要有解释——「Tables summarize decisions. They should not replace the reasoning behind them.」
5. **不要用表去替代「为什么」**。理由是散文的活。

## 五之三、★ 层次必须用 Markdown 语法凸出来（2026-09-30 用户明确要求）

**用户原话：「呈现方式弱，多用 MarkDown 语法多级嵌套来凸出层次吧（记住）」**

只写成一坨段落，即使内容对，读者也看不出结构。**层次不能靠读者自己从段落里读出来，要用语法顶出来。**

可用手段从强到弱：

| 手段 | 用途 | 写法 |
|---|---|---|
| **标题层级** | 章节骨架 | `##` / `###` / `####`，一层只放同类内容 |
| **无序列表 + 缩进** | 并列项、分组下的细化项 | `-` 主项，`  -` 子项（**缩进两格**） |
| **有序列表** | 有先后的步骤、优先级 | `1.` `2.` `3.`（固件流程、操作顺序） |
| **加粗** | 关键判断、状态名、规则名（**每段最多一处**） | `**正在建立**` 与 `**已经跟上**` 是两件事 |
| **行内代码** | 状态枚举、参数名、专有名词 | `Auto Follow`、`Re-establishing` |
| **引用块** | 用户能记住的原则、一句话总结 | `> 我要它继续替我拍——保持默认，它继续跟` |
| **分隔线** | 大段落之间的区隔 | `---`（慎用，层级已清楚就不用） |

**怎么用对**（判断依据是「这段里有几类东西」）：

- 一段里讲了**三个并列的做法** → 拆成三个 `-` 项，不要揉成一句话。
- 一个做法下面**还有条件分支** → 用缩进子项，不要另起一段。
- 讲**一串有先后的动作** → `1.` `2.` `3.`，让顺序可见。
- 讲**两个东西的区别** → 各自加粗名字，或直接上对照表。

**仍然要守的底线**：

- 列表项也要写完整句子，不能变成电报体（`- 确认目标` → 应为 `- 先确认目标仍可识别`）。
- 层次是为了让人看清结构，**不是把散文切碎**。因果和理由仍然要成句。
- 同一层级的列表项，语法形式必须一致（不能一项是句子、一项是短语）。
- 别为排版而排版：如果一个 `###` 下面只有一句话，考虑合并。

## 五之四、★ 合同不留承启：粒度由「讲到能执行」决定，篇幅由「不重复」决定（2026-09-30 用户批评后固化）

**用户原话**：「感觉有些没必要详细展开的点 讲的很细（像 3.2.3.1 直接说 b-cam 作为非实时 自定义模式 需要显式进入就行）；而后也太口水话了……这里应该是**直接的合同**而不用注重语言上的承启」。

### 病灶一：把简单的事摊成并列卡片

用户指出，「从哪里开始」不需要三个入口各配一句「适合……的时候」。**一句话定性就够**：

> B-Cam 是非实时模式，需要用户显式进入。

**怎么判断一件事该多细**：

- 读者拿它**要照着做**（布置流程、触发顺序、状态条件）→ 细到能执行，包括顺序、条件、可选项。
- 读者拿它**只为理解边界**（这个模式怎么进、归谁管）→ 一句话给性质，不展开场景分类。

反面教材：把「三种入口 + 各自适用场景」写成三条带缩进说明的列表。读者不需要知道哪种更常用——他需要知道**能不能从当前状态直接进**。

### 病灶二：产品散文的承启句混进合同

| 不要写 | 因为 | 改成 |
|---|---|---|
| 「原因很直接：同一个机位可以配不同的视线……」 | 讲为什么，是论证 | 直接写「机位不保存视线方向与构图」 |
| 「这是 B-Cam 的核心运行模型」 | 给自己抬轿子的开场白 | 删，直接写「身体与视线控制权独立」 |
| 「……这条路线因此可以配不同的视线方式」 | 「因此」是推理链 | 删，前一句已经说明了 |
| 「它处理用户已经想清楚的镜头：……」 | 用冒号展开比喻 | 直接列条款 |
| 「用户必须能区分 A 和 B」 | 替用户说话 | 写成必须提供的反馈本身 |

**判据**：把句子里的连接词（因此 / 所以 / 原因是 / 这意味着 / 反过来）删掉后，剩下的还是不是一条可执行的规定？去掉连接词就散架的句子，说明它在论证而不在定义——**论证留给讨论记录，合同只留定义**。

### 病灶三：定义式写法（合同的正确句式）

合同的基本句式是「**X 是 Y**」「**X 保存 A、B、C**」「**X 不包含 D**」「**X 时执行 Y**」，不是「我们这样设计是为了……」也不是「这样就能……」。

```
<!-- 好 -->
机位卡保存：空间位置、机头朝向、机身高度或姿态。
机位卡不保存：视线方向、构图方式。

<!-- 差 -->
一个 Position 只保存身体机位……它不保存视线方向、构图方式，也不要求绑定主体。
```

差别不在信息量，在**是否把定义和补充说明混在一句里**。分开列，读者可以逐条核对，也便于后续被引用。

## 六、与 clean-writing 的分工

- `spec-writing`（本 skill）：**内容层**——这句话该不该存在，是规格还是说明。
- clean-writing 四条结构规则：**结构层**——同一概念只讲一次、相邻微章节合并、对偶否定、防御性边界。
- 顺序：先用本 skill 判该留哪些句，再用结构规则组织。

## 七、常见误判

- **把「讲清限制」当成免责删掉**。限制本身是规格，要写；免责的语气才是病灶。
- **把「触发→动作」的兜底句当病灶删**。它规定了系统行为，是规格。
- **只清否定词不动结构**。病灶常藏在陈述句里（实现手段、替用户辩解两类完全没有否定词）。
- **改完不量化**。不报字数变化，无法证明「删掉的都是废话」。
