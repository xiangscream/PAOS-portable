# 技术调研方法论

> 从 B 线影像基础（2026-07-14 ~ 07-19）的 5 天密集学习 + GPT 审查反馈落地提炼。配套已存在的 `product-definition-research` skill：那个解决"做产品决策"的研究；本 skill 解决"建立可被审查的技术知识"。

## 核心问题

技术调研在试用期最常见的四种失败：

1. **假精确** — 引用未经核实的数字（"1080p60 = 1.5 Gbps"、"SRT 延迟 120ms-2s"），无来源不可审计
2. **绝对化表述** — "99% 观众看 HLS"、"8bit Log 等于废片"、"唯一"、"根本原因"，证据不足却语气确定
3. **把推测当事实** — 内部口径 / 工程推断 / 用户单例混进正式叙述，客户和团队按事实使用
4. **审查后不整合** — GPT/同行反馈给出纠错甚至替换内容，仍按自己旧版"重写"，浪费时间且可能再次出错

## 核心原则

### 原则 1：证据等级四档

| 等级 | 来源 | 可用场景 | 标注格式 |
|---|---|---|---|
| **A · 官方** | 厂商规格页、官方手册、RFC/IEEE/ITU 标准 | 正式培训、对外答疑、客户承诺 | A · [来源标题](URL) |
| **B · 内部** | 公司 XLSX/SOP、培训纪要、内部白皮书 | 内部知识库；对外需审批 | B · 内部：[文档名/版本] |
| **C · 推断** | 基于 A/B 的工程推断 | 方案讨论；不可作承诺 | C · 推断：依据是…… |
| **D · 待核验** | 单一来源、传闻、用户单例 | 进入待核任务；不进入正文结论 | D · 待核：[问题] |

**最低记录字段**：主张、等级、来源标题、URL/内部文档号、版本/日期、适用机型与固件、验证人、最后复核日期。

### 原则 2：绝对化表述黑名单

下列词在**没有 A 级证据**时禁用或加限定：

- 全部黑名单："99%"、"100%"、"全部"、"唯一"、"必须"、"完全"、"根本原因"、"彻底"、"绝对"、"永远"、"永不"
- 半黑名单（需限定词）："通常"→加范围、"大多数"→给百分比+"在 X 场景下"、"理论上"→加前提条件、"应该"→换"需要进一步核验"

**反例对比**：
- ❌ "8bit Log 等于废片"
- ✅ "Sony S-Log3 技术资料明确支持 8/10/12-bit code values；10bit+ 是 Log 拍摄的最佳实践，8bit 在复杂渐变下 banding 风险更高"
- ❌ "99% 观众看 HLS"
- ✅ "不同平台、地区、终端采用的播放协议各异；HLS 是其中普及度较高的一种"

### 原则 3：术语卡片 12 字段

每个概念用 12 字段卡固化，避免自由叙述：

```
1. 一句话解释
2. 所在链路（位置）
3. 解决的问题
4. 关键取舍（trade-off）
5. 典型场景
6. 公司产品关联（标注证据等级！）
7. 与相邻概念区别
8. 常见误区（用 ❌ 标注错误说法 + ✅ 修正）
9. 证据/资料来源（URL + 日期）
10. 我仍不确定的地方（D 级）
11. PM 应用指南（如何用到 PRD / 客户答疑）
12. 典型反例（行业 / 公司内具体可对照的实例）
```

### 原则 4：链路图作为 meta-card

跨多张单点卡时，做一张**功能链路图**（不是某一颗 SoC 的固定模块顺序）：

- 主链 + 分支
- 明确标"在 ISP 第 N 步"这类具体位置时，加注"实际模块位置、并行分支和缓存深度由机型、固件和输出模式决定"
- 区分"功能链路"和"硬件模块"——前者是设计意图，后者是实现细节

### 原则 5：交付物分两层

- **底库（v0.x）**：全量参数 + 证据等级 + 待核验项；可作学习底稿
- **汇报版（v1.0）**：压缩到 1 页；只放已确认结论 + 决策建议

> **汇报版不能反推回底库补全**——汇报版是摘樱桃，底库才是树。

## 标准工作流

### 阶段 1：捕获（Inbox）

任何网页、视频、想法进 `01-Inbox/`，**不要直接改分析结论**。只记录：

```text
看到什么：
来源：
可能相关工作线：
需要后续做什么：
```

### 阶段 2：结构化（Knowledge Cards）

按 12 字段模板建卡。**关键纪律**：
- 公司产品关联部分必须标证据等级
- "我仍不确定的地方"必须诚实写出
- 避免单卡超 200 行——长内容拆子卡

### 阶段 3：综合（Deliverable）

需要跨卡综合时做 1-2 张 meta-card（链路图、协议全景、对比表）。原则：
- 引用而不复述单卡内容
- 标注哪些是已确认、哪些是推断

### 阶段 4：审查（外部）

达到完成定义后，**送外部审查**：
- GPT 审查：包内放完整底库 + 单卡 + 链接图，prompt 明确 4 块（项目主线、当前任务、困难、期望输出格式）
- 同行审查：同部门或上下游 reviewer
- 专家审查：技术领域专家

### 阶段 5：审查反馈整合（**核心**）

**GPT / 同行审查返回后，按以下流程整合**：

#### 5.1 区分两类产出

- **审查报告**（指出问题、纠错、列待核项） → 用于更新其他相关文件
- **替换内容**（完整重写版） → **直接采用**作为最终版

#### 5.2 黄金规则：不要二次创作

| 错误做法 | 正确做法 |
|---|---|
| 收到 GPT 替换内容后自己再"重写一版" | 直接采用 GPT 替换内容 |
| 把 GPT 的话"用我自己的话再说一遍" | 保留 GPT 原文，标"GPT 审查修订" |
| 在审查者明确说"用我的版本"时还坚持自己的版本 | 立即采用审查者版本，把差异记为"我的修正" |

#### 5.3 整合流程

1. 读取审查报告全文，识别 4 类纠错：
   - 事实错误（数据 / 概念 / 链接）
   - 绝对化表述（黑名单词）
   - 证据等级缺失（A/B/C/D 标错）
   - 缺失 / 重复 / 矛盾
2. 区分审查者是否提供替换内容：
   - **提供了** → 用审查者替换内容覆盖原文件；在文件头加"v2 审查修订版"标记
   - **没提供** → 自己按纠错清单逐项修正
3. 把审查者的事实/规格核验用 webfetch 抽查 1-3 个最关键引用，确认权威性
4. 把审查报告里"我之前写错 → 现在正确"的对比作为学习笔记保存（避免重犯）
5. 更新工作区元数据（任务板 Done、Today 收尾、缩略语词典）

#### 5.4 常见反模式

- ❌ "我重写一版更简洁的" → 审查者通常更严谨，重写可能丢掉关键限定
- ❌ "部分采用审查者内容 + 部分保留自己的" → 这种拼凑最差，两边都失去
- ❌ "审查者错了，我是对的" → 除非有 A 级证据反驳，否则审查者已交叉验证
- ❌ "在审查者替换内容里加自己的想法" → 污染审查者的纯净版本

## Anti-patterns 总清单

| Anti-pattern | 后果 | 修正 |
|---|---|---|
| 引用数字不给来源 | 假精确；客户按数字做决策 | 每数字标"X [来源]"或留 D 级 |
| 用"99%""必须""根本原因" | 证据不足但语气确定 | 改"在 X 场景下 Y"加范围 |
| 把内部口径当 A 级 | 对外不成立 | 内部知识库默认 B 级；对外需审批 |
| 收到审查反馈后二次创作 | 浪费时间且可能再错 | 直接采用审查者替换内容 |
| 单卡超 200 行 | 不可维护、不可引用 | 拆主卡 + 子卡 |
| 链路图画成 SoC 模块图 | 误导为单一架构 | 明确"功能链路图" + 标注"实际模块位置由机型决定" |
| 缩略语首次出现不给全称 | 卡片自包含性差 | 第一次出现用"缩写（全称）"格式 |
| 把 Log / 色彩管理术语混用（YUV vs Y'CbCr、Rec.709 vs Rec.1886） | 概念混淆 | 严格区分场景线性域 / OETF / EOTF / 量化 |
| 延迟数字伪精确（"约 300ms"） | 没有测量方法时不可信 | 写"T曝光读出 + T编码 + T网络 + ..."加可测项 |

## 工作流：捕获 → 结构化 → 综合 → 审查 → 整合

```
捕获（Inbox）
   ↓ 快速记录，不立即切任务线
结构化（Knowledge Cards 12 字段）
   ↓ 每卡独立可读，证据等级清晰
综合（Deliverable，meta-card 1-2 张）
   ↓ 跨卡串联 + 不重复单卡内容
审查（GPT / 同行 / 专家）
   ↓ 完整底库 + 替换内容（如审查者提供）
整合（核心：直接采用审查者版本）
   ↓ 替换文件 + 写学习笔记
```

## 我学到的关键教训（2026-07-19 GPT 审查后）

1. **审查者已用 webfetch 交叉验证官方资料**——比我自己验证更可靠，不要重新做
2. **审查者提供的 mermaid 链路图**比我手写更严谨——直接采用
3. **绝对化表述是审查者第一刀就砍的**——以后写技术卡时刻意避开黑名单词
4. **OBSBOT 产品能力不可推测**——即使有 Center 设置树等内部资料，未公开规格只能标 B/D 级
5. **"SRT 默认延迟 120ms 但范围 20-8000ms"**——审查者从官方页确认，不是"120ms-2s"的常识
6. **官方 FAQ 是 A 级证据**——"Tail 2 不支持 LOG/LUT 录制"足以改变产品决策
7. **延迟数字必须来自实测**——审查者要求"不只报单次最好值"，要中位数 + P95
8. **OSI 不要硬塞**——审查者用"媒体本体—色彩—像素—编码—容器—媒体会话—传输—IP—接入—控制/供电"10 类替代 OSI 7 层，更准确
