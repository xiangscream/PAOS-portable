## 调用模板

```bash
# 读取（分层优先，不要一上来读全文）
wsl.exe --exec bash -lc '/home/remo/.nvm/versions/node/v24.18.0/lib/node_modules/@larksuite/cli/bin/lark-cli docs +fetch --doc "<url>" --scope outline --max-depth 4 --format json'

# 本地 md 全文写入（@file 必须相对路径，先 cd）
wsl.exe --exec bash -lc 'cd /mnt/c/<目录>; /home/remo/.nvm/versions/node/v24.18.0/lib/node_modules/@larksuite/cli/bin/lark-cli docs +update --doc "<url>" --command overwrite --doc-format markdown --content @./文件.md --format json'

# stdin 插入 block（推荐，比 @file 更稳）
wsl.exe --exec bash -lc 'cd /mnt/c/<目录>; echo "<whiteboard token=\"...\" />" | /home/remo/.nvm/versions/node/v24.18.0/lib/node_modules/@larksuite/cli/bin/lark-cli docs +update --doc "<url>" --command block_insert_after --block-id "<anchor>" --content -'
```

关键规则：调用都用绝对路径走 v1.0.70；批量操作用 WSL Node 脚本 `spawnSync(larkCliPath, [参数数组])` 避免转义问题。

## 核心工作流（最短清单）

```
验证 CLI 身份 → 读历史记录(+history-list) + 云端 revision + outline
→ 对比上次写后快照，锁定用户手动修改（受保护段落）
→ section/keyword 局部 fetch --detail with-ids 拿 block ID
→ 选 str_replace（行内精确替换）/ block_replace|insert_after（结构操作）/ overwrite（仅用户明确要求重建全篇）
→ 执行写入 → 回读验证 revision_id 变化 + 新文本存在 + 旧文本消失 + 受保护段落未变
→ 清理临时脚本 → 报告云端已确认结果
```

## 硬规则速查（2026-09 沉淀，长期有效）

### 写入纪律

1. **lark-cli 没有幂等保护**。同一条插入命令重复执行会重复插入——曾因"想看完整输出"重跑 media-insert 导致图 1 两份副本；`block_insert_after` 因路径问题重试后 markdown 被插入 3 份。**每条写操作执行后必须回读计数验证**（"某标题出现次数应为 1"），发现重复立即 `block_delete` 清理。
   **⚠️ 更狠的一种重复：分块推送脚本的 `count` 是「每批块数」不是「总共推几块」（2026-09-24 实测，损失 189 块）**。想「先插 20 块探路」时**不能**给全量推送脚本传一个小 count——若脚本写成 `while (idx < total) { insert(blocks.slice(idx, idx+count)); idx += count; }`，传 `count=3` 会变成「每批 3 块、一路推到文末」，从没打算推的内容全进文档。更糟的是这条命令被自动转后台后**脱离视野**，等到几天后核对 revision 才发现文档已经长了 63 个 revision。
   **两条防线**：① 探路必须用**独立的单次插入脚本**，或给批量脚本加显式上限（`--max-batches 1`）；② **长任务结束前核对文档 revision**——记下开始前的 rev，结束时 `+N` 必须等于预期的写操作次数，对不上就是有脱管的写入。
   **发现被截断后的处置**：半截章节比缺章节更难发现。回读时要检查「最后一节的最后一段是否讲完」，不能只看标题树齐全。
2. **`--content @file` 必须是 cwd 下的相对路径**。中文路径、WSL 绝对路径（`/mnt/c/...`）都报 `must be a relative path within the current directory`。最稳写法：写 python3 脚本在 WSL 内用 `subprocess` 调 `bash -lc`，显式指定 `cwd`，路径用 `./xxx.md`。
   **配套陷阱（2026-09-26 实测）**：不要试图把正文塞进 `bash -lc` 字符串里的 heredoc（`cat > f.xml <<'EOF' ... EOF`）——转义会错、正文被吃掉，命令静默失败（`.err` 里才有真因）。**正确分工：Windows 侧用 Write 写好 xml 文件，WSL 侧只做 `cd <目录>` + `--content @./f.xml`**，正文永远不经过 shell 字符串。

3. **★ `str_replace` 是「全文查找替换」，不是单点替换（2026-09-29 实测）**。CLI 自带文档原文：「全文文本查找替换」。`--pattern` 命中几处就改几处。
   **动手前必须确认目标串在全文的唯一性**（`content.count(pattern)`）——换术语这类全局动作正好合适，但想让局部改一句就可能误伤正文。命中数 ≥2 而又只想改一处时，改用 `block_replace` 定位到块。
   **⚠️ 命中富文本 span 内部会把 span 切开**：`<b>Shoot｜拍摄集。</b>` 做两轮替换后变成 `<b>Coverage</b><b>｜Coverage。</b>`，显示成「Coverage｜Coverage」。**替换后必须扫一遍 `</b><b>` 相邻标签**，发现就 `block_replace` 整块重建。
   `--pattern` 里的全角字符（如 `｜` U+FF5C）不保证与文档里的码位一致——**模式里写 `\uXXXX` 转义**，或先 `repr()` 对照。全角括号本身可正常匹配（2026-09-29 实测含「」的模式通过）。

4. **★ 插入裸 `<li>` 会被服务器把 `seq` 默认成 1（2026-09-29 实测）**。`block_insert_after` 一个 `<li>…</li>`（不带 seq）后，该条与后续手加条目的 `seq-marker` 都是 `1. `，在文档里显示成「1.」而不是「14.」。
   **正确写法：显式给属性** `<li seq="14" seq-marker="14. ">…</li>`；修正已有的坏条目用 `block_replace` 同样带属性重建。**批量加列表项后要回读 `seq-marker` 逐条核对**，别只看条数。
5. **不要用 `rm` 之外的思路处理临时文件**——但清理命令只放 `recycle.py`，后面**只接文件路径**，绝不串联其他脚本（见"脚本调用安全"）。
6. **★ 报告文档状态前必须重新 fetch（2026-09-29 实测踩坑）**。我曾据 9/26 的一次 fetch 报告「A.6 是半截章节，等决定续写还是撤掉」，三天后复核发现文档已被别的会话补完（rev 960 → 989），报告完全过期。
   **规矩：凡是要说「某处缺 / 断 / 没写 / 还是旧版」，先说这句结论的 fetch 时间；跨轮引用状态一律重新拉一次。** 报告里带 rev 号，让读者能判断新鲜度。
7. **🔴 `ok: true` 不等于成功，必须看 `data.result`（2026-09-30 实测，损失 192 块）**。服务器遇到非法 XML 时会**部分写入**，同时返回：
   ```json
   { "ok": true, "data": { "result": "partial_success",
     "warnings": ["degrade_code=3001,msg=XML tokenization error. Check the input for illegal characters or unclosed tags"] } }
   ```
   只看 `ok` 会把「写了一半」当成功。**推送脚本的成功判据必须是 `result == 'success'`；出现 `partial_success` 立即读 `warnings` 并当作失败处理。**

8. **★ 转 XML 时 code fence 的语言名只取第一个词（2026-09-30 实测，38 个块因此损坏）**。源文围栏常带生成器标记，形如 ```` ```text id="yflcps" ````；若把去掉三个反引号后的整串当语言名，会产出 `lang="text id="yflcps""` —— **属性值里嵌了引号，XML 直接非法**，触发第 7 条的 partial_success。
   **写法**：`m = re.match(r'^[A-Za-z0-9_+-]+', raw)` 取第一段，其余一律丢弃。落成 XML 前建议对每个顶层块做一次 `xml.etree.ElementTree.fromstring` 校验，坏块能提前暴露。

9. **★ 验证用的 fetch 要带重试与长度校验（2026-09-30 实测）**。写到文件的 fetch 结果偶尔为 0 字节，若拿空串去做「尾块是否落盘」的比对会得到**假阴性**，误判写入失败而中断（实际那批是 success）。
   **写法**：`os.path.getsize(p) > 1000` 才解析，否则重试 2–3 次；仍失败就报「无法验证」而不是「写入失败」。

10. **🔴 批量删「节区间」时，结束边界多算一节会静默删掉正文（2026-09-30 实测，误删 2 节）**。要删第 N 节，区间必须写成 `[h4pos[N], h4pos[N+1])`；若写成「从 N 的标题到 M 的下一节起点」（M>N），M 自己也会被删掉。
    **两条防线**：① 动手前把**将删的第一块和最后一块的文本打印出来核对**，只看块数不够；② 保留删除前的 fetch 快照 —— 误删后可以从快照里按 `[a, b)` 原样取回（去掉 `id` 属性即可重新插入），内容零损失。
    **删「最后一节」时额外小心**：区间终点要排除文末的说明段（收录说明 / 衔接说明），否则一起删掉。

11. **★ 不要写「兜底删最后一块」这类逻辑（2026-09-30 实测，删掉正文段）**。我的「若末块不是 X 就删掉」循环里，某轮文本特征没匹配上，兜底逻辑把一段正当的衔接说明当成碎片删了。**兜底删除必须先用文本特征确认目标，不能只靠「位置在最后」。**

12. **★ 用 `block_insert_after` 推含 `<ol>/<ul>` 的长内容，飞书可能把列表压平并把尾部残片挂到段末（2026-09-30 实测）**。症状：段末多出以「状态反馈独立于控制权：…」「Media：Record / Mark。…」这类**半句话**开头的 `<p>`，逐块删会「删一个露一个」（因为源头是一个被压平的 `<ol>`，删 `<li>` 会让父块重渲染）。
    **处置**：一次性定位整个 `<ol>` 块并删除，不要逐 `<li>` 删。**推送完成后专门查一次段末是否有非本节的半句残片。**

13. **★ 整篇重编号用 `str_replace`，不要逐块 `block_replace`（2026-09-30 跑通）**。把 A.6→A.5、A.7→A.6、A.8→A.7 这种整体位移，只需 3 次全文替换（按 6→5、7→6、8→7 顺序，无碰撞），而不是 92 次块替换。
    **前提**：① 带点的编号（`A.6.1`）只出现在标题里 —— 正文交叉引用通常不带点（写作「A.5 / A.6 的关系」），所以只改带点的模式不会误伤；② 动手前先数一遍**附录之前**的正文里有没有 `A.N` 引用（本例为 0）；③ 被替换掉的那一节（如 A.5）必须先删，否则 `A.6.` → `A.5.` 会撞上残留；④ 替换后逐节核对编号连续性与重复。h3 标题不带点，要单独 `block_replace`。

**长内容推送的推荐形态**（2026-09-30 跑通）：按「每批 25 块」切；每批先 fetch 取当前末块 id 作锚点 → 插入 → 再 fetch 校验 `result == 'success'` 且**该批尾块文本确实出现在文档里** → 通过才进下一批。脚本要支持**从指定块索引续推**（中断后不必重推）。**验证一律只回读，绝不重跑写脚本**——重跑就是第 1 条的重复插入。

### 搬块 / 改块

9. **跨章节搬块用 `block_move_after`**：`docs +update --doc <url> --command block_move_after --block-id <锚点块> --src-block-ids <id1,id2,...>`。一次可搬 19+ 块，**保序、保格式**（blockquote / ul / li / 图片原样跟随）；锚点 = 目标小节的标题块。比"删了再插"安全得多。
10. **`block_replace` 会更换 block id**（不是原地修改），旧 id 立即失效。**每轮写操作后必须重新 fetch 拿新 id**。
11. **`--src-block-ids` 的切片上界不能取"下一个 h2"**：会圈进小节之后同级的其它内容，更危险的是**锚点块本身可能也被圈进去**（等于把锚点自己搬走）。上界取"下一个**同级或更高级**大纲点的起点"。**每次都要先干跑**，打印 `i_start / i_end / 锚点索引` 与完整 src 清单核对后再 apply。
12. **markdown 表格可直接转原生表格**：`--doc-format markdown` 传 `| a | b |` 即可（已验证）。补行最稳的做法是整表 replace 重写。
13. **`--detail with-ids` 的 raw 内容是真嵌套 XML**——`<blockquote id=A>` 可包住多个 `<p>`/`<ul>`，子块各有独立 id。判断"哪些是顶层块"必须看嵌套层级，不能按线性顺序数，否则搬块会漏块或重复。
14. **⚠️ `block_move_after` 返回 `success` ≠ 真的搬动了**：对**嵌套块**（嵌在 callout / 表格里的 `<p>` 等）会**静默 no-op**——本日实测 6 处「交互参考」只搬动 3 处，同样返回 `success`、`warnings: []`，位置纹丝不动。**每次搬完必须回读位置验证**，不要只看返回码；顶层 `<p>` / `<h*>` / `<table>` 可正常搬（本日一次搬 6 块成功）。搬不动的改用「读文本 → 删原块 → 目标处重建」。
15. **生成待删 ID 清单时，切片起点不能用 `c.find('<block_id>')`**：那会从 id **值**的位置开切，而 `id="` 在切片起点之前，导致**边界块自身的 id 被漏掉**——本日因此把旧 3.1 标题漏在清单外，删完留下一个孤儿标题。**正确做法：从边界块的标签起始位置切，或把边界块 id 显式补进清单**；删完必须复查「目标标题链」是否连续。
    **⚠️ 同一个坑的第二种写法（2026-09-18 再踩一次）**：用「**start 小于锚点文本位置的最大块**」当边界——
    `boundary = max(e['start'] for e in roots if e['start'] < anchor)`——**同样是错的**。
    因为 `<h2 id="X">A.1 标题</h2>` 里，h2 的 `start` 在它自己的文本 `A.1 标题` **之前**，
    所以 h2 会被算作"边界块"而被**排除在待删清单外**，留下一个孤儿标题。
    **正确写法：取「包含锚点文本的那个顶层块」**：

    ```python
    owner = [e for e in roots if e['start'] <= anchor and (e['end'] or 10**9) > anchor]
    assert len(owner) == 1
    targets = [e for e in roots if e['start'] >= owner[0]['start']]
    ```
    **自检**：打印 `targets[0]` 的 tag 与文本，确认它就是你要删的那一节标题，而不是它的下一个块。

### ★ 整段替换（用外部长文换掉文档的一整节/一整部分）

**2026-09-16 实测跑通：功能总表「第一部分」65 块 → 新文 64 块，5 批删除零事故。** 流程与坑：

74. **正确顺序：先插新 → 回读确认成功 → 再删旧 → 回读确认干净。** 绝不在一条命令里既插又删（第 39 条）。插到「该节标题块之后」（锚点 = 节标题 id），新内容就落在旧内容前面；此时文档里会短暂并存两份，这是**预期中间态**，不是出错。
    - 删除清单从「旧节起始标题 id」到「下一节同级或更高级标题 id」之间取。
    - **只收顶层块 id + 顶层 `ul` 的直接 `li` id**（嵌套 `li` 随父项级联删除）。若把嵌套 `li` 一并收进来，父项删掉后子项报 `2001 not found`，白噪音一片。
    - 每批 ≤25 个 id，逐批看返回；本轮 5 批全 `success`、revision 连续递增。
75. **⚠️ markdown 转列表：列表项之间绝对不能有空行。** 「每块后都补一个空行」的朴素做法会把整段列表变成 **loose list**——每项被包进 `<p>`，视觉与嵌套层级都和原文不一致（父项与首个子项之间隔了空行，嵌套甚至可能断掉）。
    **正确规则**：拼装时，**只有「前一块 → 当前块」不是「li → li」时才补空行**。即 `- 父项` 紧接 `  - 子项` 不空行；最后一个 `li` 到下一个标题/段落、段落列表之间、`hr` 两侧要空行。
    自检：拼完后数 `payload.count('\n\n')`，正常值远小于行数（本轮 196 行只有 62 个空行）。
76. **markdown 模式下 XML 标签会被解析并生效**（`lark-doc-md.md` 明写）。所以整段正文用 `--doc-format markdown` 写、同时用 `<hr/>` 插分隔线是合法的，**优先用 `<hr/>` 而不是 `---`**——`-` 在行首有「无序列表 / 分隔线」双重语义，容易踩坑。

### ★★ 超长内容（300+ 块）分块推送 + 只用在目标文档里出现过的标签（2026-09-24 实测）

**场景**：把 33 节长文（387 块：33 个标题 + 280 段 + 81 个代码块 + 1 表 + 列表）作为新一节写入 PRD 附录。一次推 387 块有被截断后留半截的风险。

**流程（4 步，每步都有硬校验）**

1. **先扫目标文档的标签集合，再决定用什么标签。**
   ```python
   tags = {}
   for m in re.finditer(r'<([a-zA-Z][a-zA-Z0-9]*)[ >]', c):
       tags[m.group(1)] = tags.get(m.group(1), 0) + 1
   ```
   **本日实测 PRD 全篇：有 `h1/h2/h3/h4`、`p/ul/ol/li/b/pre/code/table/img/whiteboard/a/hr`，但 `h5`=0、`blockquote`=0。**
   → 原稿的 `## 2.1` 子节和 `###` 小标题**不能**映射成 `h5`，`>` 引用**不能**映射成 `blockquote`。改用 `<p><b>…</b></p>` 表达层级。
   **铁律：目标文档里没出现过的标签，不要在无先例时引入。** 平台对陌生标签可能"部分接受"（块进去了但结构不对），比直接失败更难查——与第 74 条表格的坑同源。

2. **自建 md→飞书 XML 转换器**，层级映射显式写死：
   - `# N. xxx` → `<h4>A.4.N xxx</h4>`（与目标文档同级节标题一致）
   - `## N.M xxx` → `<p><b>A.4.N.M xxx</b></p>`
   - `### xxx` → `<p><b>xxx</b></p>`
   - ```` ```lang ```` → `<pre lang><code>..<br/>..</code></pre>`（换行一律 `<br/>`）
   - 首行的文档大标题（`# P1｜…`）**丢弃**，由上层新节的 h3 承载，否则会变成一个多余的 h4。

### ★★ 不要拿「转换稿」做 overwrite 的 base（2026-09-17 已知风险仍然踩中）

**事故**：文档 4.x 是嵌套列表，我的 XML→markdown 转换会把嵌套拉平（父子项压成同级）。
我在换摘要时**用转换稿当 base 做了 overwrite**，于是**把拉平的列表结构写回了飞书**——

Human 在文档里留了 8 处批注指出「嵌套关系乱了」「有 * 号错误」「归属错了」。

**规矩**：
1. **只要目标章节含嵌套列表，就不要走「+fetch → 转 md → 改 → overwrite」。** 用 `block_insert_after` /
   `block_delete` 做局部修改；确需整篇 overwrite 时，正文来源必须是**保留结构的原始 md**，不是转换稿。
2. **markdown 里「父项 → 空行 → 子项」会让嵌套断裂**——父子项必须紧邻（中间不留空行）。
   拼装完跑一次扫描：`顶层 '- ' 行 + 空行 + '  - ' 行` → 命中就删掉那个空行。
3. **块级插入加进去的内容不在任何本地稿里**——重建章节时会被无声覆盖。重建前先列一遍
   「线上有、本地没有」的块（我就是这样才发现三层能力架构连着丢了）。

### ★ 块级插入：markdown 模式会丢「列表项内的缩进续行」（2026-09-17 实测）

`docs +update --command block_insert_after --block-id <id> --doc-format markdown --content @file` 可用，
但有两个必须知道的特性：

**① 列表项内的缩进续行（段落）会整个丢失。**
实测：写了一个 li 标题 + 缩进 2 空格的代码块 + 缩进 2 空格的两段正文，结果**只有 li 和 pre 进去了，
两段正文回读计数为 0**。

- **对策**：**一个块一次插入**——把段落拆成独立的 markdown 段落（**不要缩进**，各自插一次）；
  或在需要精确结构时改用 XML 格式。
- **自检**：插入后一定要回读数关键词计数，不能只看 `"ok": true`。markdown 模式的静默丢块是常见现象。

**② 插入的块是锚点的兄弟块（同级），不会自动嵌套进列表。**
想插到某个列表项"里面"，用 `block_insert_after` 是做不到的——它只会紧跟在该项后面。最终排版多半是
「列表项 + 后面跟几个普通段落」，多数情况可接受，但要知情。

**选择插入 vs overwrite 的判据**：
> **文档里有嵌套列表（li 套 li）时，不要走「转换 → 改 → overwrite」的路子。**
> XML→markdown 的转换脚本很容易把嵌套拉平，overwrite 会把原结构破坏掉。此时用**块级插入**更安全。

### ★ 整篇覆盖与文档改名（2026-09-17 实测，两次成功）

**整篇覆盖**（比逐块替换省事，适合"正文全换"）：

```bash
cd <内容文件所在目录> || exit 1     # --content 用相对路径，必须先 cd
lark-cli docs +update \
  --doc <docx token> \
  --command overwrite \
  --doc-format markdown \
  --content @./_new.md \
  --as user --format json
```

返回里看 `revision_id` 递增即生效（本次实测 5→9、14→18）。
**`overwrite` 只换正文，不动文档标题**——标题是文件属性。

**文档改名**（标题必须单独改）：

```bash
lark-cli drive files patch \
  --file-token <docx token> \
  --type docx \
  --data '{"new_title":"新标题"}' \
  --as user --format json
```

- `--type` 必填：`docx`=文档 / `sheet` / `bitable` / `file` / `folder` / `wiki` / `slides` / `mindnote`。
- **核验标题不要用 `docs +fetch`**——它只返回正文，不含文档标题。
  用 `lark-cli drive +inspect --url <文档URL> --format json`，返回里有 `title`。

**⚠️ `docs +create` 建出来的文档标题恒为 `Untitled`（2026-09-20 第 2 次复现）**：即使 markdown 首行就是 `# 标题`，
导入器也不会把它写进文档标题属性；那个 H1 会作为**正文块**留在第一篇，同时返回 `warnings: missing_document_title`
（`hint=add a top-level "# Title" heading` 具有误导性——照做也无效）。**所以用 markdown 建文档固定三步**：

1. 建文档：`docs +create --parent-position my_library --doc-format markdown --content @./x.md --as user`；
2. 改标题：`drive files patch --file-token <id> --type docx --data '{"new_title":"…"}'`（标题取 md 首行 H1 原文）；
3. 删正文重复 H1：`docs +fetch --doc <id> --detail with-ids` 取首个 `h1` 的 id（**先比对它的文本与标题逐字相同再删**）
   → `docs +update --command block_delete --block-id <该 id>`。

实测（Camera Intelligence Stack 转换）：建 rev 12（Untitled）→ 改名 rev 13 → 删块 rev 14（`result: success`），

**发布前必做：markdown 表格「单元格内含换行」修复**

从 Gemini 网页「MD 按钮」复制的正文，表格常长这样（单元格内容后跟空行再跟 ` |`）：

```
| 摄影操作 | 知道拍谁、理解拍摄意图、持续执行

```

直接导入飞书会把表格拆成散行（列数不一致）。修复一行即可：

```python
pat = re.compile(r'(\S)\n\n+ \|')     # 非空白字符 + 空行 + 「空格+竖线」
fixed = pat.sub(r'\1 |', text)
```

**自证没改文字**：`re.sub(r'\s+','',修复前) == re.sub(r'\s+','',修复后)` 必须为 True。
（本次实测：修 36 处，表格列数不一致从 7 处 → 0 处，去空白比对一致。）

**★ 还有一种表格缺陷：自己手写长文时漏掉分隔行**（2026-09-17 实测，一次漏了 16 张表）。
markdown 表格必须有 `|---|---|` 分隔行才成立，**只写「表头行 + 数据行」在飞书里会整块散成普通文本**，
而且肉眼看 markdown 源码时很容易忽略。发布前务必跑一次表格体检：

```python

SEP = re.compile(r'^\s*\|[\s\-|:]+\|\s*$')
# 若「当前行以 | 开头、上一非空行不以 | 开头、下一行以 | 开头且不是 SEP」→ 这是表头缺分隔行
```

**自我复核**：写完长文档后数一下"表格数"。如果一个 PRD/总表里出现了 `| xxx | yyy |` 这类行
却报「表格 0 张」，就是分隔行漏了。

**发布前必做：引号规范**（2026-09-17 实测，一次踩到 30/50/66 处）

- **检查**：`text.count('"')` 应为 0（用 `"` 包代码块的除外）。
- **修法**：**逐行**成对替换——第 1/3/5… 个引号 → `“`，第 2/4/6… 个 → `”`；跳过 ``` 包裹的区间。
  成对替换必须按行做，跨行会错位（替换前先看有没有行的引号数是奇数）。
- **顺手**：同一轮产出的其他手写文件一并检查，通常不止一份。

**`overwrite` 是整篇替换，内容源搞错会整篇覆盖。** 动手前先确认目标 token 就是本轮要更新的那一份

### ★ 本机内联命令的四个必踩坑（2026-09-17 一天内全踩齐，务必按此规避）

**统一解法：凡是内容超过一行的命令，一律用 Write 工具落 `.py`/`.sh` 文件再执行，不要内联。** 以下四种都是内联才出的错：

1. **反引号**：`python -c "… ` …"` 里的反引号被 bash 当命令替换，报 `unexpected EOF while looking for matching`，整条命令不执行（exit 2）。
2. **中文引号**：内联脚本里写中文时若带 `“”''「」` 与 ASCII 引号混用，bash 会吃掉配对，报 `SyntaxError: unterminated string literal`。**落文件就不会**。
3. **`%` 格式化**：Python 字符串里出现字面 `99%` 时用 `%` 格式化会报 `TypeError: not enough arguments for format string`。改用 `.replace('@@KEY@@', v)` 占位替换。
4. **PATH 缺 `/usr`**：`mkdir` / `ls` / `head` / `wc` / `cat` / `sed` / `tail` 全部 `command not found`（exit 127）。
   - Bash 工具先补：`export PATH="/c/Users/remo/.workbuddy/binaries/PortableGit/versions/1.2.0/usr/bin:$PATH"`
   - **注意 `cat > file <<'EOF'` 也会失败**（`cat: command not found`），落文件只能用 Write 工具。
5. **PowerShell 工具的输出通道可能整体失效**（连 `Write-Output "hello"` 都拿不到 stdout，exit 0 但空）——此时不要继续用它试探，改走「Bash 调 Python 绝对路径 + 输出重定向到文件 + Read 读回」。

**⚠️ 我上一轮把第 ③ 类判为「必须保留的产品规则」，那是错的。**
正常行为不需要声明"我会保证"——读者看「Mark 表示这一刻值得留下，触发后建立标记并保存事件片段」就够了。

**结构层（同样重要）**

- **不写过程态**：能合的中间步骤就合。「远程看」「远程听」「远程说」三条并列 → 全部并入「**远程控制**」。
- **分点按「用户阶段」合，不按「系统模块」拆**：B-Cam 的 7 个平铺分点 → 归成「**先进行布置**」（机位/路线/示教）
  与「**开始拍摄**」（视线/重拍/结束）两组。
- **层级能压就压**：300 ms 那段从独立分点 → 并入「远程移动」同一行；空间采集的嵌套子项 → 提为一级。

**措辞层**

- **命名用直白的词**：「从哪里拍」→「**相对位置**」、「拍多大」→「**相对构图**」、「远程在场」→「**远程控制**」。
- **语气可以正面、可以口语**：FPV 导语从"它同时服务两方…面对一个小型实体"改成
  "以新奇的视角并能够进行互动，有双向价值…现场的人或宠物则**会欢迎一个会靠近、等待、回应和发声的有趣伙伴加入**"。

**自检三问**（写完每段过一遍）：
1. 这句是在说**用户**，还是在说**系统**？
2. 这句是在说**功能**，还是在**保证功能**？
3. 这两个分点能不能合成一个？

**不要拿"信息量"或"这是产品规则"当保留理由——那是作者的焦虑，不是读者的需要。**

### ★★ 清理类改动的验收：查「缺陷类别」，不要查「单点字符串」（2026-09-17 被当场抓到）

**事故**：向协调方回报"已删除文件头过程说明"，对方回读后发现**没删干净**。
根因是**同一类缺陷有两处实例**——文档里原有两个头部块（① 上游交付时的工作稿标记，② 更早的还原/来源说明块，
紧贴正式标题）。清理脚本只删了 ①；而我的校验**只断言「本地完整稿」这一个字符串**，
①删掉就"通过"了，②一直留着。

**规矩**：清理/删除类改动，验收判据必须写成**结构性条件**，不能写成"某个字符串在不在"：

| ❌ 单点断言（会假通过） | ✅ 类别断言 |
|---|---|
| `assert '本地完整稿' not in t` | `assert lines[0] == '# 正式标题'` |
| `assert '某个头' not in t` | `assert 标题之前的非空行数 == 0` |
| `assert '某个过程词' not in t` | 把**该类别所有已知过程词**列成表，**逐个**计数必须全为 0 |
| `assert 'A.3 依据来源' in t` | 用正则取出全部附录编号，断言**唯一且连续** |

**自检口诀**：**写完断言后问一句"如果同一类缺陷换个说法/换到别处，这条断言还能抓到吗？"**
抓不到就换判据。另外**报"已完成"之前，要把判据原文和实测值都列出来**，
不要只写结论——这次如果我把"标题前非空行数"写进回报，自己就会发现异常。

**过程词黑名单（本项目实测有效，可复用）**：本文件说明、由 … 添加、粘贴件、质检、逐节字数、
工作稿、本地完整稿、重构施工计划、本次修订、本次对话、Internal Review、审查包、反向审视、
文档下载与导出提示、还原说明。

**⚠️ 黑名单只收「组合词」，不要收常用词**（2026-09-17 实测）：把「本次」「修改」「建议」「新增」「版本」
这类产品文档里的正常词汇放进黑名单，会大面积假阳性——实测一次报出 9 个"元语言"，
逐条核对**全是正当用法**（「本次使用」「保留本次布置」「可以修改的结果」）。
**规矩**：
- 只收明确的编辑语境组合：`本次修订`、`修改说明`、`版本说明`、`编辑说明`、`详见下表`、`如上所述`；
- **检查范围限定在正文**：任务说明、收尾提示里出现这些词是设计意图，不是缺陷；
- 报 FAIL 后仍按老规矩——**先看上下文再决定动不动文档**。

### ★★ 批量修订脚本：锚点怎么选、断言怎么写（2026-09-17 实测）

**① 锚点要选「插入位置的下一个标题」，不是「下一个同级章节」。**
想插在 `#### 6.2.1` 之前，如果锚点写成 `### 6.3`，替换会把 6.3 的标题整行吃掉。
差一级就会吞掉中间的标题和内容，而且脚本不会报错。

**② 每处改动打一行日志，并把「期望命中数」写成参数。**
`rep(old, new, label, expect=1)`：命中数 ≠ expect 才算失败。
只打印"成功/失败"不够——锚点匹配到**多处**时静默改掉不该改的地方，比"没匹配到"更危险。

| 写法 | 能否抓到"匹配到多处" |
|---|---|
| `if old in t: t = t.replace(old, new); print('ok')` | ❌ 抓不到，还会全改 |
| `n = t.count(old); if n == expect: ... else: print('MISS', n)` | ✅ 抓得到 |

**③ 校验断言必须用「目标文档的实际词汇」，不能凭记忆或拿参照文档的措辞。**
**事故（同一天三次）**：
- 用 PRD 的「沉浸式 FPV」「低视角互动」去断言功能总表，实际文档写的是 `Immersive FPV`、`低速互动`；
- 用「一次活动的共同主链」去断言，实际文档写的是「一次活动通常这样走完」——那个词只是**我脚本里的标签名**；
- 用 `# 标题` 断言飞书文档的正文主标题，实际回读是 HTML→纯文本，**标题不带 `# ` 前缀**。
三次全是假阴性，文档内容本身完整。

**规矩**：
1. `FAIL` 之后**先 grep 关键词的近义形式**（英文名 / 同义中文 / 拆分词），确认是"真缺"还是"断言写错"，
   再决定动不动文档。**按错断言去补内容，等于往一份完整文档里塞重复段落。**
2. **断言写完先对本地源文件跑一遍**，全过再拿去验飞书/远端。错就错在本地，不会在远端报假 FAIL。
3. **断言词尽量从目标文档 grep 出来**（或直接从源文件复制），不要手写。
4. **断言还必须匹配「目标载体的表示形式」**——源文件是 markdown、飞书回读是 HTML 转纯文本，
   同一句话在两边形式不同。**"源文件里有"不等于"飞书回读里是这个形状"**：
   markdown 的 `# 标题`、`| 表格 |` 到了纯文本里都没有那些标记。
   写飞书侧断言时，只用**纯文本内容**，不要带 markdown 语法符号。

### ★★ 块级批量修订：三个必踩坑与可复用脚本（2026-09-17 实测，一次踩齐）

**背景**：一次要在一篇含嵌套列表的长文里做 14 处局部改写（替换 `p`/`li`/`h1`、搬块、跨标签插文本）。
结果前 13 条连续 `1011`，全部出自下面三个坑。修完一次性跑通（rev 200→216）。

**坑 1｜`ok: true` + exit code 0 ≠ 成功。必须解析 `data.result`。**
`run()` 只看 `r.status === 0` 会判成成功。实际返回长这样：

```json
{"ok": true, "data": {"document": {"revision_id": 202}, "result": "failed",
 "warnings": ["degrade_code=1011,msg=Instruction produced no document changes..."]}}
```
—— `ok: true` 是「请求送达」，`result` 才是「内容改了」。**判定写成**：

```js
const j = JSON.parse(out);
const ok = j.ok === true && ['success','partial_success',undefined].includes(j.data && j.data.result);
```
并**回读 revision 是否递增**；`revision_id` 没动就是没改。

**坑 2｜自己写的 XML 扫描器「返回命中包装对象」而不是块本身。**
`locate()` 返回 `hits.push({ el, t })`，调用处若写 `const el = hits[0]`（少了 `.el`），
`el.id` 是 `undefined` → `--block-id undefined` → **每一条都是 1011**，
而报错信息会误导你去改内容。**自检：动手前把 `el.tag / el.id / ownText 前 40 字`打一行日志**，
看到 `undefined undefined` 就是脚本的错，不是文档的错。

**坑 3｜跨 `</b>` 的 `str_replace` 会让新文本继承粗体。**
想给一个没有引导句的条目（`<li><b>组名</b><ul>…`）补一句正文，最直觉的写法是
`--pattern "（批注）</b>"` + `--content "</b>　正文…"`。**它不会生效**：
`</b>` 被吞掉，新文本变成 **第二个粗体段**（`<b>组名</b><b>正文</b>`），整段加粗。

- **正解**：不要用 `str_replace` 往标题行后面插正文。改用
  **`block_replace` + `<ul>` 包裹，把该条目就地扩成两条**（本条 + 新条目）：

  ```
  --block-id <该 li 的 id>
  --content '<ul><li><b>原条目名</b>　原文…</li><li><b>新条目名</b>　新正文…</li></ul>'
  ```
  实测：仍留在原层级、嵌套不断、旧 id 换新（下轮重新 fetch）。

- **`block_insert_after` 在「嵌套 `li`」上做兄弟插入会 1011**（同一轮实测，`<li>` 和 `<ul><li>` 两种
  content 都失败）。想在列表内部加条目，**用上面那条 `block_replace` 就地扩条，不要用 insert_after**。
  `block_insert_after` 只在「标题块之后插段落」这类顶层场景稳定可用。

**可复用脚本形态**（`tmp/<日期>/apply.js`，WSL 内 Node + `spawnSync` 直调 lark-cli）：

- 操作写在 `ops_<doc>.json`，**每条用「文本前缀」定位块，绝不缓存 id**——
  `block_replace` 会换 id，缓存 id 必踩第 10/38/62 条。
- 主循环：**每条操作前重新 `+fetch --detail with-ids`**（一次 fetch 一两秒，14 条完全可接受），
  再 `locate` → 执行 → 打印 `命中 tag/id/文本` + `result` + `revision_id`。
- `str_replace` 类操作带 `expect`（期望命中数），**先 `xml.split(pattern).length-1` 比对再发请求**，
  命中 0 或 ≥2 直接跳过并报出来（避免静默改错位置）。
- 长内容一律走 stdin：`--content -` + `spawnSync(..., {input: content})`，不拼命令行、不用 `@file`。
- 收尾统一 fetch 一次存 `*_after.json`，再用「标题链 + 嵌套层级 + 块 id」的导出脚本回读校验。

**这套写法的收益**：14 处改动里 13 处是 `block_replace`/`move`/`delete`，
全程零 id 失效事故——因为**下一轮拿到的 id 一定是刚 fetch 的**。

### ★ 新增表格 / 长附录：XML 写法与落点（2026-09-18 实测跑通）

**表格用 XML 直接写最省事**（`--doc-format markdown` 的表格也能转原生表，但下面这条链要同时带嵌套列表，混格式容易出事）：

```xml
<table>
<colgroup><col width="120"/><col width="330"/><col width="170"/></colgroup>
<thead><tr><th background-color="light-gray">表头</th><th background-color="light-gray">表头</th></tr></thead>
<tbody><tr><td>单元格纯文本</td><td>单元格纯文本</td></tr></tbody>
</table>
```

- **单元格里写纯文本，不要套 `<p>`**（`lark-doc-xml.md` 的扩展示例就是这么写的）。
- `<th background-color="light-gray">` 可生效——回读时 `background-color` 的计数会等于**表头格数**，别把这个数字当成"残留高亮"去清理。
- `<colgroup>` 可以省；写了就按比例分配，长文本列给宽一点。

**2026-09-24 补充实测**：单元格**套 `<p id="...">` + 显式写 `vertical-align="top"` 也能成功**，且落盘后平台会**自动补全**内层 `<p>` 的 id（把你写的占位 id 换掉）和 `vertical-align`。但**不要只写 `<table><tbody><tr><td>`**——缺 `thead` 时会被**部分接受**（表格进去了，结构不完整，回读可见异常），比直接失败更隐蔽。**最小可靠写法**：
```xml
<table><colgroup><col width="260"/><col width="300"/></colgroup>
<thead><tr><th vertical-align="top"><p>表头</p></th><th vertical-align="top"><p>表头</p></th></tr></thead>
<tbody><tr><td vertical-align="top"><p>内容</p></td><td vertical-align="top"><p>内容</p></td></tr></tbody></table>
```

**只有一列的表不要做**：目标文档里若从无单列表格先例（先数一下 `table=` 与各表的 `col` 数），单列流程图/清单改用**代码块**，不要造低质量表格。代码块写法：
```xml
<pre id="..." lang="text"><code>第一行<br/>第二行<br/>        ↓<br/>第三行</code></pre>
```
换行一律 `<br/>`，不要写真实换行符。

**清单一：一次 `block_insert_after` 可以带多个块**（`<p>` + `<table>` + `<p>` 一次进），不需要拆成多次插入。

**清单一：想往「某一节列表之后」加内容，锚点取该列表的最后一个顶层 `li`**——新块会落在**列表外面**（本节末尾、下一个 `<hr>`/标题之前）。
实测可行（3.1 后面加一张表就是这么做的）。注意这与「在嵌套 `li` 上做兄弟插入」是两件事，后者必 1011（见上一节坑 3）。

**清单一：`block_replace` 一个带嵌套子列表的 `li` 时，`--content` 要把整棵子树重新写全**：

```
--content '<ul><li><b>父项</b>　正文…<ul><li><b>子项</b>　…</li><li>…</li></ul></li></ul>'
```
实测：嵌套层级保留、旧子项随旧 `li` 一起消失、id 换新。**动手前先把该 `li` 的原始 XML dump 出来照抄**，不要凭记忆写子项。

**别用 `<h3>` 当表格的小标题**：它会进文档大纲，让某一节凭空多出一个子节（1.7 只有一个段落时尤其突兀）。
**表标题用加粗段落** `<p><b>表标题</b></p>`。写长附录时同理——标题级别只有在你确实要让它出现在大纲里时才用。

**长内容的传参**：给批量脚本加一个 `contentFile` 字段（读 `DIR/xxx.xml`），不要把几千字的 XML 塞进 ops JSON 的字符串里——
JSON 转义一多，改一处要改三个地方，而且 diff 不可读。

### ★★ 有人在同编时怎么施工（2026-09-18 实测：对方一次会话里改了 3.1 整节）

**情形**：一份多人共享的产品文档，产品负责人一边看一边动手改。本轮实测他的编辑让 revision 在十几分钟内
从 302 跳到 320、348、354，并且**重排了整整一节**（拆 li、填括号待补项、删掉别人补的说明段）。

**四条纪律**：

1. **不要凭记忆或缓存 id 动手。** 每次写操作前重新 `+fetch`，**按文本身份**（文本前缀）定位块。
   这样即使对方刚改过结构，你的定位仍然落在正确的块上。id 只在"这一次操作"内有效。
2. **发现 revision 跳幅异常 → 先停下来看清对方改了什么。** 判据：
   - 块 id 前缀不是 `doxcn`（如 `EH6g…`、`QBWN…`）= **客户端生成的块**，那是人手动编辑留下的；
   - 出现空段落 / 空 `li`；
   - 句子没有句号、以分号或逗号收尾；
   - 括号里的待补项被填上了内容。
   这几条同时出现，基本可以断定对方正在手工重排。
3. **不要回滚对方的改动。** 他删掉的段落就是删掉了。**上一轮你补进去的内容被他删了，也不要自动补回**——
   报告出来让他决定。本轮实测：我补的「JO4308 变更说明」「六台电机经 CAN 串联」被他重排时收掉，
   我只报告、不恢复。
4. **对方的段落，等他停笔再清理。** 他编辑到一半时会留下空块和断句；**在他明确说"我改完了"之前不要动那一段**，
   否则你会在他正在写的句子上打补丁。停笔后可以清的：客户端空段落、断头残段（补回主语、补句号）、
   段落首尾的多余空格。

**"加粗残段"的识别**：分组名本该是嵌套列表的父 `li`，却只剩一个行内 `<b>组名</b>` 挂在别的条目末尾——
典型形态是 `<li>…正文。<b>先进行布置</b><ul>…</ul></li>`（组名跑到了 `<ul>` 前面），
或 `…正文。<br/><b>开始拍摄</b></li>`（组名挂在上一个子项尾）。
**清法**：把该父 `li` 的整棵子树重写一遍，去掉那两个行内 `<b>`，子项保持平铺。
若想做成真分组，`li` 里再嵌一层 `<ul>` 即可，但那会让全文从两层变三层——**先问一句再决定**。

**正文首行大标题与文档标题重复**：飞书文档标题栏已经显示标题，正文再来一个同名 `<h1>` 属常见"没收拾"痕迹。
删掉它（`block_delete` 那个 h1）不会影响文档标题——`<title>` 是文档属性，独立于正文。

**按 id 定位空块**：空块的文本是空串，用文本前缀定位必然匹配到一堆块。
批量脚本要有一个 `findId` 分支（直接 `parseBlocks(...).all.find(e => e.id === op.findId)`），
专用于删这类块。

### ★ 表格单元格边界：不要写跨单元格的 pattern（2026-09-18 踩中）

想改 1.6 表里「LRC101 新建 / 小型轮腿运动…」这两格，很自然会写 `LRC101 新建小型轮腿运动` 当 pattern——
**必然 0 命中**。因为 `LRC101 新建` 在上一格、`小型轮腿运动` 在下一格，中间隔着 `</td><td>`，
`str_replace` 的 pattern 是**行内文本**，跨块边界就断了。

**判据**：`pattern 命中 0 次` 而文本明明在屏幕上连着 → 先怀疑它跨了单元格 / 列表项 / 段落边界，
把 pattern 收进**单块之内**再试。

### ★ 从 Gemini / ChatGPT 网页复制文档的两种失效模式（2026-09-17 实测，判据不同）

数**四个数**就能立刻分辨，先数再动手：

| 判据 | ① 渲染视图式复制 | ② Markdown 按钮式复制 |
|---|---|---|
| `#` 行数 | **0**（标题全平） | 正常 |
| 真实 tab（`chr(9)`） | 有（表格靠 tab） | **0** |
| 粗体 `**` 对数 | 近乎 0 | 正常 |
| `MD` / `+ N` 字样 | **有**（`MD`=复制按钮；`+ N`=「还有 N 行未展开」，**意味着内容缺行**） | 无 |

- **① 渲染视图式** → 需要**整体还原**：用旧版标题表做锚还原层级、按 tab 分组还原表格；
  **粗体不可恢复**；若有 `+ N`，**必须在缺行处插显式标记，不要伪造**。
- **② Markdown 按钮式** → 只有一处真问题：**表格单元格内的换行被保留**，导致整行被拆散，形如
  `| 行标签 | 单元格A ␊␊ | 单元格B ␊␊ |`（一行散成三行）。
  **解法**：把表格块的所有行拼回一条字符串，按「**凑满 列数+1 个竖线即一行**」重新切行；
  列数取自表头（表头竖线数 − 1）。拼完回读**列数一致性**（每行竖线数 == 表头竖线数）即可确认。

**★ 优先级判断**：有 `+ N` 缺行时，**请用户重新点「MD」按钮取一份干净件，比自己还原划算得多**——
重取是一分钟的事，还原要多轮迭代且仍缺内容。**缺行件不能作为内容审阅的基线**（只可用于判断结构）。

### 分割线、缩进与层级呈现

29. **分割线＝`<hr/>`**（XML 模式，默认格式即可）：`docs +update --command block_insert_after --block-id <锚点> --content "<hr/>"`。**没有 `block_insert_before`**——要在某个标题**前面**插东西，锚点取它的**前一个块**。（`--doc-format markdown` 下 `<hr/>` 同样生效，见第 76 条；**不要用 `---`**。）
30. **列表最后一项可以当锚点**：`<ul>` 容器本身没 id，但每个 `<li>` 是独立 block 且带 id。用最后一个 `li` 的 id 插入，新块会落在**列表外面**（顶层），位置正好是"这一节之后"——不需要用 `block_replace` 重建标题。
31. **嵌套列表用 markdown 两个空格缩进**：`- 一级` / `  - 二级`，lark-cli 会生成 `<li>…<ul><li>…</li></ul></li>` 的真嵌套。回读验证方式：数 `<ul>` 与 `<li>` 的个数。
32. **飞书正文里层级只能靠列表缩进表达**——标题（h1–h9）**没有缩进属性**，h4/h5 在版面上与 h3 齐平。要"让多级结构看起来更有条理"，正确姿势是**大块之间用分割线、块内层级用嵌套列表**，而不是继续往下堆标题级别（h5 已经很难看出从属关系）。
33. **⚠️ 单层项目符号不算缩进**：列表项的文字位置与正文段落齐平（只有符号落在页边），所以"把子项改成单层 bullet"交付后会被告知"还是看不出层级"。要真做出缩进必须**嵌两层**——把引导句升为一级项、子项降为二级项（`- 父` / `  - 子`）；或者用**引用块**（左侧竖线 + 内缩），后者更接近"缩进引导线"的观感。
34. **删列表不能删 `<ul>`**：`<ul>` 容器没有 `id`，只有每个 `<li>` 有。删除整段列表要**逐个删 `<li>` 的 id**（`block_delete` 支持逗号分隔批量）。
35. **把标题层级整体换成列表缩进**时，最省事的做法不是逐个 `block_replace` 每个标题，而是**按节整段重建**：保留该节的 H3 与引导段，在引导段后 `block_insert_after` 一整段嵌套 markdown 列表（每行 `- **编号 名称**　说明`），再按节分批 `block_delete` 掉原来的标题、说明段与旧列表。**代价必须提前说清楚：该层级的标题会从文档大纲里消失**（飞书侧边大纲只收 h1–h9）。
36. **同类对象横向对比保留表格**：加缩进不等于把所有表都拆成列表。表适合"几个对象 × 同一组维度"的横向对比，列表适合"一个对象的若干子项"。两者分工不同。
37. **写前必比 revision**：`docs +history-list --doc <url>` 的返回字段是 `entries`（不是 `items` / `history`），每条含 `revision_id / history_version_id / edit_time / editor_ids`。若 revision 比自己上次写入后多了，先判断有没有**用户手动编辑**——典型痕迹是列表里出现**空 `<li>`**，或某个块的 id 前缀不是 `doxcn`（客户端生成的）。这类空行可以在重建该段时一并清掉，但**必须在报告里说明**。
38. **⚠️ `block_replace` 会换 id，旧 id 立刻失效**。用失效 id 当 `block_insert_after` 的锚点，**不报"锚点无效"，而是报 `degrade_code=1011, msg=Instruction produced no document changes`**——看起来像"内容没变/格式不对"，实际是锚点没了。**看到 1011 先怀疑锚点，别先改内容**。
39. **⚠️「插新的」和「删旧的」不要放在同一条命令里赌**。一次操作里先插后删，插失败（1011/限流/任何原因）但删成功了，就会**把旧内容删掉而新的没进去**（本日 §4.4 一度整节消失）。规矩：**插入成功后回读确认，再执行删除**；或至少把插入与删除分成两批，先确认前一批的返回。发现内容被删空时，重新 fetch 取锚点后补插即可，飞书有历史可回退。
40. **批量改编号别手写列表**（本日跑通、强烈推荐）。要给一整节的嵌套列表换编号时：**写脚本 fetch → ElementTree 解析 → 把 `<li>` 还原成 markdown（`<b>` → `**`；`<li>` 嵌套用两个空格缩进）→ 正则替换编号 → `block_insert_after` 插新的 → 按老 `li` id 批量 `block_delete`**。好处：用户的手动编辑一字不丢、粗体与嵌套结构保留、不用手抄几百行。别用正则直接 `str_replace` 编号——同一编号可能出现在正文里，会误伤。
41. **`block_delete` 一次传太多 id 会部分失败**：报 `degrade_code=2001,msg=Specified block ID not found`（`partial_success`）。**按每批 25 个左右拆开**，并逐批检查返回；失败的那批重新 fetch 后再删。
42. **清理批注/草稿文字后要复检**：搜关键词（如用户留下的批注标记）时，注意**块 id 本身可能包含该字符串**（如 id 里的 `WBD`），别当残留内容去删块。
43. **⚠️ 在 WSL 里调 lark-cli 必须写 shell 脚本，不要拼单行**。`wsl -- bash -lc "… \$L docs +update …"` 这种写法，`\$L` 展开后会被 WSL 参数传递机制吃掉，报 `docs: command not found`。**正确做法：把命令写进 `.sh` 文件（用 Write 工具，避免 CRLF —— 先 `sed -i 's/\r$//'` 再 `bash`），在脚本里定义 `L=…/lark-cli`，然后顺序调用。** 还能顺手把多步操作（改名 + 删除）串在一起，每步 `grep -E '"ok"|"revision_id"|"result"'` 打印关键行便于核对。
44. **给整节重编号前，先 dump 一份"结构 id 表"当工作底稿**：fetch → ElementTree → 按顺序列出 `tag / id / 文本前 40 字`（含 ul 内每个 li 的 id）。改编号会连带 `block_replace` 换掉多个标题的 id，**下一轮再改同一节时旧 id 全失效**；留一份 id 表（连同 rev 号）能省掉一整个来回。本日 rev 542 的 id 表已归档到工位 outputs。
45. **一次会话里连做多次 `block_replace` 重编号时，revision 可能不单调递增**（同一批操作里两次返回同一个 rev，或跳号）。**不要用 revision 当"这一步是否生效"的判据**，看 `"result": "success"` + 最后统一 fetch 回读全文结构。
46. **会议决议要落进文档时，先做「逐节现状导出」再动手**（本日跑通）。做法：`+fetch --detail with-ids` → 写脚本按节打印（`tag / id / 全文`，含 `ul` 里每个 `li` 及其嵌套子 `li`），把**待改各节的现状**一次性摊平成文本；然后拿这份文本跟会议原话逐条比。好处有三个：①能看出决议是"已经改过了"还是"还没改"——本日就发现「预设云台」早已删、「机位接力」还留着；②能顺手发现格式残留（本日的 `**调整云台（相机构图） **` 星号错误、`（接着B-cam）` 内部批注）；③能定位"决议与文档现状互相矛盾"的地方（本日 §3.1 与 §3.3 对体感的说法打架）。**不要凭上一轮的记忆写改动清单。**
47. **读会议逐字稿时，把"能直接落表"和"不敢落表"分开记**。自动转录会有同音错字（本日「决策化」= 角色化、「试效」= 示教、「英特360/森海高斯」= Insta360 / 3D 高斯）、缩写对不上（「RCA」）、指代不明（「我们这三家公司」）。**这些一律不进文档**，单独列成"存疑"清单交回人工确认；宁可少写，不要按猜测写进正式文档。
48. **★ 动笔前必查 revision 有没有被人工改过**。本日版本从 542 跳到 667——用户自己动手了：在标题里留批注（`3.3 驾驶与视线（手机 pro sku）`、`4.2 角色化（可行）（模块化）`）、改节名（`4.4 空间采集 / 3DGS`）、并**自行删掉了两整节**。若按旧 id 或旧结构写，会覆盖或错位。检查动作：`+fetch` 拿 `revision_id` 与自己上次写入值比，不一致就**重新 dump 一遍结构**再动手；标题级的括号内容往往是用户的"待办批注"，不是最终文案——要按它改写正文、再把括号去掉。
49. **判断功能列表"能力与功能混杂"的三条判据**（本日用户点出、跑通）：① **能力/口径不是功能**——"安全停稳与自恢复"（能力）、"失锁说明"（口径）、"切换期间先降低运动强度"（约束）要从列表移进引导段或删；② **状态不是动作**——"Ready 进入待拍状态"是状态，折进"录制"；③ **一个条目别横跨两个域**——"手势与语音"写在"指定目标"里却夹着开始/暂停/Mark 指令，要窄化到只管目标。清理后条目数会掉一截（本日 29→25），这是对的，不是丢内容。
50. **"无层级"的三个典型症状与修法**：① **孤条**——某一层里只有它没有子项（如 `切换使用方式`），要么给它子项、要么并入引导段；② **编号不成套**——同文档里 §2.2 的分组叫 `2.2.1`、§1.3 的分组却是裸组名，按文档已有约定补编号（`1.3.1`…），顺带把英文子项名（Preview/Record/Hold·Resume）改回中文与前后节一致；③ **同一视觉层级承载两种语义**——某节 L1 是"分组"、邻节 L1 是"叶子"。修 ② 时注意：**改编号会连带 `block_replace` 换 id**，先 dump 一份 id 表。
51. **"不清晰"最常见的一种：分组行把子项重抄一遍**。症状是 L1 文本 = 组名 + 概述 + 三个子项原文，下面又列同样的三个子项 → 读者读两遍。**正确形态（对照本项目 §2.2.1）**：L1 只写 `组名 + 一句真引导`，子项另起 `<ul>`。修的时候别用 `str_replace` 抠字，**按节整段重建**：在节标题后 `block_insert_after` 插入新的 `<p>引导段</p><ul>…</ul>`，回读确认后再按旧顶层 `li` 的 id 批量 `block_delete`（删父 `li` 会连带其子项）。**插入与删除分两批，先验证插入**。
52. **★ 枚举取值不是功能条目**（层级判据，2026-09-15）。一个"模板 / 方式"下的几个取值（直线 / 弧线 / 环绕 / 平行）要与该事物的**另一种做法**（自定义路线）平级，必须归到模板名下。典型症状：**引导句里已经写着"分 A 与 B 两类"，但层级上没做出来**——文字说了两类，列表里却是 N 条并列。判别方法：读分组引导句，找"分…两类 / 有…几种"这类表述，若列表里没有对应的两层，就是这里断了。
53. **嵌套超过两层是可以的，但要说明代价**。飞书原生列表支持多层（`<li>` 里再嵌 `<ul>`）。本日 §2.3.2 出现全篇第一处三层（节 → 两个分支 → 分支取值）。**三层会打破"全篇统一两层"的观感**，所以另有一个更平的方案：把两个分支各自升为独立小节（全篇保持两层），代价是后面小节编号要顺延。**两种都合理，选完要在回报里说清理由并给出另一种，让用户一句话就能切换**——尤其当文档里还有其他人在同编时，改编号会撞车，不动编号往往更稳。
54. **段落末尾常有飞书遗留的空 `<p>`**（`txt()` 为空）。按节重建时顺手删掉，`+fetch` 时用 `txt(el).strip()==''` 就能识别。
55. **★「不像功能，像使用流程」的识别与修法**（2026-09-15）。症状：一节下面平铺 5–7 条，逐条按"用户能做的事 / 设备给出的结果"过**居然都能过**，但整节读起来就是一条时间线。**根因不是条目内容，是命名和排列**——条目名用了**阶段词**（开始 / 进行中 / 完成 / 结束），或几条连起来天然成序。**修法：给这条流程一支**，让它当"过程"就名正言顺（如「拍一次」下含 启动 / 拍摄中 / 拍完），再把混在里面的控制项升成另一支（如「云台控制」）。**改名只是辅助，分组才是主因。** 附带好处：节名若本身暗示两分（「拍摄**与**云台控制」），分组后节名才真正落地。
56. **★ 全局功能不重复讲，名字也别撞**。文档里若有"跨方式 / 公共"层（本项目 §1.3），各模式小节就**不要再列**公共层已有的条目（准备连接 / 指定目标 / 预览·录制·暂停·标记·召回·结束 / 状态反馈 / 素材整理）。做法：写任何模式小节前，先过一遍公共层清单。**并且条目名不能与公共层重名**——即使语义不同也要改（本项目「结束」(Take 结束) 撞全局「结束」(Stop 整场)，改成「拍完」）。**同名会让读者以为是同一件事，这是比重复列举更隐蔽的错。**
57. **`block_replace` 用在嵌套 `li` 上可以保嵌套**（本日实测）：对 L3 的 `li` 传 `<ul><li>…</li></ul>`，替换后仍留在原层，不会 hoist 上去。替换后 id 会变，记得重新 fetch。若只是改一段行内文字（如去掉句中「…」），优先用 `str_replace` 打整句，比 `block_replace` 更稳、也不换 id。
58. **🔴🔴 `1011` 时绝不要"换个姿势重试"，尤其不要把失败 id 和别的 id 凑成一批删。** 本日删某个 `li` 时它的 id 反复报 `1011`（而同一文档里其它 id 都正常）。我为了试探，把它**和相邻 id 塞进同一批 `block_delete`**——结果目标报 `not found`、**相邻那个 id 被删掉了**（批量里的 partial_success 会照删能删的）。重建回来花了好几轮。
    **规矩：targeted 操作失败（1011 / 2001）时先停手查因，一次只动一个 id；确认单 id 的行为后，再考虑批量。** 这是第 39 条（插入与删除别赌在一起）的姊妹条款，但触发方式不同：那条是"插失败删成功"，这条是"目标失败、邻居被删"。
59. **存在"只能改文字、不能做结构操作"的块**（本日实测，新现象）。某个 `<li>`（id 在 `+fetch` 里存在）的表现：
    - `block_delete` → 1011；`block_replace` → 1011；`block_move_after`（作 src）→ 1011；`block_insert_after`（作锚点）→ 1011
    - **`str_replace` → 成功**
    排查顺序：① 确认 fetch 里该 id 确实存在（排除锚点失效）② 逐个命令试，找出一条能用的 ③ 一旦确认只能改文字，**先试"只改文字"的保守收尾，然后隔一段时间重试一次结构性命令**。
    **★ 那个"锁"是暂时态，不是永久损坏**：同一天内该块所有结构命令全 1011，**隔夜后 `block_delete` 一次就成功**。所以判定"永久损坏"之前至少要跨一段时间重试一次；**但绝不要用"凑批"等旁门去试**——批量里的 partial_success 会删掉你没打算删的邻居（见第 58 条，本日真的误删了相邻条目）。
60. **标题/段落文本改不动时，别纠缠 pattern，直接 `block_replace` 整块换。** 本日一个 h2 上的批注 `（3d，SDK 二次开发 可传播的应用（用户自发掘））`（含全角括号与逗号）用 `str_replace` 试了两次都静默失败（返回 success 计数为 0），改成 `block_replace --block-id <标题id> --content '<h3>新标题</h3>'` **一次成功**。判断信号：pattern 里含全角括号、成对括号嵌套、或标点密集时，优先直接换块。
61. **★ 标题的 block id 也会自己变，不要跨轮硬记。** 本日功能总表的 §4 h2 在**没有对它做结构化操作**的情况下，id 从 `doxcn1zTy1FgYrZS8wOsaF4CJEg` 变成了 `doxcn8jrVbr00hEzM0chOWhg68f`（推测是同一位置被重建）。**规矩：任何一轮动手前都重新 `+fetch` 取 id；写脚本时不要把上一轮 dump 出来的标题 id 当常量复用。** 正文里长期不变的只有"内容锚点"（标题文字），不是 id。
62. **"先替换、后拿旧 id 当锚点"是必然 1011**（第 10 / 38 / 57 条的推论，本日再次验证到）。同一节里若要既换引导段、又插新列表：**先插列表（用旧 id 当锚点），再替换引导段**。顺序反了，插入必失败——而且失败信息仍然是那句会误导人的 `1011 Instruction produced no document changes`。

67. **🔴 逐项审读长文档前，必须导出「每块自身文本」，不要用递归摊平**（2026-09-16 实测，差点误报）。给父子嵌套的结构（`<li>` 里嵌 `<ul>`）写审读脚本时，如果取文本的函数递归进子块，**父项的输出会包含它所有子项的文字**——看上去就像"父项把子项重抄了一遍"，于是你会把它当成"分组行重抄子项"（第 51 条那个病）去批注，而文档其实没这个毛病。
    **正确做法**：写两个导出函数。① `own_text(el)` 只拼 `el.text` + **行内**子元素（`a/b/span/text/br/equation/mention/reminder/emoji`）的文本与 tail，遇到块级子元素（`p/ul/ol/li/table/...`）就停；② 递归函数只负责缩进排版，文本一律取 `own_text`。本日先用递归版审到一半才发现，重写后结论完全不同。
    **判别口诀**：父项文本恰好等于「父项文本 + 全部子项文本」时，先怀疑是自己的脚本，别先怀疑文档。

68. **★ 批量加行内批注：`str_replace` + 「唯一句末锚点」，一次几十条稳过**（2026-09-16 跑通 19 条）。做法：
    - 一次 `+fetch --detail with-ids` 拿全文（审读场景要全量，不要 `--scope`）；
    - 对每条批注，**锚点取该条目末尾那半句独立的陈述**（如「距离越近速度越低。」），`--content` = 锚点原文 + `（@ 审读：…）`；这样批注落在句末，既不换 block id，也不碰行内的 `<b>` 粗体组名。
    - **锚点里绝对不要出现全角括号 `（）`**（第 60 条的同类坑），也不要跨 `<b>` 边界；纯中文陈述句最好，且必须全文唯一（写脚本前先 `raw.count(pattern) == 1` 自检一遍）。
    - 每条之间 `sleep 0.4`；脚本里逐条 `grep -E '"result"|"revision_id"'` 打印，跑完再 fetch 一次回读 `count('（@ 审读：')` 应等于条数。
    - **起草批注时避免自称有结论**：批注是给人分的，写法是"这里怎么了 + 我的判断（可被否决）"，不要写成已经定了的结论。

69. **本机 Git Bash 的 PATH 可能缺 `/usr`**（`sed`/`ls`/`head` 全部 `command not found`，exit 127），而 `PowerShell` 工具**禁止 spawn 非 PowerShell shell**（调 `wsl.exe` 会被安全策略拦掉，报 `Spawning a non-PowerShell shell…`）。可行的组合是：**在 Bash 工具里先补 PATH 再调 wsl**：
    ```bash
    export PATH="/c/Users/remo/.workbuddy/binaries/PortableGit/versions/1.2.0/usr/bin:$PATH"
    sed -i 's/\r$//' ./x.sh
    wsl.exe --exec bash -lc "bash /mnt/c/Users/remo/Downloads/tmp_lrc/x.sh"
    ```
    CRLF 的清理放在 **WSL 侧**（`wsl … bash -lc "sed -i …; bash …"`）比 Windows 侧更省事——Windows 侧的 `sed` 一旦不在 PATH 就整条命令挂在第一步。
    `wsl.exe` 启动时会打印一行 UTF-16 的中文告警（`wsl: 检测到 localhost 代理配置…`），**忽略即可**，不影响后续输出。

70. **🔴 修正第 60 条：含全角括号的 `--pattern` 能不能匹配，取决于括号在第几层**（2026-09-16 实测）。给一批批注做清理时连跑 8 条 `str_replace` 删批注，结果是：
    - **批注里只有「」和 ——、没有内层圆括号** → **成功**。所以第 60 条那句"pattern 里含全角括号就优先换块"要收窄：**行内纯文本上的全角括号是可以匹配的**，那个坑只出现在"标题富文本 span"场景。
    - **批注里嵌了内层圆括号**（如「…儿童场合的合规与年龄边界（3.6 只写了现场约定），以及…」）→ **失败**（`result: failed`），换成同一条里不含内层括号的片段也一样失败。
    **处置**：遇到**双层括号**的 pattern 直接改走 `block_replace`（目标是 `<p>` 或普通块时最省事），别在 pattern 上试第三次。
    **更省事的做法**：批注是附在某个块末尾的，**如果那个块本来就要改，就用 `block_replace` 整块重写、批注顺手消失**——本日 14 条批注里有 9 条是这样顺带清掉的，根本没用到 `str_replace`。

71. **★ 改「带子项的分组项」：`block_replace` 一条命令连组名带子项一起换，比"插新列表 + 批量删旧 li"更省事**（2026-09-16 实测两次成功）。嵌套列表里的组 `li` 想要改名、或要增删子项时：

    ```
    --block-id <组li的id>
    --content '<ul><li><b>1.3.3 新组名</b>　新引导句。<ul><li><b>子项1</b>　…</li><li><b>子项2</b>　…</li>…</ul></li></ul>'
    ```

    即：**外层补一个 `<ul>` 把组 `li` 包住，组 `li` 内部自己再带 `<ul>` 写全部子项**。
    实测结论（回读确认）：① 嵌套层级保留，组 li 仍是原来那一层的项；② **旧子项随旧组 li 一起消失，不留孤儿**——不需要再去删旧子项 id；③ 子项会拿到新 id（下次动手前重新 fetch）。
    这比第 51 条推荐的"`block_insert_after` 插新列表 + 按旧 id 批量 `block_delete`"少两步、少一个失败点，**本项目内应优先用它**。
    **前提**：子项内容必须完整写进 `--content`（不会自动保留），所以先把组和它的全部子项文本 dump 出来再拼装，别凭记忆写。加粗用 `<b>` 标签，条目名与说明之间的分隔符沿用文档里的全角空格 `　`，否则视觉层级会和别处不一致。

72. **★ 多轮改同一篇共享文档，收尾必须做三件事**（2026-09-16 跑通，33 次写入无事故）：
    1. **每轮动手前重新 fetch 比对 revision**——本次期间产品负责人一直在同编（标题里加待办、扩写想法），拿旧结构动手必错位。开工前先确认 revision 稳定，是动手的窗口。
    2. **改完复查"大纲逐条一致"**：把编辑前 `+fetch --scope outline` 的 `h1/h2/h3` 列表与编辑后的逐条比对，输出"多出/少了"。本次 33 条完全一致（只有产品负责人自己改的两条标题不同），一眼确认没误删章节或把标题弄丢。比逐个人工看快得多。
    3. **清掉已被改动作废的批注**：改动解决了某条批注，就在同一轮删掉它，否则文档累积过期批注，下一个人分不清哪些还待办。本次 19 条批注随改动降到 5 条（9 条被 `block_replace` 顺带清掉，4 条单独删，另 1 条因内层括号改用 `block_replace`）。**剩下的必须是真待决**，不能留"已解决但没删"的。

73. **🔴 `block_insert_after` / `block_delete` 之后，**后续 id 可能已经变了——同批里的下一条命令会拿到失效 id**（2026-09-16 实测）。本日一批 16 条命令里唯一失败的那条是：先 `block_insert_after` 在 §4.5「开放面」之后插入一条，「外观与分享」组 li 的 id 随即由 `doxcnkYbBNYss3ZYYiHU7jqfrbu` 变成 `doxcnaCPFo7HTju5ytmTLfsdRHc`，紧接着用旧 id 做的 `block_delete` 报 `result: failed`。
    **症状识别**：`block_delete` 报 failed 而该 id 在上一轮 fetch 里明明存在 → **先怀疑它被上一次结构性操作换掉了，重新 fetch 一遍再删，不要怀疑"这个块删不掉"**（那是第 59 条那个少见的暂时锁）。
    **规矩**：把一批操作按"**结构性写入（insert/delete/replace）**"和"**纯行内 `str_replace`**"分开排队——
    - 一批里要连做多个结构性写入时，**每做一次就重新 fetch**（或至少把可能受影响的相邻块 id 全部重新取一遍）；
    - `str_replace` 不换 id，可以安全地连续跑十几条，不受影响；
    - 因此**推荐顺序：先把所有 `str_replace` 跑完 → 再 fetch → 再做结构性写入**（本日第三轮 21 条命令按这个顺序排，只有一处栽在把 insert 和 delete 挨着放）。
    **自检**：结构性写入之后的那条命令若用了上一个 fetch 拿到的 id，就在脚本注释里标一句"此处需重新 fetch"，别赌。

### 媒体（图片 / 视频 / 文件）

14. **取回原素材**：`docs +media-download --token <file_token> --output <路径>`（token 从 `+fetch` 的 `<img src=…>` / `<source token=…>` 里拿）。
15. **本地处理工具**（本机默认没有）：托管 venv 里 `pip install Pillow imageio-ffmpeg` 即可获得图像处理 + **自带 ffmpeg 二进制**（`imageio_ffmpeg.get_ffmpeg_exe()` 拿路径，不必装系统 ffmpeg）。
16. **插入**：`docs +media-insert --doc <url> --file <本地图> --type image --width N --selection-with-ellipsis "<锚点文字>"`；**视频/音频**加 `--type file --file-view preview` 才渲染成内嵌播放器（默认是卡片）。
    - **`--file` 只接受 cwd 下的相对路径**（2026-09-18 踩）：传 `/mnt/c/...` 绝对路径报
      `unsafe file path: --file must be a relative path within the current directory`。
      解法：**先把图 `cp` 进 cwd**（子目录 `./stage/x.png` 也不保险），再用 `./文件名`。
      与 `--content @file` 是同一类约束。
    - **锚点用 `--selection-with-ellipsis` 时，插图落在该块顶层祖先之后**：给每张图配一句**唯一的「选用：…」说明段落**，
      以它为锚点，图就紧跟说明；比用正文句子当锚点稳得多（正文句子容易被别的编辑改掉）。
    - **⚠️ 锚点落在「嵌套 `li`」上时，图会跑到「顶级列表之后」——也就是整节末尾**（2026-09-18 主稿 4.4 实测）。
      主稿 4.4 的正文全部装在一个顶级 `<ul>` 里（h2 / 引导段之后只有这一个列表），锚点取「开发与分享应用」这条嵌套 li，
      图没有落在该条附近，而是落在了列表之后、附录 h1 之前。
      **判据**：目标节如果是「一个顶级列表装下全部正文」，就不要指望插图能贴近某一条。
      想要贴近只有两条路：① 在飞书 UI 里拖；② 先落到节末，再用 `block_move_after` 调（锚点必须是顶级块，
      往嵌套 li 里搬没验证过）。**先把这件事告诉人，不要默认它会落在你锚的那句话旁边。**
    - **同一锚点连插两张，顺序会反转**：后插的离锚点更近。先插 A 再插 B → 实际是 B、A。
      要拿到 A、B 就先插 B 再插 A；已经插反了就用 `block_move_after --block-id <A> --src-block-ids <B>` 换回来。
      **顶级 `<img>` 之间的换序是可靠的**（实测 `result: success` 且位置真的变了），与第 14 条说的「嵌套块 move 静默 no-op」是两回事。
    - 返回里有 `block_id` 与 `file_token`，**逐张检查 `ok: true`**——批量插图时中间失败不会中断后面的。
      **⚠️ 这个返回体带 `_notice` 字段（版本升级提示），`JSON.parse` 必然失败并报成 `NON_JSON`——
      不代表没插进去，必须回读 `<img>` 计数。**
      **连带后果（2026-09-18 踩）：如果你的脚本写成 `const r = JSON.parse(raw)`，`r` 恒为 `null`，
      后续 `if (r.id) { 换序 }` 这类依赖 block_id 的步骤会静默跳过**（插入成功、换序没做，还看不出来）。
      **规矩：block_id / file_token 一律用正则从原文抓**
      （`/"block_id"\s*:\s*"([^"]+)"/`），不要经过 `JSON.parse`。同理适用于 `--command overwrite` 等其他返回 `_notice` 的命令。
    - **⚠️ 批量插图后必须按 `<img>` 计数核对（2026-09-18 踩）**：某一次 `media-insert` 会输出**非 JSON 的进度文本**

      `JSON.parse` 静默失败。**但这个返回"非 JSON"本身不代表失败** —— 同一天两次实测结论相反：
      实验田那次 6 张里**真有 1 张没插进去**，主稿那次 7 张**全部插进去了**。
      **规矩：不要凭返回值判断，插完 `+fetch` 数一次 `<img ` 的个数，跟预期比，缺的单独补插。**
17. **替换 = 插入新的 + 删除旧的**。`--selection-with-ellipsis` 插在匹配块的**顶层祖先之后**；随后 `block_delete` 旧块。
18. **调整位置用 `block_move_after`，不是 `--after`**。图片标签是 `<img>` 不是 `<image>`。
19. **⚠️ `block_replace` 用 markdown 写「**标题**\n\n说明文字」会生成两个独立块**——只记标题的新 id 去 move，会把说明段留在原位。替换后必须重新 fetch 逐块确认。
    **⚠️⚠️ 而且 `--content` 的标签决定块类型：一律包 `<p>` 会把标题降级成正文段落（2026-09-18 真事故）。**

    结果 `1.5 轮足｜…`（h2）、`工程基础｜轮足已从研究走向产品化`（h3）、`4.2 摄像模组`（h2）**三个标题变成普通段落**，
    文档大纲少了两级、导航直接看不到。
    **返回 `result: success` 完全看不出来**——只有回读比对 `<h1..h5>` 计数才暴露。
    **规矩：① 批量改文本前先记下每块原本的 tag，替换时用原 tag 包回去**；
    **② 每批写完后不仅数块数，还要分别数 h1/h2/h3/h4 与列表项，跟改前对齐。**
    修复很简单（用正确标签再 `block_replace` 一次），但必须先发现。
20. **批量改写的正确骨架（2026-09-18 跑通，61+39+33 个操作 0 失败）**：
    - 一次 `+fetch --detail with-ids` → 建 `Map<整块文本, [id...]>`，**唯一命中才执行**，否则报「找不到/不唯一」
    - 规则写成 `{match: 整块原文, new: 新文本}` 纯文本对，**不要手抄 id**
    - 先 `--dry` 跑一遍看解析结果，歧义清零再真跑
    - **执行顺序必须排成 `move → insert → replace → delete`**：`block_replace` 会生成**新块 id**，
      replace 先跑会让后面 move 的锚点失效（实测踩到：1.2 顺序调整报 `failed`，
      一半是方向写反、一半是锚点已被同批 replace 换了 id）

### 线框块（`pre`）

21. **原生结构**：`<pre caption="&#xA;"><code>第1行<br/>第2行</code></pre>`——行间是 `<br/>`，内容包在 `<code>` 里。
22. **⚠️ 不能用 XML 模式替换**：传 `<pre>…<br/>…</pre>` 时 lark-cli 会把 `<br/>` 转义成字面文本 `&lt;br/&gt;`，整块塌成一行。**正确写法 = `--doc-format markdown` + 围栏代码块**。
23. **读回**：fetch 到 XML 后取 `<code>…</code>` 之间、把 `<br/>` 换回 `\n`。
24. **画 ASCII 框必须自己算显示宽度**：CJK（含全角括号、`｜`）= 2 列；box-drawing（─│┌┐└┘├┤）、箭头 ←、`·`、`✓`、`●` = 1 列。写 `wd(s)` + `refit(line)` 批量校正。**顺序坑：先 replace 文本、再 refit**——反过来会让变长的标题行溢出若干列。

## 批量结构编辑的十六条硬规矩（2026-09-21/23 实战沉淀；编号 81–96）

这十条都是当天真实踩出来的，且**多数踩了不止一次**。做多块批量编辑前先扫一遍。

81. **★ 换序：优先「把后者下移」，不要「把前者上移」。**
    `block_move_after` **不支持向上移动**（目标位置在源位置之前时静默失败）。
    所以要让 A 排在 B 前面时，**不要搬 A，搬 B**——把 B 移到 A 的后面。这是下移，`block_move_after` 支持。
    好处：不经内容复制（无丢失风险）、不改 id、可逐块验证。
    **口诀：要 A 在 B 前，就把 B 移到 A 后。**

82. **🔴 插入锚点绝不能是本批的「替换目标」。**（当天踩两次）
    同一批里如果既有 `block_replace` 又有 `block_insert_after`，而锚点块**正好也在替换清单里**：
    替换先执行 → 该块换了新 id → 插入用旧 id 失败（表现为 1011 或 `failed`）。
    危险之处在于**同批的替换全都成功了**，只有插入失败，很容易误判成"做完了"。
    规矩：**先插入、后替换**；或插入单独一轮，执行前重新 fetch 取 id。
    更稳的做法：**锚点一律选本批不动的邻块**。

83. **块替换清单要排除 `<table>` 容器。** 否则整块替换会把**表格压平成一段文字**。
    过滤：`if (b.tag === 'table' || inTable(b.pos)) continue;`
    要改表头/单元格文字时，改用**单元格内的 `<p>` 块**单独 `block_replace`（这个有效）。

84. **多模式批量替换不要用 `for...break`。** 一个块里同时命中多个模式时，`break` 只换第一个，
    漏掉的要等下一遍才清。要么不用 break，要么**收尾统一复扫一遍**（看残留计数是否归零）。

85. **整节删除区间的终止条件必须是「下一个层级 ≤ 当前层级的标题」**，
    **不能用「某个已知的下一节标题名」**。否则两节之间夹着的高层级标题会被一起吞掉
    （实测把 `# 第四章｜硬件与基础能力` 删掉了）。h1 计数从 5 变 4 才暴露。

86. **回读时必须分别数 h1 / h2 / h3 / h4，不能只数总块数或总字符。**
    44 和 41 这两类错误，只数块数完全看不出来。

87. **表格可以整体搬运。** 取 `<table id="…">…</table>` 的**完整 XML**，用 `--content` 插到新位置，
    表格结构完好（实测 16 行 4 列零丢失）。**比用 markdown 重新生成表安全得多**——后者要人肉重打一遍数据。

88. **锚点判据用通用短语时，先干跑看它命中几块、命中哪几块。**
    实测用「借这副身体」找锚点，结果竞品段也含这句 → 会把新内容插到竞品段后面。
    判据要收到**只在该块出现的独特短语**上。

89. **用 `block_replace` 改标题，`--content` 里只放标题文字，不要带 markdown 的 `#` 前缀。**
    写 `<h4>### 3.4.2.3 标题</h4>` 会让标题里混进字面量 `### `（导出成 `#### \### 3.4.2.3`）。

90. **替换会留下多余空格。** 原词常带尾空格（如 `高层 SDK `），替换成中文词后变成「中层原语 组合设备能力」。
    收尾统一 `'新词 '` → `'新词'` 清一遍。

91. **判块顺序要用 XML 的块序列，不要用 markdown 导出的字符位置。**
    两者不是一套坐标系（markdown 里表格的渲染位置与 XML 块顺序不一致）。
    拿 `c.index()` 比 markdown 位置，会得出"归属错了"的**假结论**（当天就被误导过一次）。
    要用 markdown 判顺序时，只比**标题行**的位置。

92. **🔴🔴 替换或删除含嵌套子项的 `<li>` / 标题块，必须把子树内容一起给全。**
    `<li 父><p>…</p><ul><li>子1</li><li>子2</li></ul></li>` —— **整段是一个块**。
    所以 `block_replace` 一个父 `<li>`（你以为只改它自己那句）= **连它的全部子块一起替换掉**。
    实测：只想给一个父项改首句，**它的 4 个子项当场全消失**；紧接着对其中某个子项做 `block_replace` 报 `failed`——
    不是"这个块删不掉"，而是**它已经不存在了**。
    **规矩**：动任何"可能是父节点"的块之前，先确认它有没有子项；有就把**父 + 全部子项（含 `<ul>` 包裹）一次给全**。
    **自检**：`<li>` 块里出现 `<ul>` 就是有子树；同理，`<h*>` 后面若紧跟子级标题，删它时要连带考虑。
    **这与第 82 条是同一类认知错误**——都出在没意识到"一个块可能是一棵树"而不是一行。

93. **`block_move_after` 能一次搬一组块，优先用它做换序。**
    参数是 `--block-id <落点> --src-block-ids <源1,源2,…>`（源按给出顺序依次落在落点之后）。
    搬整节（标题 + 导语 + N 个段落）**一次调用完成**，比"逐块链式移动 7 次"安全得多，而且**不改块 id**，
    搬完还能直接用原 id 继续改标题/正文。实测把 §5.3 的标题+导语+5.3.1 共 7 块一次搬到 §5.2.7 之后，结果顺序正确。
    **注意**：它只能向下搬（把后面的块搬到前面的块之后），不能向上——这就是第 81 条"要 A 在 B 前，就把 B 移到 A 后"。

94. **🔴 `block_replace` 会换掉块 id —— 同一块的多处改动必须合并成一次替换。**
    实测：同一脚本里先替换某段的 A 串，再用**原 id** 替换同段的 B 串 → 第二次静默失败（块 id 已变）。
    **做法**：先把该块 raw XML 取出，在内存里做完所有 `replace`，**只调用一次** `block_replace`；
    或者每次操作前重新 `+fetch` 取最新 id。
    **推论**：脚本里若"先 block_replace 某块、再用该 id 做锚点插入/替换"，一定失败——
    这是第 82 条（锚点不能是本批替换目标）的另一种表现，根因相同：**id 是易变的**。

95. **改「枚举型内容」（功能域清单 / 编号序列 / A—B—C 选项）后，必须回扫引用它的地方。**
    实测：把某处的域清单从 `A 角色化；B 远程到场；C 应用与开发；D 空间采集` 改为 3 项后，
    另一节的"用户不必按 **A—D** 的顺序逐层开启"就失效了，需要同步改成 A—C。
    **做法**：改完枚举，grep 枚举符号（如 `A—D`）与该枚举项的**特征词**，逐处判断。

96. **查「某个多级编号还剩几处」时，必须用词边界正则，否则长编号会假命中。**
    实测：检查 `2.3.x` 残留时，`3.2.3.2 / 3.2.3.3 / …` 这类更长编号的**子串**会被数进来，
    得出「残留 5 处」的假警报；检查 `2.2.1` 时，`3.2.2.1` 也会被命中。
    **做法**：用 `(?<![\d.])2\.3\.\d(?!\d)` 这种前后否定环视；改编号类操作前先跑一次，
    确认「命中的就是标题本身、没有正文交叉引用」，再动手。
    **同样适用于**：统计术语/编号出现次数后据以判断「还有没有残留」的任何场合。

97. **🔴 Windows→WSL 传中文 argv 会被截断或丢失 —— 中文参数一律走文件，不内联。**
    实测（2026-09-24，同一坑连踩三次）：`wsl.exe bash run.sh sec.js "身体、声音与灯效表达"` 到 WSL 侧变成乱码/空串，
    Node 收不到关键字，直接报 `NOT FOUND`；报错里显示 `"Enabot E"… 38 chars total` 这类**被截断**的证据。
    `MSYS_NO_PATHCONV=1`、单引号、双引号、`--exec bash -lc` 全都**不管用**。
    **可靠做法**：把参数写进一个 ASCII 文件（如 `q.txt`，第 1 行=关键字、第 2 行=模式、第 3 行=长度），
    Node 脚本 `fs.readFileSync('q.txt','utf8')` 读它。`--content` 同理，一律 `@./file.xml`。
    **推论**：任何"给 WSL 里的 Node 脚本传参数"的场景，参数通道只认平台无关的**文件**。
    **配套**：run.sh 里要 `export PATH=<nvm node bin>:/usr/local/bin:/usr/bin:/bin` 与 `LANG/LC_ALL=C.UTF-8`，
    否则报 `node: command not found`（`bash -lc` 不加载 nvm）。

98. **定位「某章节有哪些块」用标题区间扫描，不要用标签深度解析。**
    实测：`tops()` 那种"depth 计数器 + VOID 集合"的顶层块解析会在本机 PRD 上**漂**（`depth_end=-2`，
    只因漏识别某个 void 标签或注释），返回的块数与结构都不可信，按它找锚点会指错位置。
    **可靠做法**：正则捞出全部 `<h1..h4 id="...">…</h\1>`，对目标标题取「它自己 → 下一个层级 ≤ 它的标题」之间这段 XML，
    再用 `/<(h[1-4]|p|table|ul|img|whiteboard|quote)\b([^>]*)>/g` 顺序列出，**id 要单独从 attrs 里 `\bid="([^"]*)"` 取**
    （把 id 写成正则可选组 `(?:id="([^"]*)")?` 会拿不到——属性顺序不保证 id 在前）。
    输出格式建议「层级 + 块 id + 前 120 字」一张清单，一眼就能确认锚点选得对不对。
