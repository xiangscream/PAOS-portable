### ★★ 零丢失最强校验：云端块 ↔ 本地行「双向」比对（2026-09-20 实测，700 = 700）

字符数对账（正文/表格/代码块三分账）能定位量级，但**证明不了"某一句话还在"**。
最强的一招是**双向集合比对**，比逐行 difflib 更省事、结论更硬：

```python
cnt_cloud, cnt_local = Counter(cloud_blocks), Counter(local_blocks)
only_cloud = cnt_cloud - cnt_local    # 云端有、本地无 → 真丢了东西会出现在这里
only_local = cnt_local - cnt_cloud
assert sum((only_cloud + only_local).values()) == 0
```

本次跑出 **本地 700 块 / 云端 700 块 / 不匹配 0**，即：本地每一个内容块都在云端，反之亦然。

**四个必踩坑（全部踩过）：**

1. **表格内部的 `<p>` 会被重复计入正文**。取正文时要先算出 table 内所有后代的 `id` 集合，
   把它们从 `p`/`li` 分支里排除。不排除时本次正文多出 1389 字（正好等于表格单元格文本），
   看得像"云端多了一大段"，其实是自己数的。
2. **云端标题文本保留编号**（`own_text(h1)` → `10. 与现有技术路线的关系`），
   所以**本地投影不能把 `10. ` 剥掉**，否则 25 个标题全报不匹配。
   ✏️ 顺带纠正一个想法：`own_text` 是**保留**块内既有文字的，不要指望它帮你归一。
3. **云端可能把连续 `> ` 行合并成一个块**（本次顶部 3 行 blockquote 合成 1 块）。
   本地投影要先把连续引用行 join 再比对。
4. **`Counter` 的差集方向极易写反**（`a - b` 是「a 有 b 无」）。
   我第一版把 `c6/c7` 命名成版本号，结果两组列表的标题贴反，读起来完全颠倒。
   **规矩：变量名直接叫 `cnt_local` / `cnt_cloud`，别用序号。**

**这条校验能抓出的真问题**：本次它只报了 3 处不匹配，其中一处是**真缺陷**——
11 章某节末尾的 `参考：` 与前一句之间**缺一个空行**，markdown 里属于同一段，
导入后 `参考：` 被粘进上一句尾部（`…Capability Envelope。参考：`）。
**这是源稿自带的、过了四轮 overwrite 都没被发现的问题**（因为字符数对账只看总量，看不见结构）。

**顺带加一条发布前体检**：扫「上一行非空、非列表、非标题，本行是 `参考：` / 某个小标题」的组合，
命中就要在中间补空行。markdown 的「无空行 = 同段」在飞书导入后同样成立。

### ★★ 验证链缺的第四环：「原件 ↔ 定稿」反向审计（2026-09-20 事故）

**前四轮校验全绿，但仍然丢了一句实质内容。** 这值得单独记一条。

当时的验证链：① 本地 markdown 体检 → ② 回读比对（云端块 = 本地块）→ ③ 双向集合比对（700=700、不匹配 0）
→ ④ 字符量三分账（代码块、表格精确对上）。

**这四步证明的都是「云端 == 我手上这版稿」，没有一步能证明「我手上这版稿 == 原件」。**
损失是在某一轮编辑里产生的，之后每一轮都拿"上一版"当基准，**链条自己把损失洗白了**。

**事故原样**：可读性那一轮有一处改动标注为「删作者备注括号」——
`并把长程目标变成可执行的任务结构。（GPT-6 接入机器人实时进行任务）` → 去掉括号。
我按"元语言清理"处理了。用户后来指出：**那不是批注，是实质例子**——
GPT-6 接入机器人实时完成任务（编排 + 读反馈 + 调整），正好是「第一层 Embodied Agent」在现实中的实例。
四轮校验全绿，因为它在第二轮开始时就已经不在了。

**规矩：只要某一轮改动包含「删除」或「压缩」，就必须单独跑一次「原件 ↔ 最终稿」差集审计**，
逐条确认每个消失的块属于哪一类，并对 (b)(c) 找到落地处：

| 类别 | 要求 |
|---|---|
| (a) 有意删除 | 能说出删除理由（如实施计划整章删除） |
| (b) 被移动 | 目标位置确实有该内容 |
| (c) 被压缩成回指 | 回指的目标处确实有等价内容 |

**判断括号里是"过程批注"还是"实质内容"的测试**：
> **删掉之后，读者还能从别处拿到这个事实吗？** 能 → 可删；不能 → 它是内容。

经验判据：**短括号 + 具体外部实例名（产品名 / 版本号 / 实验名 / 论文名）通常是「证据指针」，不是编辑批注。**
本次被误删的正是这种。反过来，真正该删的是「本节待补充」「作者认为……」这类**不含事实的**元语言。

**审计脚本骨架**（本次实测抓住了唯一一处非预期丢失）：

def blocks(seg):                     # 切内容块：表格按单元格、代码块整体、引用块合并、列表去标记
    ...
def key(s):                          # 归一化：去 markdown 标记、去空白、把 "见 N.M" 换成占位
    ...
only_orig = Counter(map(key, blocks(chapter(orig, pat)))) - Counter(map(key, blocks(chapter(final, pat))))

**审计范围要按"用户会逐字看的部分"逐章聚焦**（本次只审四个「层」章），
全篇跑会把所有故意的改动一起倒出来，看不过来。

**恢复时的写法**：不要逐字恢复那个括号备注（它本身像占位符），
**写成一句实质论述，挂在该实例恰好能佐证的位置**，数字留在原处、这里只指过去
（一处内容一个家）。本次把实例挂在「Observation / Action Space」两要素之后——
因为 GPT-6 那个实验恰好同时体现这两者；数字留在第 11 章，正文只写
「具体能做到什么程度、又在哪里失效，见第 11 章」。
另外把参考文献里对应条目的出处改成双指向「（见 3 / 11）」，让恢复的链接可追溯。

### 验证

25. **验证脚本必须"内部先 fetch，再打印"**。只读本地 `doc_current.xml` 缓存的脚本会给出过时结论——曾因此误判"页面没改成功"，白折腾一轮。规范：先跑会 fetch 的脚本，再跑读缓存的脚本。
    **⚠️ 同一天又踩一次（2026-09-18，更隐蔽的版本）：`fetch.sh` 写的是 `x.json`，另有一份 `x.xml` 是更早一次转换留下的。**
    我跑完 `fetch.sh` 后用 python 读 `x.xml` 做校验，读到的是**上一版内容**，于是得出结论「第二张图没插进去」并准备重插。
    重跑一次（这次直接从 `x.json` 解析并顺手重写 `x.xml`）才发现图一直都在。
    **规矩：回读只认「本分钟刚写出来的那一个文件」**——要么脚本里 fetch 完就地解析并落盘 `.xml`，
    要么校验脚本直接读 `.json`。**同一批里同时存在 `.json` 和 `.xml` 时，先确认哪个是刚才写的，别默认 `.xml` 是最新。**
26. **探测（probe）不要落在真正要改的块上**。曾用同一个块 id 连做两次探测，第二次覆盖了第一次的"探针"内容，后续 `find("探针")` 失败、脚本中断。
27. **改带链接的富文本段落，`str_replace` 匹配不到**（飞书存 `<a href=...>` 标签，纯文本 pattern 匹配 0 处，但返回 `ok=true`、revision 不变）。**改用 `block_replace` 整段替换**，改完回读关键词验证。
28. **排查标题问题先跑"全文标题体检"**：列出所有 h1–h5 层级 + 编号，再单独扫两类异常——"像编号标题但其实是 `<p>`"的伪标题，和"整段加粗的短段落"（可能是被当小标题用）。比逐处目视快得多。
29. **⚠️ 脚本输出被管道吞掉时，绝对不要直接重跑（2026-09-18 踩，造成真实脏数据）**。
    在 Windows→WSL 这条链路上，`wsl.exe --exec bash -lc "… node x.js" | grep …` 会因为 node 输出里含 NUL 字节
    而只回一句 `Binary file (standard input) matches`，**脚本其实已经执行成功了，只是你看不到日志**。
    我当时以为没跑成，直接重跑一次 → `block_insert_after`（不可重入）和 `media-insert` 各写了两遍，
    实验田文档里多出一组重复的段落 + 图片，只好事后 `block_delete` 收拾。
    **规矩：**
    - 跑这类脚本一律落盘再读：`node x.js > /tmp/x.log 2>&1; tr -d '\000' < /tmp/x.log`。
    - 输出缺失时，**先 fetch 回读判断上一轮到底生效没有**，再决定是否重跑。
    - 同一条命令在一天内出现过「没生效」和「已生效」两种结论时，默认「先怀疑自己的观测方式」。
30. **写操作要能重入，或至少能自证**：`block_replace` 会生成新 block id，所以**第二次执行必然 "failed"——这反而是安全的自证信号**；
    而 `block_insert_after` / `media-insert` 没有这个特性，重跑就是纯重复。
    **优先用可自证的操作，或在脚本里先回读判存在。**
31. **⚠️⚠️ 整节替换（插新块 + 删旧块）的两条硬规矩（2026-09-21 差点毁掉一章）**

    做法：`block_insert_after <节标题id>` 插入新的 markdown 整节（含标题）→ 把**旧标题及其后所有块**逐块 `block_delete`。

    **(a) 删除区间的终止条件必须是「下一个层级 ≤ 当前层级的标题」，不能用「某个已知的下一个节标题」名。**
    事故：重写 `§3.4.D`（h3）时我用「下一个 h2 = 4.1 机器人身体与运动配置」当终止条件，
    但 3.4.D 与 4.1 之间夹着 `<h1>第四章｜硬件与基础能力</h1>`——**整个章标题被一起删掉**。
    回读时 h1 从 5 变 4 才暴露。修复：在节末段之后 `block_insert_after` 补回。
    **回读时必须分别数 h1 / h2 / h3 / h4**，只数总块数或总字符完全看不出来。

    **(b) 选择器要排除落在 `<table>…</table>` 区间内的 `<p>`。**
    表格单元格里的 `<p>` 也是块、也能被正则抓到，但它们是嵌套块、`block_delete` 删不掉，
    会产生一堆**假失败**（父表格删掉后它们跟着一起没了）。
    误判后果很严重：看到「24 个删除失败」会以为操作没做全而**重复执行**，那才是真事故。
    实现：先扫出所有 `<table[\s\S]*?</table>` 的 `[start,end]` 区间，`pos` 落在区间内的 id 一律剔除。

    **(c) 表内 `<p>` 用 `--doc-format markdown` 整节写入更省事**：`+update --content` 支持
    `--doc-format markdown`，markdown 表格会被转成真表格。所以「换表 / 去表 / 加列」都可以
    在整节重写里一次做完，不必逐单元格 `block_replace`（那是 15+ 次调用）。
