# skill-independent-review

**只回答"怎么做"**：如何独立检验一个候选是否真正满足其契约。
它不拥有验收或 merge 权限，不代表执行者修补工作，也不复制工作流程的责任/权限/生命周期/收口语义。复核的授权范围与结论去向由当前任务与批准范围决定。

复核的目标是**独立地**判断，而不是替执行者确认，也不是把执行者的流程重跑一遍。

## 1. 理解契约与变更面

- 先读**预期契约**：需求/验收口径/不变量，理解候选"应该做什么"。
- **固定可定位的候选/基线**（稳定引用），确保复核对象不会漂移。
- 检视**改动面**：实际改变了什么、影响了哪些边界与依赖。

## 2. 挑战隐藏假设与边界

- 主动寻找**未被说明的假设**：输入边界、并发、错误路径、兼容性、平台差异、默认值。
- 检查**边界条件**与"看起来对但其实没覆盖"的场景。
- 区分候选**声明做的事**与**实际做到的事**。

## 3. 按风险选择验证手段

- **focused evidence**：针对契约的关键点做决定性检验。
- 当"原生行为"本身是契约的一部分时，用**真实机器 / 跨运行时**验证（真实文件系统、路径/编码、进程行为），而不只信静态阅读或 mock。
- 验证深度与风险相称：高风险深挖，低风险点到即止，不做无差别全量重跑。

## 4. 分类发现

对每个发现明确归类，避免混淆责任：

- **P1**：阻断性、影响契约正确性、必须解决。
- **P2**：非阻断，但值得记录/后续处理。
- **历史问题**：存在于基线，不是本次引入。
- **环境限制**：由运行环境/工具造成，而非候选本身（标明，不误判为回归）。

同时区分"源码行为"与"环境问题"。

## 5. 报告与 verdict

- 报告**决定性的发现**：证据、可复现路径、影响、归类。
- 给出明确 **verdict**（通过 / 有保留 / 退回）与理由；指出结论的强度与未知。
- **默认不替执行者修补**：复核只给出判定与证据，修补属于执行者职责，除非任务另有授权。
- 复核结论是**输入**，不是 acceptance；最终接受与否遵循相应发布或接受流程。

## 检查问题（自用）

- 我固定的候选/基线是否稳定、可复现？
- 我是否真的独立检验，而不是默认相信执行者的自述？
- 我是否挑战了隐藏假设，而不只看表面 diff？
- 我的证据深度是否与风险相称？
- 我把 P1/P2/历史/环境分清了吗？
- 我是否越权替执行者改动，或代替发布方做接受决定？
