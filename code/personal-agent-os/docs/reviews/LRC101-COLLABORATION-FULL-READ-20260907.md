## 3. 协作全景：发散→补证→反驳→收敛→文档→复核

## 4. 最有效的协作环节（4–6 个，按产出排序）

1. **反驳→收敛环（全文最高产）**。每一次反驳都带来结构性升级而非局部修改：外部批评 → Shot Graph + 证据链（T6）；层级纠正 → L0–L4 能力栈（T8）；可行性回压 → 体验|技术|成熟度映射表（T61）；证伪框架 → 巡逻降级为 Candidate（T65）；公司现实一句（「考虑寻影」）→ GPT 推翻自己上一版激进预设（T193）；技术红线 → 每条 Story 行为挂成熟度列。纯发散（如 T4 的大量候选）若不跟反驳，会产生被自己后续降级的过度承诺。
2. **「用户定海拔、GPT 填结构」的分工**。用户一句话决定讨论层级（T8 拉回硬件底座、T148 立「一个点不要提第 3 次」、T189「先一部分一部分过」、T248「从用户视角而非技术反推」），GPT 在被定海拔内产出完整可执行结构。双方各守其位：用户不代写结构，GPT 不争夺方向权。
3. **语音发散 → 文字成稿的两段式**（T32-52 → T53）。用户用语音低成本倾倒场景设想，再用一条文字指令让 GPT 压成 V0.1 基线文档；配合「你发散、我删减」（T58）与复述校验（T36-38 一次抓出 GPT 弱化关键叙事）。模态分工效率高。
4. **证据警察与证据分级制**。GPT 把强结论逐条降级（「顶住 DJI 压力」「十万级别」「Neo 零蚕食」），区分「口头可讲 vs 正文可写」（T134）；A/B/C 三级证据制（T163）让 Auto Rejoin 这类原创功能诚实标 C 级「痛点真实、解法待验证」，避免为凑证据把逻辑做假。
5. **阶段化产出 + 逐段审阅 + 冻结门**（T189 立制、T221 成体系）。用户明确「不着急整体采用，先一部分一部分过」，之后 20+ turns 全部沿此节奏：GPT 贴原文 → 用户定点改 → 「进入阶段 X / ok 了 / 就这样吧」即冻结。这是防止 AI 全量重写失控的核心工作制。
6. **用户范例教学**（T165）。用户亲手改好 Story 01，让 GPT「学习优化方法」再迁移到 Story 02/03 和第三、四章——一次范例胜过十轮抽象批评；后续「审计语言」类问题又花两个回合（T183/T185）才靠反问式元规则真正内化。

## 5. 用户反复纠正的失败（3–5 种，按复发度排序）

1. **写作者视角/审计腔混入正文**（最高频，跨 ≥6 个回合才收敛）：「会议里最后形成的判断」「这一版」「我建议」「这里不需要…」类内部迭代史语言反复出现在交付稿。T165 用户亲手示范清理、T183 明令禁止、T185 反问考元规则——同一毛病横跨 Story/第三章/第四章三次复发。另含**防御性写作**（「它不是…」「这些参数服务的不是…」，T224/226/229 三次点名）。
2. **内容膨胀与框架过度设计**：10 Gate → 四循环（T10）、第二部分 7 节框架被砍成四章（T148-150）、T173「太长」→T174「太简」→T184「又臃肿」、T206/T217/T228「篇幅太膨胀/主线弱」。GPT 会「加字/减字」但不会「重组信息层级」，每次靠用户定档。
3. **证据强度过高 / 无据精确数字**：「Beni 证明了形态吸引力」「3kg 可接受」「220-300mm 低位光心」——把兴趣信号写成已验证结论、把推断写成冻结参数（T94/T107/T133-134/T200）。需要证据警察机制兜底。
4. **版本边界漂移**：独旅/Auto Rejoin 三次被偷写进首代定义（T94/T101/T107）；第四章职责与第三章重复（T180）、结构约定丢失另起炉灶（T182「你是丢失上下文了吗」）。**最严重一例：T244-245，GPT 把「装配已冻结正文」偷换成「按摘要重新生成」，被用户定性「这是很严重的问题」**，靠历史源映射+SHA256 重建版本信任。
5. **图像/形态生成不达约束**：T88-91 形态图三轮失败（不是双轮腿、没有云台、电机裸露、多轮不一致）——跨模态生成是最明确能力短板，且回复在导出中缺失，无法复盘细节。

## 7. 可分工判断：哪些交 DSH、哪些留 Codex/用户

**适合交执行型 Agent（DSH，本机/窄写通道）：**
- 大材料包通读与结构化摘要（读 5 份飞书 revision、审查包、会议记录，输出「新状态 vs 旧基线」差异）——本报告即是实证；
- 证据分级文档整理（高置信/推断/待确认三分）、外部方法论检索与「对本项目的映射」综述；
- PAOS manual writeback envelope 生成、三表（Decision/Requirement/Evidence）例行维护、Blocker 清单跟踪、链接核查类原子任务（T166 Furbo 式）；
- 语义清洗/术语与数字一致性 QA、版本装配+审计+diff（T240/T245/T246 类，规则已明确）；
- 市场证据并行搜索（T163/T243/T247 类，按功能点或 Research Pack 切块并行）；
- 调研 Prompt 的批量生产（T251 用户发起的多 agent 模式——DSH 可作为并行调研执行体）。

**必须留 Codex/用户：**
- 品类定义、第一锚点、冻结与否的终裁（T6/T12/T16/T224「我坚持」）；价格带与商业化深度（T220→T224 收回）；场景/情节取舍（T236 陪狗、T237 换猫）；
- 「为什么我不买」红队攻击的最终裁决（T16）；外部批评哪些成立的取舍权（T5/T6）；二手证据可信度终判；
- 系统架构次序（T231）、参数背后的工程因果（T226 dToF 限速）、文档方法论（T248 用户视角 vs 技术反推）；
- 跨团队访谈与创始人沟通（人际与政治判断）；公司内部材料确认（Company Pack 类，agent 无权限）；
- 图像/形态生成的质检（T88-91）与版本真实性的最终核验（T244 由人发现）。

## 8. 用 PAOS Work/Request/Artifact/Decision + CAT Exchange 串起来的最小流程建议

把全文里自然生长出的协作方式落到 PAOS/CAT 合同上（不改数据模型，只映射既有对象）：

1. **Work 主线**：「LRC101 产品定义」为一个 Work；每章/每故事为一个子任务由 Session 认领。DSH 执行材料通读、证据嵌入、QA 清洗；Codex 做结构与评审稿；用户裁决。
2. **发散/补证阶段**：Coordinator 发定向 **Request**（调研问题+方法约束，如 T243「不看官方定义、看实际行为」）→ Agent 回 Artifact（带 A/B/C 证据分级）。
3. **反驳/收敛阶段**：GPT 的批评清单 → **Decision**（用户人工裁决：接受/拒绝/改法，对应 T220 的逐条批办）；「考虑寻影」类公司约束直接作为 Coordinator 输入。
4. **文档阶段**：章节正文 → **Artifact**（评审稿）；冻结门 = 用户在 PAOS 里对该 Artifact 的显式确认（对应「就这样吧/ok 了/进入阶段X」）。
5. **复核阶段**：角色扮演审稿（创始人视角找茬）作为 Agent 任务；硬伤门禁作为汇报前检查；**冻结正文的装配必须可溯源**（历史源映射+哈希，对应 T244 教训——这是 S6 事件给 PAOS 的最大警示）。
6. **CAT Exchange 串场**：跨 Runtime 协作（Codex↔DSH↔用户）用 Exchange 传递任务与回执；多 agent 并行调研（T251 模式）= 多 Participant 同 Room、交叉印证在 Timeline 中可见。

一句话：**发散补证进 Request/Artifact，反驳收敛进 Decision，文档冻结进 Artifact 确认，复核溯源进版本审计**——把这段对话里已验证的协作肌肉，装进 PAOS 的正式合同通道。
