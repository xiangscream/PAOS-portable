# Personal Agent OS 开发准则

适用范围：本仓库全部代码与文档。任何 Agent 或人类在动手前先读这一份，再读具体设计书。

前提：**本机单用户、回环地址、本地磁盘、零第三方依赖。** 这些准则是在这个前提下写的；一旦系统跨设备、多用户、开放局域网、接入公司数据或远程 API，第 2、5、9 条要重新评估。

---

## 1. 不以维护向后兼容性为目标

老路径要删掉，不要留着"以防万一"。schema 改了就迁移全部真实数据，然后把旧分支从代码、测试和 fixture 里一次性清除。

**为什么：** 单用户系统里，唯一的 v1 数据就是自己的 8 个项目文件；迁移一次的成本远低于让每个函数长期背两套 schema。v0.4 删 v1 时，`project_store.py` 从 1775 行降到约 1500 行，前端少了 13 处 `schema === V2_SCHEMA` 判断——那些判断每一处都是未来读代码时要重新推理的分叉。

**怎么做：** 迁移前先独立快照 + 记录哈希，dry-run 全部对象，验证数量守恒，再 apply。删代码时把测试一起改到新路径上，而不是保留旧测试来"证明兼容"。

### 1.1 例外：代码兼容可弃，证据兼容永存

这一条准则**只适用于代码、schema 和界面**。它不适用于证据。

**证据 = `ledger` 事件 + `operation_receipts` + Session 的 `close_result`。** 它们记录的是"某时某刻某个 Agent 承诺了什么、做了什么、返回了什么"。这类记录只能追加，不能改写、不能重建、不能因为格式演进而被迁移覆盖。

判据很简单：**这条数据是"当前事实"还是"历史发生过"？**

- 当前事实（`name` / `human` / Work Item 状态 / `next_items`）→ 归准则第 1 条，迁移时按新 schema 重写，旧形态删掉
- 历史发生过（Ledger / 回执 / 关闭结果）→ append-only，迁移只能追加一条说明性事件，不得重写既有条目

**为什么要单独写出来：** 因为这条路已经被走过了。v0.4 迁移 v1 → v2 时，8 个项目的 `ledger` 被重建成了单条 `project.migrated`，v1 时期的 handshake 历史没有保留。现在的账本只知道"这个项目被迁移过"，不知道"迁移前发生过什么"。当时体量小、无实际损失，但它证明了一件事：**遵守准则第 1 条的 Agent 会顺手清理证据，因为准则没告诉它不该这么做。**

**怎么做：**

- 迁移证据类集合时只允许 append，把旧条目原样搬过去；无法解析的旧条目也要保留原文（放进 `raw` 字段），不得丢弃
- 需要改证据格式时，新增字段而不是改写旧字段的含义；读取侧容忍缺字段
- 迁移前的独立快照（准则第 1 条的"怎么做"）对证据来说不是可选项——它是唯一的回退路径

## 2. 采用尽可能简单的实现方案

先问"不加这个东西能不能做到"。JSON 单文件够用就不上 SQLite；标准库够用就不引依赖；一个函数够用就不建抽象层。

**为什么：** 每个多出来的机制都要被理解、被测试、被调试。PAOS 到 v0.3 的全部状态存储就是 `private-data/project-registry/projects/<id>.json` + 原子写 + revision 乐观锁 + 备份，222 项测试覆盖得住，因为要覆盖的东西本来就少。

**边界：** "简单"指结构简单，不指偷工减料。原子写、revision 冲突保护、备份恢复是简单方案的**一部分**，不是它的对立面——静默丢状态不叫简单，叫坏。

## 3. 渐进式分层构建

一次只加一层，加完就能跑、能测、能用。不要为了三个月后的功能先把骨架搭满。

**为什么：** v0.2 的 Session 生命周期是 Open → Ack → Update → Close 一段一段落地的，每段都有自己的测试和可用界面。如果一开始就照最终形态写完再调试，中间没有任何一刻能验证方向对不对。

**怎么做：** 每一层都要有"这一层做完，用户能多做什么"的答案。答不出来的层先不做。

## 4. 保持组件模块化

一个模块一件事，边界写在文档里也写在代码里。

**当前分层（v3 正常入口；改动时不要越界）：**

| 层 | 文件 | 职责 | 禁止 |
|---|---|---|---|
| CLI 入口 | `scripts/paos.py` | 参数、命令装配、结果渲染与错误出口 | 复制业务规则、绕过 Home/Project 写者 |
| 服务模块 | `scripts/paos_*.py` | 各自的语义动作与校验（Home、Mail、Notice、Activation、安装等） | 越界改其它 Home、直接拼 Project 状态 |
| Home 写者 | `paos_todo_v3.py`、`paos_mail.py`、`paos_notice.py`、`paos_attention_service.py` 及激活/唤醒写者 | 只写自己负责的 Home 文件、Mail/Notice/激活事实；合法的跨 Home Mail 投递仍走 mail 写者 | 充当 Project 状态写者、越权改写其它 Home 或绕过对应写者 |
| Project 状态 | `project_store.py`（`ProjectStore`） | **Project JSON 的唯一写者**：原子写、revision、备份、Ledger、operation receipt、恢复 | 写 Home/Mail/Notice、HTTP 概念 |
| 设备/安装定位 | `paos_installation.py`、`paos_workstation.py` | 安装描述、data_root、Library/Windows-WSL locator | 业务状态变更 |
| 业务规则 | 共享 Workflow Library | 角色、工作循环、Notice/Mail、激活与写协议 | 在 Source 复制第二份规程 |
| 历史 HTTP 链 | `local_server.py` → `workflow_service.py` | v2 时代内部管线/兼容，不是当前业务入口或恢复路径 | 以它推断当前业务语义 |

**为什么这个分层值得守：** Project 状态换存储层（比如上 SQLite）只需要改 `project_store.py`；Home 文件则各有独立写者。两条写入边界不能合成“一个唯一磁盘写者”，也不能让服务模块绕过任一写者直接落盘——边界一破，revision、recovery 与责任归属就同时失效。

## 5. 优先采用成熟库（有明确范围）

**允许引入第三方依赖的领域：** 存储引擎、序列化、schema 校验、测试框架。这些领域的正确实现难度高、边界情况多、自己写会长期出错。

**不引入的领域：** UI 框架、状态管理库、ORM、容器化。这些在当前规模下只增加构建步骤和心智负担，原生 JS + 标准库完全够。

**现状：** 零第三方依赖，没有 `requirements.txt`，没有 `package.json`。这不是教条，是当前没有任何需求落在"允许"清单里——SQLite 在标准库里，unittest 和 `node --test` 也在。

**触发条件：** 真的需要复杂筛选统计、跨项目查询、并发写入或多对象事务时，先用标准库 `sqlite3`；仍然不够再谈第三方。

## 6. 优先评估现有依赖（同样有范围）

要加新东西前，先确认现有工具真的做不到。

**判据不是"能不能硬凑出来"，而是"凑出来的代码是不是比引入更难维护"。** 用 `json` 模块模拟出一个查询引擎，比引入 `sqlite3` 更糟——前者是自制的、无人测试过的、只有你懂的东西。

**具体顺序：** 标准库 → 项目已有模块 → 标准库的冷门部分 → 第 5 条允许清单里的第三方 → 讨论扩大清单。

## 7. 架构决策按"爆炸半径"分级，不是"一律不用权宜方案"

改动分两类，用不同的标准：

**核心公共合同**（Project schema、ProjectStore/Home 写者路径、状态转换、错误码映射）——这些地方一个错误会污染真实状态或让所有调用方一起错。这里不要权宜方案，要想清楚长期形态再动，并且配阻塞测试。

**局部实现**（一个渲染函数、一个 Prompt 模板、一个 CLI 参数）——这些地方错了影响半径就是它自己。这里允许先用能跑的写法，之后按需要重构。为它们做"长期演进设计"是浪费。

**为什么这样切：** "永不用权宜方案"听起来严谨，实际会让每个小改动都触发一轮架构讨论，最后是慢和不敢改。爆炸半径是唯一有操作性的判据。

**判断方法：** 问"这个写法错了，是我下次读到时改一行，还是要迁移数据/改所有调用方"。后者才是核心合同。

## 8. 先研究成熟产品怎么解决同类问题（只借机制，不借形态）

遇到陌生问题先看别人怎么做的——但**借的是机制，不是产品形态**。

**该借的：** 乐观锁的 revision 语义、append-only 事件日志、幂等键 + 请求哈希、原子重命名写入。这些是被验证过的机制，PAOS 的单文件原子提交就是这么来的。

**不该借的：** 别人的产品形态、别人的抽象层数、别人为多租户/高并发付的复杂度。Jira 的工作流引擎、Notion 的块模型，解决的是本系统没有的问题。

**为什么强调这个区分：** 照搬形态是"看起来专业"的最大来源，也是复杂度失控的最大来源。PAOS 当前的业务模型——Project 保存耐久事实，固定 Home 保存 Current、TODO、Mail、Notice 与激活证据，Agent 通过 CLI 窄写入——是从用户真实工作方式长出来的，不是从任何产品抄的；不要用某个产品的 Work/Session 形态替换它。

## 9. 错误必须可见、可定位、可恢复

一个错误如果只是让界面变空、让字段静默变 `null`、或者返回 500 而不说原因，它比崩溃更糟——崩溃至少你知道出事了。

**必须做到：**
- 每个错误有能读懂的中文原因，能定位到哪个对象、哪个字段
- 校验失败不写盘，不留半个状态
- 异常类型和 HTTP 状态码要对得上。`ValidationError` → 422、`ConflictError` → 409、`NotFoundError` → 404
- 用户的状态永不静默覆盖：写入前备份，冲突时报错而不是猜

**真实教训：** v0.3 有一个 bug 是 `payload.get("progress")` 把"键不存在"和"值是 None"混为一谈，`None` 流到下游触发 `AttributeError`——而 `AttributeError` 不是 `ValueError` 子类，不在错误映射表里，于是变成 HTTP 500。用户看到的是"保存失败"，没有任何线索。**新增异常类型时，同步检查它是否在映射表里。**

**测试止损（哪些错误值得加阻塞测试）：** 只有三类——
1. 用户正常路径曾经跑不通
2. 可能静默覆盖、损坏或丢失真实状态
3. 核心公共合同修改后容易复发

不属于这三类的，靠代码审查和实际使用发现就够，不需要为它写永久测试。

## 10. 规则变更包含文档退役

升级交付包含现行指南登记、受影响引用检查和旧口径退出。执行方法统一使用共享 Workflow 的 `Guides/guide-project-work-world.md`「准则登记与退役」；定位见[基线导航](V1.2-BASELINE.md#准则与操作入口)。Source 的规则只在对应合同或原则中维护，操作流程链接共享 Library，不复制第二份。

## 附：安全边界（本地单用户前提下的最小集）

保留这五条，其余安全加固推迟：

1. 服务默认绑定 `127.0.0.1`，不开放局域网端口
2. `private-data/`、凭据、真实业务资料不进 Git
3. 项目状态用原子写入 + revision 冲突保护 + 备份与恢复
4. PAOS 主服务不自动启动或调度外部 Agent；人类显式创建并启动的临时 Collaboration Run，可以在限定 Session、有效期与任务数内，通过 Runtime Adapter 调用已配置的唤醒入口
5. 错误可见且可恢复，不静默覆盖用户状态

**明确推迟到系统跨设备/多用户/开放局域网/接入公司数据或远程 API 之后：** scoped capability、一次性 Token、复杂 Origin 权限矩阵、Prompt 出机确认、系统化攻击测试。现在做这些是给不存在的威胁模型付成本。

## 附：文件编辑边界

当前已是分层边界，不是“尚未设计”的单一开关：

- **普通 Project 内容**（正文、文档、成果、`Materials/TIPS.md`）由 Owner 通过正常文件与 Git 直接维护，按共享 Workflow 的 `Guides/guide-project-work-world.md`「项目文本 Git / Project 经验」执行。
- **Home 治理字段与 Project 状态**按已部署写者合同写入：TODO/Current、Mail、Notice、激活走各自 `paos_*` 写者；Project JSON 只走 `ProjectStore`。Service/CLI 不绕过这些写者直接拼状态。
- **框架性文件**（Project schema、写者合同与路径、本文件）修改走人工审查。
- 直接编辑仍要留痕：改了什么、哪个 Agent/Project 归属、能否用所在层的 Git 或恢复点回滚；跨 Home 的合法 Mail 投递按 mail 写者合同进行，不算越权代写。
