# Personal Agent OS 阶段性构建总计划 v0.2

> 文件名保留 `v0.1` 以避免旧链接失效；本页内容自 2026-07-31 起按 v0.2 执行。

## 0. 为什么改计划

外部 Agent 对首版计划的批评成立：为一次隔离、可回退的 32 文件代码迁移设置了过重的设计、Dry Run、三阶段批准和审查流程，元工作开始吞噬实际工作。

这次校正不否定数据边界和恢复意识，而是让流程重量匹配风险：

- Git 分支里的代码复制不是用户资料迁移；
- 可回退的小任务不默认需要独立设计书和审查 Agent；
- Skill、模型和 NAS 只有在真实使用产生具体需求后才进入；
- 当前目标从“完成八周架构”改为“尽快验证系统是否每天有用”。

## 1. 一句话产品定义

Personal Agent OS 是个人注意力与工作记忆控制面：

- Attention Dashboard 决定今天看什么；
- Memory 保留来源、阶段判断和被遗忘但影响决策的信息；
- Skill 只在一个流程被反复证明有效后固化；
- 模型与 Agent 是可替换的执行者，不是系统中心。

Dashboard 的竞争对手是纸笔。系统必须通过“可追溯记忆和阶段性回顾”证明额外价值，而不是通过更多功能证明复杂度。

## 2. 当前唯一问题

如何把已通过 32 项测试的 Attention Dashboard v1.2 与 Markdown Memory Pipeline v0 迁成一个可运行、可恢复的仓库基线，并尽快开始真实使用？

### 当前交付物

一个 Draft PR，包含：

- 两个现有原型的白名单复制；
- Tips Inbox 路径优先级修复；
- 32 项测试与本机 HTTP 验证；
- 最小启动、诊断和恢复说明；
- 敏感扫描结论。

### 完成定义

- 来源不移动、不删除、不覆盖；
- 只修改 `local_server.py` 与对应测试中的既有逻辑；
- Pipeline 17 项、Tips Server 5 项、Dashboard 10 项全部通过；
- `/api/health` 成功，页面返回 200；
- 默认 Inbox 指向 `<repo>/private-data/inbox/tips`；
- `private-data`、Secret、构建产物和真实资料不进入 Git；
- 创建 Draft PR，不直接合并。

## 3. 流程按风险分级

| 等级 | 典型动作 | 默认流程 |
|---|---|---|
| L0 | 阅读、搜索、诊断、对比 | 直接执行并返回结论 |
| L1 | 隔离分支内可回退的代码/文档、Agent 生成文件 | 实施 → 测试 → Draft PR；不另设 Dry Run 或审查 Agent |
| L2 | 真实 Vault 切片、既有用户资料、超过 20 个不可重建文件、新的外部写入 | Dry Run → 用户批准 → 执行 → 校验 |
| L3 | 移动、删除、覆盖、Secret、公司资料、权限、常驻部署 | 快照与恢复验证 → 精确目标 → 用户明确批准 |

补充规则：

- “超过 20 个文件”只针对用户既有、不可重建或难以回退的数据，不机械套用于有 Git 版本保护的代码复制；
- 低成本对抗性审查只用于数据所有权、权限、破坏性动作、冻结规格或连续失败，不作为每个小任务的固定仪式；
- 同一问题三轮失败仍无法定位时停止扩功能，返回最小复现和证据。

## 4. 构建顺序：先用，再治理

### S0｜可运行基线

目标：把现有原型迁入仓库并形成 Draft PR。

执行方式：T-002 在同一轮完成快速预检、复制、最小修复、验证和 Draft PR。预检只在发现异常时触发停止，不单独等待批准。

不做：

- UI 重构；
- 排序算法重写；
- 数据库、Docker 或新框架；
- 真实 Vault、模型、NAS、agent-co Runtime；
- 完整 Skill 治理。

### S1｜三天真实使用实验

进入条件：S0 PR 合并且本机可启动。

唯一问题：

> 这个界面是否真的减少了每天找主线和恢复上下文的成本？

流程：

```text
早晨：确认或手动调整三条主线（≤3 分钟）
白天：Tip 只捕获，不自动变成任务
日终：完成 / 继续 / 降级，并写一句原因（≤5 分钟）
```

硬限制：

- 每天最多显示 3 条待审核候选；
- 活跃主线连续 3 个工作日没有实际推进时，必须显式选择：拆小、降级或归档；
- 不全量扫描 Vault；先由用户手工选择少量低敏 Markdown；
- 不接模型，先验证工作方式。

三天后只做一个判断：继续、修改，或停止。不得用“再加功能看看”代替判断。

### S2｜一周记忆价值实验

只有 S1 被用户判断为有用才进入。

唯一问题：

> 相比纸笔，系统是否能在需要时找回来源明确、真正影响决策的信息？

验证项：

- 任何事实、候选和决策都能返回来源；
- 候选不会静默升级为事实；
- 找回至少一条原本会被遗忘、但改变当前判断的信息；
- 死项目保留停止原因、可复用资产和重启条件；
- 每日系统总交互时间不随数据量上升。

冷启动：系统闲置 5 天后，不要求用户处理积压。未审核候选折叠为“历史未审核”，首页只要求重新选当前三条主线。

G3“记忆治理”不再是独立大 Gate；上述治理规则随 S2 的真实问题逐步实现。

### S3｜一个模型候选实验（可选）

只有当 S2 暴露出一个规则或手工方式明显做不好的任务时进入。首个模型任务只能选一个，例如：

- Tip 初步归类；
- 重复候选识别；
- 日终候选摘要；
- Prompt 边界复述。

模型只生成候选，关闭模型后系统仍可运行。首轮只接一个模型和一种协议。

### S4｜第一个 Skill 候选（可选）

Skill 不再作为预设支柱建设。某个流程连续成功至少 3 次，且不同 Agent 都能按相同边界完成时，才把它整理成 Skill 候选。

优先候选可能是“日终收敛”或“阶段复盘”，但不提前指定结果。

### 后续选项

NAS、个人服务器、本地模型、Runtime Bridge、多 Agent 聊天室均进入候选池，不进入当前时间表。它们必须由一个已出现的使用问题拉动，而不是由技术兴趣自动解锁。

## 5. 成功指标

系统成功不是功能越来越多，而是用户花在系统上的时间越来越少，同时主线和记忆质量提高。

首轮指标：

- 早晨确认三条主线 ≤3 分钟；
- 日终整理 ≤5 分钟；
- 首页活跃主线最多 3 条；
- 每日可见候选最多 3 条；
- 长期项目每周至少发生 2 次真实推进；
- 活跃主线不会无解释地僵尸化；
- 至少一次找回被遗忘但影响决策的信息；
- 用户能根据 README 定位到数据、构建、服务、浏览器或输入层中的故障。

“夜间候选超过一半值得保留”不再单独作为成功标准；如果候选很多，即使保留率高，也可能只是制造了第二个 Inbox。

## 6. 阶段存档

GitHub 保存可执行版本、PR、验证和恢复方式；Obsidian 保存阶段判断、失败原因与个人复盘。小任务不重复写两份长报告，用链接互相引用即可。

存档服务于系统恢复、长期判断和经验复用，不为外部展示预设叙事。
