# 外置记忆与主管式交付：整合需求与实施计划（实施方输入）

> 整合自：37 号编排需求、38 号外置记忆需求、GPT6 的 M0–M5 实施计划、用户的 Room 模型澄清、DS-H 对过度设计部分的回收意见。
> 状态：供网页端 GPT 实施；本文档是唯一实施输入，替代 37/38 中的过度框架部分。
> 基线：PAOS `main@e4f2cdd`（2026-09-08）；CAT 各涉及包实施前单独记录实际 HEAD。
> 整理：DS-H · 3002-s028。

## 1. 一句话目标

让长工作能**可靠接班**（换 Session/换模型/压缩上下文后接得上）+ **可靠交付**（多阶段成果从已审原文装配，不从摘要重新生成）。

**不是**再造调度平台、记忆数据库或工作流引擎。所有能力贴在 PAOS/CAT 既有 durable fact + 投影 + receipt 的地基上。

## 2. 需求范围（简化后，以 GPT6 校正为准）

三个相互独立、可分别交付的功能：

### R1. 轻量 Session 接班（外置记忆）
每个 agent 接入 PAOS 时获得一份**「历史积累 + 当前主线」的持久记录**；新 Session 继承时读它而非翻旧会话全文。

- 新 Session 初始注入 = 前序身份/使命 + 当前记忆入口与短摘要 + 证据锚点 + 未决事项（目标约 2k tokens），**不含**过程历史；
- 过程历史按需读取对应 Artifact，不预载、不粘贴全量进会话；
- Working Memory 最小内容：任务目标及理由、当前执行位置、已确认取舍及来源、当前判断、未决问题、精确产物入口、下一步与审阅者、待接收/回复对象；
- **不承诺**额度节省比例、不承诺「转生零丢失」；测的是接班输入规模、重复读取、接续正确性、完成同一任务的实际成本。

### R2. 精确版本与按原文装配（主管式交付）
阶段成果经审后冻结为**精确版本**；最终交付只从这些已审原文**装配**，不从聊天摘要重新生成（T244 教训）。

- Git 文件用具体 commit+path；非 Git Markdown 用不可覆盖的快照（哈希只用于内容完整性，且仅限此处，不扩散）；
- 冻结后修改须形成新版本，旧版本仍可读；替代只改当前选用关系，不撤销历史审阅；
- **冻结 ≠ 人类认可**：工作记忆/普通实现包可由 Agent 写、主管验收；产品方向/最终稿等仍走人工关口（不把 Agent 自报提升为人类承诺）。

### R3. 项目底层 Room + Coordinator 触达下属（通信层）
每个 project 有一个**底层 Room**；每个 agent 接入时被分配一个 CAT「邮箱」（Participant）；Coordinator 由此能**联系自己全部下属**——不需要人手动建 Room/拉人。

- 这是 Coordinator 编排动作的通信底座：PAOS assignment/request（已有动词）+ CAT room/participant（已有 API）串成一个受权的编排动作（cross-system Saga，失败分步可见）；
- 这是 g008（Agent-Agent 边）与 g015（Coordinator 主流程）在通信层的统一；**不单独立项工作流引擎**。

## 3. GPT6 的七处事实校正（实施前必须吸收）

1. **Artifact 冻结尚未实现**——不得把「可冻结/可溯源」写成现有能力；
2. **Session 继承已有代码**（continues_session_id）——不要重造员工身份系统；
3. **换 Session 不重置额度**——删除「<40% 窗口」「零丢失」类保证；
4. **current/已审/冻结是不同维度，非互斥三态**——最小方案：追加版本+替代关系+独立审阅记录，投影算当前选择；
5. **冻结 ≠ 人类认可**——范围收敛，避免制造新行政负担；
6. **文件存在 ≠ 证据固定**——用精确 commit 引用或不可覆盖快照；哈希仅内容完整性、仅限交付装配，不扩散；
7. **retirement ≠ 消息自动转交**——CAT 交班必须是显式 Saga，含未读责任归属与部分成功状态。

**采用**：Artifact 精确引用/来源关系、按需 Context 投影、跨系统分步恢复。
**不采用**：「纯机械计算可识别语义冲突」——机械工具只发现参数/版本差异；语义矛盾由 Agent 提出、主管审阅、产品分歧交人类裁决。

## 4. 实施计划（GPT6 的 M0–M5 + R3 补充）

> 原则：**先让一个全新原生会话可靠接班，再让多阶段已审成果可靠装配。** 共享的是 Artifact 精确引用与来源关系，不先建通用治理平台。

| 里程碑 | 目标 | 依赖 | 用户收益 | 关键验收 |
|---|---|---|---|---|
| **M0 合同收敛** | 冻结最小合同 + 可执行样例 | — | 新执行者只读合同即可回答「记忆与事实冲突怎么办/谁能审/审哪个版本/最终内容从哪来」 | 输出 `docs/contracts/MEMORY-AND-DELIVERY-V0.md` + 接班/装配样例；不扩领域对象、不跑真实迁移 |
| **M1 轻量接班** | 新原生会话能接着干，不翻旧会话全文 | M0 | 首次减轻上下文 | 加入大量无关历史后接班包不线性膨胀；记忆旧态与实时 Work 冲突按实时事实；独立会话能指出已批准版本/未完成步骤/正确审阅者 |
| **M2 精确版本+冻结** | 通过稿可找回，修改不偷换已审内容 | M0/M1 | 交付可信 | 审后改源文件可发现且旧稿可恢复；冻结被替代后仍留冻结证据；幂等/Restore 继承内核合同 |
| **M3 阶段审阅+装配** | 多阶段结果直接组成交付 | M2 | 不再从摘要重写 | 两份已审章节确定性装配；漏章/混入未审稿被拒；源稿被覆盖仍能从冻结版装配；局部返工不重生成未受影响章节 |
| **M4 PAOS↔CAT 可恢复交班** | 页面发起「接班并继续接收 Room 消息」，每步结果可见 | M1/M2 | 跨系统换班可控 | 旧未读与换班窗口新消息都有人负责；CAT 不可用时 PAOS 接续成功可见；恢复后不产生第二 successor |
| **M5 真实验收+发布** | 一个 ≥3 阶段真实文档任务端到端验证 | M1–M4 | 可信上线 | 含两个独立执行包、一次实质返工、一次接班；人工 Gate 未被主管替代；成本对比用同类任务同模型（不用共享窗口百分比推导精确费用） |
| **M6（R3 补充）项目底层 Room + 邮箱分配** | Coordinator 能触达全部下属，不需人手动建 Room/拉人 | M1 后 | Coordinator 自组织通信 | agent 接入 PAOS 时自动分配 CAT 邮箱并入 project 底层 room；Coordinator 一个受权动作完成 assignment + room 编排；失败分步可见可恢复 |

**执行顺序**：M0→M1→M2→M3→M4→M5；M4 技术上可在 M2 后并行，本次默认串行降协调成本；M6 作为独立卡并行排（不塞进 M0 合同收敛里稀释）。

## 5. 不变式（不可违反）

1. **冻结即冻结**：已冻结内容永不被改写；装配只读已审原文，绝不从摘要重新生成；
2. **决策门必须人类**：产品方向、承诺、最终批准、分歧裁决——Coordinator 只能提出不能代办；普通实现/测试包由主管验收；
3. **纯投影不加对象**：Intake/Gate/聚合/索引视图都从现有 Artifact/Request/Needs-me 投影；V0 不新增 Stage/Gate/Workflow/Memory 独立实体；
4. **历史 append-only**：老 Artifact 保留原始证据，不批量补造审阅人/哈希/冻结时间；治理只向前；
5. **跨系统不越界**：PAOS 不 import CAT、不读 CAT 私有文件；CAT 访问 PAOS 只经只读 HTTP adapter；交班是显式 Saga 不是隐式级联。

## 6. 交付纪律（沿用 SUPERVISED-DELIVERY.md）

- Codex 负责计划、关键取舍、独立阶段验收；DS-H 负责包内实现、测试、初审、修订；不以自审代替独立验收；
- 每包先写实际输入 HEAD、文件清单、验收命令；每包独立提交并保留精确审阅版本；
- 核心合同变更跑全量 verifier；文档/低影响改动不机械重跑；
- 短分支→PR→主管复核→按批准合并主干→删短分支；不长期堆积只 push 未 merge 的分支；
- **历史 Ledger/receipt/Close 证据不清理**；临时数据测试，真实业务写入依任务授权。

## 7. Grill 待定项（实施时逐个关闭）

1. **Working Memory 形态**：新 Artifact 类型 vs 复用现有 Artifact 追加（GPT6 倾向后者：每个检查点保存新文件/版本，note_for_next_session 只留当前记忆入口）——M0 定；
2. **M6 的 Room 模型**：project 底层 room 是否自动随 project 创建？邮箱分配是否随 agent 注册自动发生？——M6 设计时定；
3. **M2 快照存储**：非 Git Markdown 的不可覆盖快照放哪（建议 `private-data` 下的内容寻址或 approved/ 目录）——M2 定；
4. **接班包预算的度量**：2k tokens 目标不引入 tokenizer 依赖，用什么近似（字符数/条数上限）——M0 定。

## 8. 第一张执行卡

**M0**：输出 `docs/contracts/MEMORY-AND-DELIVERY-V0.md`（合同 + 一份真实形状的接班样例 + 一份两章节装配样例 + 动作与权限表），供主管审阅；通过后只放行 M1。

第一次阶段收益：一个新 Session 能从短接班包准确接续工作，并能找到已批准原稿。

**明确不并入**：g008 的 Agent-Agent 关系线（M6 另行）、g015 的全部 Room UX、DSH 上游升级——各自有独立实施包；成为接班实测的具体阻碍时再按实际依赖处理。
