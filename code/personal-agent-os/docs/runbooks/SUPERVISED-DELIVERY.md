# 主管式交付：计划、执行、阶段审阅、保存、装配

状态：2026-09-07 用户确认的工作规则已落地；LRC101 全文证据补充待 DS-H 完整阅读，不将选读算作全文阅读。

## 1. 分工与唯一交付原则

Codex 负责详细拆解、关键判断、阶段验收和最终整合；DS-H 负责材料通读、检索、实施、测试、初审和阶段内修订。产品方向、承诺及明确保留的人类批准事项仍由用户决定。初审可以由执行者做，但不能称为独立审查。

**最终交付来自已验收文件的装配，不来自对话摘要的重新生成。** PAOS 保存长期工作事实和证据入口；CAT 传递任务、问题和阶段汇报；文件保存完整产物。三者不复制全量内容，不新增数据库或工作流引擎。

## 2. 开始前：把执行计划写细

沿用项目已有计划文件；没有时建立一份 `EXECUTION-PLAN.md`。先填本次最终交付物和不能变的边界，然后拆成可独立审阅的包。每包写清：

1. 要解决的问题、对应最终文档章节或代码能力；不做什么。
2. 输入：实际存在的路径、版本或 Git revision；哪些是人类已确认、哪些只是候选。
3. 执行步骤：先读什么、产出什么、怎么检查；不要只写“完善”“优化”。
4. 输出：精确文件路径；大文档先按章节保存，不等全稿完成才写盘。
5. 验收：主管实际要看到的证据与正常流程结果，而不只是测试数字。
6. 依赖及下一道关口：哪些包可并行、哪些必须等前包通过；谁审阅。

已批准的大方向不重复问；执行者可在包内补证据、试错、自审、修改。只有超出范围、关键产品选择或必需材料确实缺失才升级。不得把“材料发过去了”当成“执行者已接单”。

## 3. 分阶段执行

| 阶段 | DS-H 工作 | Codex 验收 | 必须留下的文件 |
| --- | --- | --- | --- |
| 输入整理 | 分段通读，记录覆盖范围；提取已批准内容、候选、被否决方案和缺失附件 | 抽查关键原文与来源，确认不把历史指令当新任务 | 输入索引和覆盖记录 |
| 详细计划 | 将目标展开到章节/功能包，列步骤、输出和依赖 | 校正产品判断和串行顺序；用户只裁决需其决定的事项 | 本次执行计划 |
| 单包执行 | 按输入版本完成内容/代码，先自审，解决包内问题 | 检查关键证据、正确性和与上包的一致性 | 候选正文/代码、验证结果 |
| 阶段收口 | 对审阅问题逐项修订，保存修订差异 | 通过、局部返工或需人类裁决；只重审受影响部分 | 精确通过版本及审阅记录 |
| 最终装配 | 按清单读取通过文件，统一获准的编号、目录和格式 | 核对未漏章、未混入候选、未悄悄改结论 | 最终稿、装配清单及差异说明 |
| 使用与交接 | 留入口、已知缺口和下一步，按授权发布 | 确认用户实际能取用；不把发布等同产品成熟 | 使用入口、交接记录 |

研究任务允许发散，但发散稿和通过稿分开。代码任务沿用提交与测试证据，不机械套用文档章节形式。一个包未完成不必阻塞其他无依赖工作。

## 4. 阶段通过后立即保存

沿用现有版本管理。无 Git 的长文可用 `approved/章节-v1.md` 留下通过正文；有 Git 的代码引用精确提交和受审文件。不要为了此流程擅自提交或推送。

在计划中直接记四项：通过的文件/版本、审阅者及时间、通过范围、仍未通过事项。用户对正文的原句修改优先保留；仅凭“总体认可”不能推断后续新写内容也已获批。

通过文件不能被候选覆盖。确有新事实要改时，生成新版本并说明语义差异，重审受影响部分后再切换引用。上下文压缩、换 Agent、服务中断后，从计划与通过文件续接，不从聊天记忆重建。

## 5. 最终装配的验收

装配前列出“最终章节 → 通过正文路径/版本”，缺一章就先补源文件，不让模型凭摘要填空。装配时只允许已约定的格式与编号统一；所有实质改动单列，不混在排版修正里。

验收至少检查：

- 每个最终章节都能追到通过原文；缺失附件不伪装成已恢复。
- 与通过原文比较，未授权删段、压缩论证、改参数、改故事或重排结论为零。
- 新旧版本的名词、参数、交叉引用冲突有明确处理记录；不能静默挑一个。
- 最终文件可打开、内容完整；视觉产物完成对应视觉检查。
- 未通过部分明确排除或标待审，不把“看起来完整”当完成。
